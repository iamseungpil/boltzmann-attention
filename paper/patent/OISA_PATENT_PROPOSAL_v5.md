**Method for Constructing Multi-Facet Orthogonal Ontology from Denormalized Domain Data and Internalizing Context-Dependent Tool Selection into Large Language Models**

## 1. 발명의 명칭

**한글**: 비정규화 도메인 데이터의 다면 직교 온톨로지 구성 및 이를 활용한 대규모 언어 모델의 컨텍스트 의존적 도구 선택 내재화 방법

**영문**: Method for Constructing Multi-Facet Orthogonal Ontology from Denormalized Domain Data and Internalizing Context-Dependent Tool Selection into Large Language Models

---

## 2. 기술 분야

본 발명은 대규모 언어 모델(Large Language Model, LLM)의 파라미터 효율적 미세조정(Parameter-Efficient Fine-Tuning, PEFT), 어텐션 메커니즘 최적화, 도메인 온톨로지 반자동 구성, 및 온톨로지 기반 자연어 처리에 관한 것이다.

구체적으로, (1) 엔터프라이즈 현장의 비정규화(denormalized) 데이터로부터 상호 직교하는 복수의 의미론적 관점(facet)을 자동 발견하고 각 facet 내에서 정규화된 클래스 체계를 구성하는 방법, (2) 발견된 다면 직교 온톨로지를 LLM의 모델 가중치에 내재화하는 facet 조건부 미세조정 기법, (3) 이름과 기능이 중복되는 수천 개의 도구를 facet 벡터로 분류하고 팀별·개인별 선호에 기반하여 모델 가중치 수준에서 추천하는 방법, (4) 키-값(Key-Value) 캐시를 facet 중요도에 기반하여 적응적으로 압축하는 포스트 트레이닝 어댑터, 및 (5) 정적/동적/개인화 온톨로지의 3단 분리 학습 방법에 관한 것이다.

본 발명은 다수의 이해관계자가 서로 다른 분류 기준으로 동일 데이터를 해석하고, 이름과 기능이 중복되는 다수의 도구를 운용하며, 오랜 기간 다수의 담당자에 의해 비정규화된 메타데이터가 축적된 모든 엔터프라이즈 AI 에이전트 시스템에 적용 가능하다. 구체적 적용 도메인으로는 금융(고객 데이터 플랫폼, 마케팅 자동화), 의료(전자의무기록 EMR, 임상시험 관리, 보험 청구), 제조(설비 관리, 품질 관리, 공급망), 물류(배송 추적, 재고 관리, 창고 운영), 공공(행정 데이터, 민원 관리), 이커머스(상품 카탈로그, 고객 행동 분석) 등이 포함되나 이에 한정되지 않는다. 특히 장기간 운영되어 수십에서 수백 개의 독립적 분류 관점이 파편적으로 축적된 레거시 데이터베이스 환경에서 효과적이다.

## 3. 배경 기술 (종래 기술의 문제점)

### 3.1 엔터프라이즈 AI 에이전트의 현장 제약

엔터프라이즈 환경에서 LLM 기반 AI 에이전트는 수십에서 수천 개의 도구 스키마, 데이터베이스 테이블 정의, 워크플로우 규칙, 도메인 용어집 등을 컨텍스트로 제공받아야 한다. 예를 들어, 고객 데이터 플랫폼에서 45개의 분석 도구를 운용하는 경우, 도구 스키마만으로도 82,000 토큰 이상을 소비하며, 이는 단일 요청당 KV(Key-Value) 캐시 20.5GB를 점유한다. NVIDIA H200(141GB HBM3e) 4장 구성에서도 동시 처리 가능 사용자는 13명에 불과하여, 엔터프라이즈 규모(100명 이상 동시 접속)의 서비스에는 근본적으로 부적합하다.

또한, 도메인 특화 환경에서는 동일한 자연어 용어가 완전히 다른 의미를 가지는 동음이의어(homonym) 문제가 빈번하다. "전환"이라는 용어 하나가 마케팅 맥락의 전환율(exit_count/inflow_count)과 사용자 행동 분석의 페이지 전환(page transition)이라는 전혀 다른 개념을 지칭할 수 있으며, 종래 시스템에서의 동음이의어 정확도는 58%에 불과하다.

### 3.2 엔터프라이즈 데이터의 비정규화 문제

실제 엔터프라이즈 환경의 도메인 데이터는 다음과 같은 비정규화(denormalization) 특성을 가진다. 이는 장기간 다수의 담당자에 의해 독립적으로 구축·유지된 결과이며, 종래의 온톨로지 기반 기술이 전제하는 "정규화된 도메인 지식"과 근본적으로 괴리된다. 이 특성은 금융뿐 아니라 의료, 제조, 물류, 공공 등 레거시 시스템을 운용하는 모든 도메인에서 공통적으로 관찰된다.

**첫째, 다중 분류 체계의 혼재.** 동일 엔티티(예: "우리꿈적금" 상품)가 시스템 내에서 최소 3가지 이상의 분류 기준으로 동시에 존재한다.

```
동일 엔티티 "우리꿈적금"의 다중 분류:

  개발자 관점 (메뉴 트리):
    공통/기타 > 금융상품 > 입출금/예금/적금 > 가입하기 > 상품 상세
    → 페이지 ID: NWMMH00051_001M

  마케터 관점 (캠페인 카테고리):
    캠페인상품 > 예적금 > 고금리적금 > MZ타겟 > 우리꿈적금
    → 전환율, ROAS, 타겟 세그먼트 중심

  분석가 관점 (행동 퍼널):
    상품탐색 > 상품조회 > 상세진입 > 가입시작 > 약관동의 > 가입완료
    → 퍼널 이탈률, 체류시간, 경로 분석 중심

  운영자 관점 (상품 관리):
    상품관리 > 활성상품 > 수신상품 > 적금 > 우리꿈적금_v3
    → 상품 코드, 약관 버전, 금리 조건 중심
```

이 네 분류 체계는 서로 독립적이며, 하나의 온톨로지 트리로 통합할 수 없다. 개발자 관점의 메뉴 트리 위치가 변경되어도 마케터 관점의 캠페인 분류는 불변이며, 분석가 관점의 퍼널 단계가 동일해도 운영자 관점의 상품 코드는 다르다.

이러한 다중 분류 체계의 혼재는 금융에 한정되지 않으며, 레거시 시스템이 존재하는 모든 도메인에서 관찰된다.

```
다도메인 비정규화 예시:

[의료 도메인] 동일 엔티티 "아스피린 100mg"의 다중 분류:
  임상의 관점:     심혈관계 > 항혈소판제 > 저용량 아스피린
  약사 관점:       ATC 코드 B01AC06 > 비스테로이드 항염증제
  보험 관점:       급여코드 641600070 > 일반의약품 > 경구제
  공급망 관점:     바이엘 > 수입의약품 > 냉장불요 > 정제
  연구자 관점:     COX-1 억제제 > 혈소판 응집 억제
  → 최소 5개의 독립적 분류 관점이 공존

[제조 도메인] 동일 엔티티 "CNC 밀링머신 #3"의 다중 분류:
  생산관리:        제2공장 > A라인 > 3번 설비
  보전관리:        정밀가공설비 > 5축 > 2020년 도입 > 주기적점검
  품질관리:        정밀도 ±0.01mm > ISO 9001 > 측정기구 연계
  원가관리:        감가상각 대상 > 잔존가액 2억 > 2030년 폐기 예정
  에너지관리:      전력 대소비 설비 > 피크시간 가동제한
  → 최소 5개의 독립적 분류 관점

[물류 도메인] 동일 엔티티 "배송건 #2024-0312"의 다중 분류:
  고객 관점:       마이페이지 > 주문내역 > 배송중
  운송사 관점:     허브→서브허브→배달 > 3PL_A사 > 냉장차량
  상품 관점:       신선식품 > 냉장 > 3kg 이하 > 당일배송
  CS 관점:        정상배송 > 클레임없음
  재고 관점:       김포물류센터 > B-3구역 > 출고완료
  → 최소 5개의 독립적 분류 관점

핵심: 도메인이 복잡할수록, 레거시가 길수록 분류 관점(facet)은 증가한다.
  금융(CDP): 4~8개 facet
  의료(EMR+보험+연구): 10~30개 facet
  제조(스마트팩토리): 10~50개 facet
  대규모 이커머스(상품+고객+물류+마케팅+CS): 20~100개 facet
  범정부 행정 데이터(부처 간 연계): 50~수백 개 facet
```

**둘째, 경로 표기의 불일치.** 동일 시스템의 페이지 경로 데이터에서조차 구분자가 통일되지 않는다. 실제 데이터에서 관측된 4가지 이상의 구분자 패턴은 다음과 같다.

```
구분자 패턴 혼재 (실제 현장 데이터):

  패턴 A — ">" 공백 포함:
    "메인(나) > 로그인전 > 로그인 이력 있는 고객"

  패턴 B — ">" 공백 없음:
    "메인(나)>금융회원 홈(일반홈)"

  패턴 C — "-" 구분:
    "즉시/예약이체-입금계좌 입력"

  패턴 D — 구분자 없음 (연접):
    "공통/기타로그인우리won인증서 로그인PIN"

  패턴 E — 혼합:
    "인증/보안 > 본인확인 > 휴대폰 본인확인"
    ("/" 는 카테고리 내 구분, ">" 는 계층 구분)
```

이 혼재는 장기간 다수의 개발자가 독립적으로 페이지를 정의한 결과이며, 단순 정규표현식 파싱으로는 계층 구조를 정확히 추출할 수 없다.

**셋째, 식별자-콘텐츠 불일치.** 동일 페이지 식별자(Page ID)가 수십 개의 서로 다른 콘텐츠에 매핑된다.

```
식별자-콘텐츠 불일치 예:

  NWMMH00051_001M = "안내" = "금융상품 > 입출금/예금/적금 > 가입하기 > 상품 상세"

  이 하나의 페이지 ID에 매핑되는 실제 콘텐츠:
    - 우리SUPER정기예금 상세
    - WON플러스예금 상세
    - 우리꿈적금 상세
    - 우리SUPER정기적금 상세
    - ... (수십 개 상품)

  → 페이지 ID만으로는 실제 콘텐츠를 구분 불가
  → 템플릿 기반 UI 아키텍처의 필연적 결과
```

**넷째, 도구의 대규모 중복.** 엔터프라이즈 환경에서 수천 개의 분석 도구 중 이름이 중복되거나 기능이 유사하지만 파라미터·출력 형식·집계 기준이 다른 도구가 다수 존재한다.

```
도구 중복의 세 가지 유형:

  유형 1 — 이름 중복, 기능 상이:
    "전환율 분석" (마케팅팀용): 파라미터={채널, 기간}, 출력=채널별 CVR
    "전환율 분석" (분석팀용): 파라미터={퍼널단계, 세그먼트}, 출력=단계별 전환율
    "전환율 분석" (경영진용): 파라미터={사업부}, 출력=사업부별 요약 보고서

  유형 2 — 이름 상이, 기능 유사:
    "채널별 유입 분석" / "유입 채널 분석" / "채널 퍼포먼스"
    → 세 도구 모두 채널별 유입량을 분석하나 집계 기준이 상이

  유형 3 — 이름·기능 유사, 사용 맥락 상이:
    팀 A는 "채널별 유입 분석"을 항상 사용
    팀 B는 "채널 퍼포먼스"를 선호
    → 동일 목적이나 팀별 관습에 의한 도구 선택 분화

  문제: 이 모든 도구를 프롬프트에 나열하면 82,000 토큰 초과
  → 도구 간 차이를 LLM이 프롬프트만으로 구분하는 것은 불가능
```

### 3.3 종래기술 1: GraphRAG 기반 온톨로지 활용

Microsoft GraphRAG(2024) 등의 기술은 도메인 지식을 그래프 데이터베이스(Neo4j, TypeDB 등)에 저장하고, 매 추론 시 관련 서브그래프를 검색하여 프롬프트에 삽입하는 방식을 취한다.

이 방식의 문제점은 다음과 같다.

**첫째, 단일 온톨로지 전제.** GraphRAG는 하나의 정규화된 온톨로지 그래프를 전제하나, §3.2에서 기술한 바와 같이 실제 환경에서는 동일 엔티티에 대해 이해관계자별로 다른 분류 체계가 공존한다. 단일 그래프로 이를 표현하면 에지(edge)가 폭증하여 검색 정밀도가 하락한다.

**둘째, 추론 시 외부 의존성 문제.** 매 요청마다 그래프 DB에 SPARQL 또는 Cypher 쿼리를 실행해야 하므로 50~200ms의 추가 지연이 발생한다. 그래프 DB 장애 시 전체 서비스가 중단되며, 마이크로서비스 아키텍처에서의 cascading failure 위험이 존재한다.

**셋째, 토큰 소비 문제.** 검색된 온톨로지 서브그래프를 텍스트로 직렬화하면 2,000~4,000 토큰이 추가 소비된다. 기존 도구 스키마 82,000 토큰에 더해지므로 총 프롬프트 크기가 86,000 토큰을 초과하게 되어 KV 캐시 부담이 가중된다.

**넷째, 비정규화 데이터 미대응.** GraphRAG는 정규화된 그래프를 입력으로 요구하며, §3.2의 비정규화 데이터를 자동으로 정규화하는 메커니즘이 없다. 비정규화 데이터를 수작업으로 정규화하는 비용은 도메인 전문가의 수개월 작업을 요구한다.

### 3.4 종래기술 2: 기존 LoRA/QLoRA 미세조정

LoRA(Hu et al., 2021)는 사전 학습된 모델 가중치를 동결하고, 저랭크(low-rank) 행렬 A, B를 추가하여 미세조정하는 기법이다. QLoRA(Dettmers et al., 2023)는 이를 4비트 양자화와 결합하여 메모리 효율을 높인다.

이 방식의 문제점은 다음과 같다.

**첫째, 다중 관점 학습 실패.** LoRA/QLoRA는 입출력 쌍(input-output pair)의 패턴을 학습하지만, 동일 엔티티에 대한 복수의 분류 관점(개발자/마케터/분석가/운영자)을 명시적으로 분리하여 학습하는 메커니즘이 없다. 단일 (B, A) 행렬이 모든 관점의 입력에 동일하게 적용되므로, 관점 간 간섭(inter-perspective interference)이 발생한다.

**둘째, 구조적 관계 학습 실패.** 온톨로지의 is-a, has-metric, belongs-to 등 구조적 관계를 명시적으로 학습하는 메커니즘이 없다.

**셋째, 동음이의어 해소 메커니즘 부재.** 대조학습(contrastive learning) 없이 단순 지도학습만으로는 미묘한 문맥 차이를 포착하기 어렵다.

**넷째, Catastrophic Forgetting.** 정적 도메인 지식과 동적 사용자 선호를 동일 adapter로 학습하면, 동적 지식 업데이트 시 정적 지식이 망각된다.

### 3.5 종래기술 3: Mixture of LoRA (MoLoRA) 및 Mixture of Experts (MoE)

MoLoRA 및 MoE 방식은 학습 가능한 라우터 네트워크가 expert를 선택하는 구조를 취한다.

이 방식의 문제점은 다음과 같다.

**첫째, expert 정의의 고정성.** expert의 수와 역할이 사전에 고정되며, 현장 데이터의 다중 관점 구조를 자동으로 반영하는 메커니즘이 없다. 새로운 관점이 추가되면 전체 라우터를 재학습해야 한다.

**둘째, 라우팅 불안정(routing instability).** 학습 가능 라우터는 expert collapse(특정 expert에 트래픽 집중), 라우팅 진동(oscillation) 등의 불안정 문제를 야기한다.

**셋째, 단일 차원 라우팅.** 기존 MoLoRA/MoE는 하나의 라우팅 결정(어떤 expert를 선택할 것인가)만을 수행하며, 복수의 직교 관점에서 동시에 라우팅하는 메커니즘이 부재하다. 예를 들어, "이 입력은 마케터 관점(F1)에서는 캠페인 분석이고, 기능 관점(F2)에서는 측정이며, 데이터 관점(F3)에서는 수신 상품이다"와 같은 다면적 라우팅이 불가능하다.

### 3.6 종래기술 4: Native Sparse Attention (NSA)

DeepSeek의 Native Sparse Attention(NSA, 2025)은 압축(Compression), 선택(Selection), 슬라이딩 윈도우(Sliding Window)의 3경로 어텐션을 제안하여 KV 캐시를 효과적으로 압축한다.

그러나 NSA는 사전 학습(pre-training) 단계에서 모델 아키텍처에 내장되어야 하는 근본적 제약이 있다. Qwen2.5, Llama 3, Mistral 등 이미 학습 완료된 dense attention 모델에 NSA를 적용하려면 모델을 처음부터 재학습해야 하며, 이는 대부분의 기업에서 실행 불가능하다.

### 3.7 종래기술 5: 기존 KV Cache 최적화 (휴리스틱 기반)

SnapKV(Li et al., 2024), H2O(Zhang et al., 2023), Quest(Tang et al., 2024) 등은 KV 캐시에서 중요하지 않은 토큰을 제거하는 기법이다.

이 방식은 학습 없는 규칙 기반 방법으로 도메인 특화 최적화가 불가능하며, 특히 다면 온톨로지의 facet별 중요도를 반영할 수 없다. 현재 질의에서 중요한 facet의 관련 토큰이 일시적으로 낮은 attention weight를 가질 때 부당하게 제거되는 문제가 있다.

### 3.8 종래기술 6: DMC (Dynamic Memory Compression, Nawrot et al., 2024)

DMC는 KV 캐시 압축에 학습 기반 접근을 최초로 시도한 연구로서, 각 어텐션 헤드에 학습 가능한 sigmoid gate를 추가하여 연속 토큰의 KV를 동적으로 병합한다.

이 방식의 문제점은 다음과 같다.

**첫째, 어텐션 내부 코드 수정 필수.** Flash Attention, Ring Attention 등 최적화된 어텐션 커널과 호환되지 않는다.

**둘째, 대규모 continued pre-training 필요.** 수십억 토큰 규모의 학습이 필요하다.

**셋째, 도메인 구조 비인식.** DMC의 gate는 도메인 온톨로지의 facet별 중요도를 반영하지 못한다.

### 3.8a 종래기술 6a: TurboQuant (Google, ICLR 2026) — 랜덤 직교 회전 기반 KV 캐시 양자화

TurboQuant(Google Research, 2025/2026)은 KV 캐시의 K, V 벡터를 랜덤 직교 행렬로 회전시킨 후, 회전된 좌표가 Beta 분포에 수렴하는 성질을 이용하여 좌표별 Lloyd-Max 최적 스칼라 양자화를 적용하는 기법이다. 잔차에 1-bit QJL(Quantized Johnson-Lindenstrauss) 변환을 추가하여 내적 추정의 편향을 제거한다. 학습이나 미세조정 없이 KV 캐시를 3비트로 양자화하면서 정확도 손실이 없고, H100 GPU에서 attention 연산 8배 속도 향상을 달성하였다.

그러나 TurboQuant는 다음과 같은 한계를 가진다.

**첫째, 도메인 무관(data-oblivious) 균일 양자화.** 랜덤 직교 회전은 데이터의 의미론적 구조와 무관하게 적용되므로, 모든 차원이 동일한 비트 수로 양자화된다. 도메인 특화 환경에서 의미론적으로 중요한 차원(예: 도구 선택에 결정적인 facet 관련 차원)과 덜 중요한 차원(예: 현재 질의와 무관한 facet 차원)을 구분하여 차등 비트를 할당하는 것이 불가능하다.

**둘째, 질의 무관(query-oblivious) 정적 양자화.** TurboQuant의 양자화 비트 할당은 질의에 무관하게 고정된다. 그러나 실제 엔터프라이즈 환경에서는 동일 KV 캐시라도 질의에 따라 중요한 차원이 달라진다. "적금 전환율 분석" 질의에서 중요한 차원(마케팅 facet)과 "로그인 인증 오류" 질의에서 중요한 차원(보안 facet)은 다르며, 균일 양자화는 이 차이를 반영하지 못한다.

**셋째, 의미론적 직교 분해의 부재.** TurboQuant의 랜덤 회전은 통계적 독립성을 유도하나, 회전된 좌표에 의미론적 해석이 불가능하다. 반면, 도메인 온톨로지의 facet에 기반한 직교 분해는 각 부분공간에 "구조 관점", "행동 관점", "기능 관점" 등 해석 가능한 의미가 부여되어, 어떤 관점의 정보가 손실되는지를 투명하게 제어할 수 있다.

🔵 **넷째, 어텐션 헤드별 비등방성 적응의 부재.** 본 발명자의 실험에 의하면, KV 캐시의 비등방성(anisotropy) 정도는 레이어 및 어텐션 헤드마다 극적으로 상이하다. GPT-2 Medium(24층, 16헤드, d_head=64) 모델에서 측정한 유효 랭크(effective rank) r_eff는 2.60(Layer 3)부터 14.03(Layer 7, conversational)까지 범위하며, 비등방성이 강한 헤드(r_eff < 5)에서는 비균일 비트 할당이 KL divergence를 88%까지 감소시키지만, 비등방성이 약한 헤드(r_eff > 14)에서는 오히려 346% 악화된다(§7.4 실시예 4 참조). TurboQuant의 균일 양자화는 이러한 헤드별 차이를 고려하지 못하며, 비등방 헤드에서 낭비되는 비트를 등방 헤드에서 절약하는 적응적 전략이 불가능하다.

### 3.9 종래기술 7: 온톨로지 반자동 구성 기법

온톨로지 학습(Ontology Learning) 분야에서 텍스트로부터 온톨로지를 반자동 구성하는 연구(OntoLearn, Text2Onto 등)가 존재하나, 다음과 같은 한계가 있다.

**첫째, 단일 관점 온톨로지.** 기존 온톨로지 학습은 하나의 분류 체계를 구축하는 것을 목적으로 하며, 동일 엔티티에 대한 복수의 직교 관점을 동시에 발견하는 메커니즘이 없다.

**둘째, 구조화된 메타데이터 미활용.** 기존 연구는 주로 비구조화 텍스트(문서, 논문)로부터 개념과 관계를 추출하며, 페이지 경로·페이지 ID·도구 스키마·사용 로그 등 엔터프라이즈 특유의 반구조화(semi-structured) 메타데이터를 활용하는 방법이 부재하다.

**셋째, 직교성 보장 메커니즘 부재.** 발견된 복수의 분류 체계가 상호 직교(orthogonal)한지를 검증하고, 직교하지 않는 분류를 병합하거나 분리하는 자동 메커니즘이 없다.

### 3.10 종래기술 8: Multi-view Clustering

Multi-view clustering(Bickel & Scheffer, 2004; Blum & Mitchell, 1998; Strehl & Ghosh, 2002)은 동일 데이터에 대해 복수의 "뷰(view)"를 생성하고, 뷰 간 합의(consensus)를 통해 더 나은 클러스터링을 산출하는 기법이다. NMI(정규화 상호정보량)를 이용한 클러스터링 품질 평가 및 뷰 간 일치도 측정은 이 분야의 표준 기법이다(Vinh et al., 2010).

그러나 종래의 multi-view clustering은 다음과 같은 한계를 가진다.

**첫째, 목적의 차이.** 종래 multi-view clustering의 목적은 복수 뷰의 합의(consensus)를 통한 단일 최적 클러스터링 산출이다. 즉, 복수 뷰를 "융합"하여 하나의 분류 결과를 얻는 것이 목표이다. 반면, 본 발명이 요구하는 것은 복수 뷰의 "분리 유지" — 각 뷰(facet)를 독립적으로 보존하면서 이들의 직교성을 검증하고, 직교하지 않는 뷰를 병합하는 것이다. 이는 multi-view clustering의 목적과 정반대이다.

**둘째, 동음이의어 공동 발견의 부재.** 종래 multi-view clustering은 클러스터 구조만을 다루며, 클러스터링 결과로부터 "어떤 뷰에서 동음이의어인지"를 자동 식별하는 메커니즘이 없다. 본 발명이 요구하는 것은 facet 분리와 facet별 의미 분기 매트릭스의 "공동 발견(co-discovery)"이며, 이는 종래 multi-view clustering의 범위를 넘어선다.

**셋째, 비정규화 입력 미대응.** 종래 multi-view clustering은 각 뷰의 특징 행렬(feature matrix)이 사전에 구성되어 있음을 전제하나, §3.2에서 기술한 비정규화 데이터(구분자 혼재, ID-콘텐츠 괴리 등)로부터 뷰를 추출하는 전처리를 다루지 않는다.

### 3.11 종래기술 9: 다면 분류 (Faceted Classification)

다면 분류(Faceted Classification)는 1933년 Ranganathan의 Colon Classification 이후 도서관학에서 80년 이상 연구되어 온 분류 이론이다(Spiteri, 1998). 엔티티를 복수의 독립적 면(facet)으로 동시에 분류하는 개념 자체는 공지 기술이다.

그러나 종래의 다면 분류는 다음과 같은 한계를 가진다.

**첫째, 수동 설계.** Ranganathan의 PMEST(Personality, Matter, Energy, Space, Time) 등 facet 정의는 도메인 전문가가 수동으로 설계하며, 데이터로부터 자동 발견하는 메커니즘이 없다.

**둘째, 직교성의 비형식적 보장.** 종래 다면 분류에서 facet 간 독립성은 설계자의 직관에 의존하며, 정량적 직교성 검증(NMI 등) 메커니즘이 없다.

**셋째, LLM 학습과의 연결 부재.** 다면 분류 이론은 분류 체계의 설계에 관한 것이며, 발견된 facet을 LLM의 모델 가중치에 내재화하는 방법(facet 조건부 어댑터, facet별 손실 함수, facet별 투영 병목 등)과의 기술적 연결이 없다.

### 3.12 종래기술 10: Conditional Adapter 및 Multi-task LoRA

AdapterFusion(Pfeiffer et al., 2021)은 복수의 task-specific adapter를 학습한 후, 새로운 task에서 이들 adapter의 출력을 attention 기반으로 융합하는 기법이다. LoRAHub(Huang et al., 2023)는 LoRA 모듈을 gradient-free 방식으로 조합한다. MTLoRA(2024)는 multi-task 설정에서 task-specific LoRA를 라우팅한다.

이 방식들의 문제점은 다음과 같다.

**첫째, task 단위 분리.** 기존 conditional adapter는 "task"(예: 감성 분석, 요약, 번역) 단위로 adapter를 분리한다. 그러나 본 발명이 다루는 문제는 동일 task(도메인 질의 응답) 내에서 복수의 직교 의미론적 관점(facet)에 따라 adapter를 조건부 활성화하는 것으로, task 단위 분리와는 기술적 성격이 다르다.

**둘째, adapter 정의의 수동성.** 기존 방식에서 어떤 adapter를 몇 개 만들 것인가는 사전에 수동으로 결정되며, 데이터로부터 자동 결정되지 않는다.

**셋째, 다면 동시 라우팅 부재.** 기존 방식은 하나의 라우팅 결정(어떤 adapter/task를 선택할 것인가)을 수행하나, 복수의 직교 축에서 동시에 라우팅하는 메커니즘이 없다.

### 3.13 종래기술 11: LLM 기반 도구 선택 및 작업 계획 수립

ReAct(Yao et al., 2022)는 reasoning과 acting을 반복하여 LLM이 도구를 순차적으로 호출하는 기법이다. Toolformer(Schick et al., 2023)는 도구 호출을 자기지도 학습으로 LLM에 내재화한다. TaskMatrix.AI(Liang et al., 2023)는 시각 모델과 API를 조합하여 복합 작업을 수행한다. HuggingGPT(Shen et al., 2023)는 LLM이 task를 분해하고 적절한 모델을 선택하여 실행하는 프레임워크이다.

이 방식들의 문제점은 다음과 같다.

**첫째, 프롬프트 기반 도구 열거의 한계.** ReAct, HuggingGPT 등은 사용 가능한 도구 목록을 프롬프트에 나열하고 LLM의 추론 능력에 의존하여 도구를 선택한다. 도구가 수십 개 수준에서는 효과적이나, 수백~수천 개로 증가하면 프롬프트 길이 한계에 도달하여 적용 불가능하다.

**둘째, 도구 검색 공간의 비구조화.** 종래 기법은 도구 간의 다면적 관계(기능 관점에서의 유사성, 데이터 관점에서의 호환성, 사용자 관점에서의 선호도 등)를 구조화하지 않는다. 모든 도구가 동등한 후보로 취급되므로, 이름과 기능이 유사한 복수 도구(예: "전환율 분석" 3개 변종) 간의 선택이 LLM의 추론에만 의존한다.

**셋째, 컨텍스트 의존적 경로 분기의 미처리.** 동일 질의에 대해 대화 컨텍스트, 팀별 선호, 데이터 상태에 따라 최적 도구 체인이 달라지는 문제를 체계적으로 처리하지 못한다. ReAct의 reasoning-acting 루프는 매 단계에서 "다음에 무엇을 할지"를 결정하나, "가능한 경로 전체를 구조화하여 최적 경로를 선택"하는 것이 아니라 탐욕적(greedy)으로 다음 단계를 선택한다.

본 발명과의 차별점: 본 발명은 ReAct/Toolformer 등의 도구 호출 메커니즘 자체를 대체하는 것이 아니라, **도구 검색 공간을 facet 기반으로 사전 구조화하여 축소**하는 것이다. 비유하면, ReAct이 "길을 찾는 네비게이션"이라면 본 발명은 "도로망 자체를 구조화하는 지도 제작"에 해당한다. 본 발명에 의하여 수천 개 도구가 facet 벡터 기반 도구 패밀리로 축약되면, 축약된 검색 공간에서 ReAct/Toolformer 등의 기존 기법이 더 효과적으로 동작할 수 있다.

### 3.14 종래기술 12: Hyperbolic Entailment Cones 및 계층적 임베딩

Ganea et al.(2018)의 Hyperbolic Entailment Cones는 온톨로지의 is-a 계층 관계를 쌍곡 공간(hyperbolic space)에서 원추(cone)로 표현하여, 포함 관계를 기하학적으로 보존하는 기법이다. Nickel & Kiela(2017)의 Poincaré Embeddings도 유사하게 계층 구조를 쌍곡 공간에 임베딩한다.

본 발명의 L_hier_multi(다면 계층 보존 손실)는 코사인 유사도 기반 마진 손실을 사용하며, 쌍곡 공간이 아닌 유클리드 부분공간에서 동작한다. 차별점은 (1) 계층 보존이 단일 공간이 아닌 facet별 직교 부분공간에서 독립 적용되고, (2) 계층 보존과 분기 해소가 동일 부분공간에서 동시 학습되며, (3) 쌍곡 공간 연산이 불필요하여 기존 LLM 프레임워크(vLLM, PyTorch)와의 호환성이 유지된다는 점이다.

> **참고**: 본 명세서에서 언급하는 QLoRA, DoRA, RAFT, NMI 기반 클러스터링 평가, 다면 분류, AdapterFusion, LoRAHub, ReAct, Toolformer, TaskMatrix.AI, HuggingGPT, Hyperbolic Entailment Cones는 각각 독립적으로 공지된 기반 기술이다. 본 발명은 이들 기반 기술 자체를 청구하지 않으며, "비정규화 데이터로부터 facet과 컨텍스트 의존적 의미 분기를 공동 발견하고, facet 기반으로 도구 검색 공간을 구조화하여 LLM 가중치에 내재화"하는 통합적 기술 과제에 대한 해결 수단을 발명의 대상으로 한다.

### 3.15 종래기술의 개별 적용이 실패하는 기술적 곤란성

상기 종래기술 각각을 개별 적용한 경우, 본 발명이 해결하고자 하는 과제가 해결되지 않는 기술적 곤란성은 다음과 같다.

**시나리오 A: Multi-view clustering(§3.10)만 적용한 경우.** 복수 뷰로부터 consensus clustering을 산출하면 단일 분류가 얻어지나, 이는 이해관계자별 독립 관점을 소실시킨다. 예를 들어, 개발자의 메뉴 트리 분류와 마케터의 캠페인 분류를 consensus로 융합하면, "적금 상품 상세"가 "금융상품" 클러스터에 속하게 되나, 마케터가 필요한 "MZ타겟 캠페인" 분류와 분석가가 필요한 "상품탐색 퍼널" 분류가 소실된다. 또한, consensus 결과로부터 "어떤 관점에서 동음이의어인지"를 역추적할 수 없다.

**시나리오 B: 다면 분류(§3.11)를 수동 설계 후 LoRA 적용한 경우.** 도메인 전문가가 facet을 수동 설계하면, (1) 설계에 수개월이 소요되며, (2) 설계자의 편향이 반영되고, (3) 직교성이 보장되지 않으며, (4) 새 도메인 이전 시 전면 재설계가 필요하다. 또한, 수동 설계된 facet이 실제 데이터의 분포와 괴리될 경우 LLM 학습 효과가 저하되나, 이를 사후 검증할 정량적 메커니즘이 없다.

**시나리오 C: Conditional Adapter(§3.12)만 적용한 경우.** task 단위로 분리된 adapter는 "이 입력은 마케팅 task"라는 단일 축 라우팅만 수행하며, "이 입력은 마케터 관점에서는 캠페인 분석이고, 기능 관점에서는 측정이며, 데이터 관점에서는 수신 상품"이라는 다면적 인식이 불가능하다. 이는 동음이의어 해소에서 결정적 한계가 된다 — "전환"이 기능 관점에서는 동음이의어(조회 vs 실행)이지만 데이터 관점에서는 동음이의어가 아닌 경우, 단일 축 라우팅으로는 이를 구분할 수 없다.

**시나리오 D: 시나리오 A+B+C를 순차 적용한 경우.** Multi-view clustering으로 뷰를 발견하고, 수동으로 facet을 정의하고, Conditional Adapter로 학습하는 순차 파이프라인을 구성하더라도, (1) multi-view clustering의 consensus 지향성과 facet 분리 유지의 모순이 해결되지 않으며, (2) facet 발견과 동음이의어 발견이 독립 프로세스이므로 "어떤 facet에서 동음이의어인지"의 정보가 누락되고, (3) 발견된 facet이 LLM의 투영 부분공간, 손실 함수, 토큰 가중치에 일관되게 반영되는 메커니즘이 부재하다.

**시나리오 E: 도구/계획 경로 선택에서의 조합 폭발.** 상기 시나리오 A~D는 주로 용어 수준의 의미 해소(동음이의어)를 다루었으나, 실제 엔터프라이즈 환경의 핵심 문제는 **도구 선택 및 작업 계획 수립에서의 컨텍스트 의존적 경로 선택**이다. 동일 질의 "적금 상품의 전환율을 분석해줘"에 대해, (1) 상품명→페이지ID→경로분석의 3단계 체인, (2) 상품→페이지 통합 도구→경로분석의 2단계 체인, (3) 상품경로분석 복합 도구의 1단계, (4) 이전 대화에서 페이지ID가 확보된 경우의 1단계 등 복수의 유효한 경로가 존재한다. 최적 경로는 대화 컨텍스트, 사용자 의도, 팀별 선호, 도구 가용성에 따라 달라진다. 종래의 multi-view clustering, 다면 분류, conditional adapter 어디에도 "복수 도구 체인 경로를 컨텍스트에 따라 선택"하는 메커니즘이 없다. 이 문제는 용어 다의성(동음이의어)의 상위 일반화이며, 각 facet이 도구 선택의 한 축(기능 관점, 데이터 관점, 사용자 관점 등)을 담당하여 조합 공간을 구조적으로 축소할 때만 해결 가능하다.

본 발명은 상기 기술적 곤란성을 해결하기 위하여, facet 발견·컨텍스트 의존적 분기 식별(용어 다의성, 도구 경로 분기, 계획 경로 분기를 포함)·LLM 내재화를 하나의 통합 Facet-Centric 파이프라인으로 연결하되, AFOD의 출력이 다운스트림 구성요소(facet별 어댑터, 손실, 투영, 도구 호환 그래프, 계획 템플릿)에 구조적으로 반영되는 "facet-분기-내재화 공동 최적화(co-optimization)"를 제공한다.

## 4. 발명이 해결하고자 하는 과제

### 4.1 핵심 과제: 컨텍스트 의존적 도구 선택 및 작업 계획의 조합 폭발

엔터프라이즈 AI 에이전트가 사용자 질의에 응답하려면, (1) 질의의 의미론적 해석, (2) 적절한 도구 선택, (3) 복수 도구를 조합한 작업 계획(plan) 수립의 세 단계를 수행해야 한다. 도구가 수십~수천 개이고, 각 도구가 다른 도구의 출력을 입력으로 받는 복합 도구 체인이 가능한 경우, 가능한 작업 경로는 기하급수적으로 폭증한다.

```
조합 폭발 예시:

  질의: "적금 상품의 전환율이 높은 채널을 분석해줘"

  경로 A (3단계 복합):
    1. product_lookup("적금") → product_ids
    2. page_mapper(product_ids) → page_ids
    3. channel_path_analysis(page_ids)
    → 중간 결과 확인 가능 (투명성 높음)

  경로 B (2단계):
    1. product_page_search("적금") → page_ids (통합 도구)
    2. channel_path_analysis(page_ids)

  경로 C (1단계 복합):
    1. product_channel_analysis("적금") → 결과
    → 가장 빠르지만 파라미터 제어 제한

  경로 D (컨텍스트 의존):
    이전 대화에서 page_id 확보 → 상품 조회 생략
    1. channel_path_analysis(known_page_ids)

  최적 경로 결정 요인:
    - 대화 컨텍스트: 이미 확보된 정보
    - 사용자 의도: 중간 결과 필요 여부
    - 팀별 선호: 단계별 확인 vs 원스텝
    - 도구 가용성: 복합 도구 존재 여부
    - 데이터 상태: 상품명 검색 가능 vs page_id만 가능

  도구 45개, 평균 3단계 체인: 가능 경로 ≈ 85,000+
  프롬프트에 나열: 불가능
```

본 발명이 해결하고자 하는 것은 **"동일 질의라도 컨텍스트에 따라 최적 도구 및 계획 경로가 달라지는 문제"**이며, 이를 다면 직교 온톨로지로 도구·계획·컨텍스트를 구조화하고 LLM 가중치에 내재화하여 해결한다. 동음이의어 해소는 이 과제의 한 특수 사례(용어 수준의 의미 분기)이며, 도구 경로 분기 및 계획 경로 분기가 보다 일반적이고 핵심적인 과제이다.

### 4.2 과제 목록

**과제 1 (다면 직교 온톨로지 반자동 구성)**: 비정규화 데이터로부터, 도구·계획·컨텍스트를 구조화하는 복수의 직교 facet을 발견하고, 각 facet별로 **컨텍스트 의존적 의미 분기**(용어 다의성, 도구 경로 분기, 계획 경로 분기를 포함)를 자동 식별하는 방법을 제공한다.

**과제 2 (온톨로지 내재화 — 도구 선택 및 계획 수립)**: 과제 1의 다면 온톨로지 — 특히 도구 간 호환 관계, 복합 도구 체인, 컨텍스트 의존 경로 분기 —를 LLM 가중치에 내재화하여, 프롬프트에 도구 스키마를 나열하지 않고도 컨텍스트에 적합한 도구 선택 및 계획 수립이 가능한 방법을 제공한다.

**과제 3 (컨텍스트 의존적 의미 해소)**: 동일 용어의 다의성, 동일 기능의 복수 도구, 동일 목적의 복수 계획 경로를 포함하는 **컨텍스트 의존적 분기**를, "어떤 facet에서 분기가 발생하는지"에 따라 해당 facet의 부분공간에서 선택적으로 해소하는 방법을 제공한다.

**과제 4 (도구·계획 경로의 facet 기반 축약)**: 수천 개의 중복 도구와 기하급수적 계획 경로를, facet 벡터 기반 도구 패밀리 + 계획 템플릿으로 축약하여 프롬프트 85% 절감 + 팀별 경로 추천을 모델 가중치 수준에서 구현하는 방법을 제공한다.

**과제 5 (포스트 트레이닝 KV 캐시 압축)**: facet별 중요도에 따른 적응적 KV 캐시 압축을 제공한다.

**과제 6 (3단 분리 학습)**: facet 구조/내용/개인화를 분리 학습한다.

## 5. 과제의 해결 수단

### 5.1 발명의 전체 구성: Facet-Centric Architecture

#### 5.1.1 기존 3축 직교 구조의 폐기와 Facet 중심 아키텍처

종래의 DC-QDoRA-RAFT는 3개의 "직교 축"을 설정하였다.

```
종래 DC-QDoRA-RAFT의 3축 (폐기):
  축 1 (구조적 분리): OC-LoRA — "어디서 학습하는가" → 도메인별 어댑터
  축 2 (학습 목표):   Structured Loss — "무엇을 학습하는가" → 보조 손실
  축 3 (학습 집중도): Token Weighting — "얼마나 집중하는가" → 토큰 가중치

문제:
  - "3축"은 인공적 분류이며, 실제로 3축 간 독립성은 수학적으로 보장되지 않음
  - 어댑터 구조(축 1)를 변경하면 손실 함수(축 2)와 토큰 가중치(축 3)도 변경해야 함
  - 진정한 직교 축은 "3개 기법"이 아니라 "F개 facet" 자체임
```

본 발명은 이 3축 구조를 폐기하고, **facet 자체를 직교 축으로 삼는 Facet-Centric Architecture**를 채택한다. F개 facet이 F개 직교 축이며, 각 facet 축을 따라 어댑터·손실·가중치·투영·압축·인코딩·라우팅의 7가지 기능이 일체로 구성된다.

```
본 발명의 Facet-Centric Architecture:

  각 facet f (f = 1, ..., F)가 하나의 직교 축을 구성하며,
  축 f에 대해 다음 7가지 기능이 일체로 정의된다:

  ┌──────────────────────────────────────────────────────────────┐
  │  Facet f (하나의 직교 축)                                    │
  │                                                              │
  │  (1) Adapter_f:   B_f, A_f (저랭크 어댑터)                  │
  │  (2) Loss_f:      L_hier_f + L_branch_f (facet 내 손실)     │
  │      L_branch_f: 용어 다의성 + 도구 경로 분기               │
  │                  + 계획 경로 분기를 통합한 분기 해소 손실    │
  │  (3) Weight_f:    w_f(token) (토큰별 facet 관련 가중치)      │
  │  (4) Projection_f: P_down_f, P_up_f (직교 부분공간)         │
  │  (5) Compress_f:  importance_f(block) (KV 압축 중요도)       │
  │  (6) Encode_f:    E_f[class] (온톨로지 임베딩)               │
  │  (7) Route_f:     도구 호환 그래프 + 계획 템플릿             │
  │      → facet f 관점에서의 도구 체인 및 계획 경로 정보        │
  │                                                              │
  │  + Gate_f: g_f(x) (입력 의존적 활성화 강도)                  │
  └──────────────────────────────────────────────────────────────┘

  F개 facet이 F개 직교 축 → facet 간 직교성은 NMI + L_facet_orth로 보장

  Facet 간 관계:
    직교 (NMI < 0.3): 완전 독립, 간섭 없음
    소프트 직교 (NMI ∈ [0.3, 0.5]): L_facet_orth로 학습 시 분리 강제
    병합 (NMI > 0.5): AFOD Stage 3에서 사전 병합

  핵심 전환:
    종래: "3개 기법 축" × "N개 도메인" = 3×N 격자
    본 발명: "F개 facet 축" × "6개 기능 일체" = F개 독립 모듈
    → facet이 추가되면 해당 facet의 모듈만 추가 (다른 facet 불변)
    → facet이 제거되면 해당 facet의 모듈만 제거 (다른 facet 불변)
```

#### 5.1.2 Facet-Centric 구성요소

본 발명은 다음 구성요소로 이루어지며, 모든 구성요소가 **facet을 1급 시민(first-class citizen)**으로 취급한다.

**기반 구성요소:**
- **AFOD** (Automatic Facet-Orthogonal Ontology Discovery): 비정규화 현장 데이터로부터 F개 직교 facet을 발견하고, 각 facet의 7가지 기능(어댑터/손실/가중치/투영/압축/인코딩/라우팅)을 초기화하는 기법 (과제 1 해결)

**Per-Facet 기능 (각 facet f에 대해 인스턴스화):**
- **Adapter_f**: facet f 전용 저랭크 어댑터 (B_f, A_f), 입력의 facet f 관련성에 따라 희소 활성화 (과제 2)
- **Loss_f**: facet f의 부분공간에서의 계층 보존 + facet f에서만 의미 분기가 발생하는 쌍의 선택적 분리 (과제 3)
- **Weight_f**: facet f 관련 토큰에 대한 동적 가중치 (과제 3 보강)
- **Projection_f**: facet f의 직교 부분공간 투영 행렬 P_down_f, P_up_f + 입력 의존적 게이트 g_f (과제 2·3 보강)
- **Compress_f**: KV 캐시 블록의 facet f 관련 중요도 스코어 (과제 5)
- **Encode_f**: facet f의 온톨로지 클래스 임베딩 E_f, Graph Attention에서의 관계 인코딩 (과제 2 보강)
- **Route_f**: facet f 관점에서의 도구 호환 그래프 및 도구 체인 경로 템플릿, 컨텍스트에 따른 최적 도구 체인 선택에 활용 (과제 4 보강)

**Cross-Facet 기능 (facet 간 관계):**
- **L_facet_orth**: facet 간 투영 행렬 직교성 보존 손실
- **L_tool_family**: 도구 패밀리(복수 facet에 걸친 도구 그룹) 정렬 손실
- **Facet Hierarchy**: F>10 시 super-facet 계층 구조 및 희소 활성화
- **3-Level Decoupled Training**: facet 구조/내용/개인화 분리 학습 (과제 6)

```
Facet-Centric vs 종래 3축의 대비:

  종래 3축:
    OC-LoRA(축1) + Structured Loss(축2) + Token Weighting(축3)
    → 축을 추가하려면 전체 아키텍처 재설계
    → 축 간 "직교"는 설계 의도일 뿐 보장 없음

  Facet-Centric:
    Facet_1 = {Adapter_1, Loss_1, Weight_1, Projection_1, Compress_1, Encode_1}
    Facet_2 = {Adapter_2, Loss_2, Weight_2, Projection_2, Compress_2, Encode_2}
    ...
    Facet_F = {Adapter_F, Loss_F, Weight_F, Projection_F, Compress_F, Encode_F}
    → facet 추가 = 모듈 하나 추가 (O(1) 아키텍처 변경)
    → facet 간 직교 = NMI + L_facet_orth로 정량 보장
    → F=4에서 F=500까지 동일 아키텍처

통합 학습 알고리즘 (Facet-Centric):

  For each batch:
    // 1. Facet 활성화 (희소)
    active_facets = TopK(Φ_multi(x), K)

    // 2. Per-Facet 순전파
    For each f ∈ active_facets:
      h_f = Adapter_f(x, g_f(x))              // facet별 어댑터
      z_f = Projection_f(h_f)                  // facet별 투영
      w_f = Weight_f(tokens, g_f(x))           // facet별 토큰 가중치

    // 3. Cross-Facet 집계
    h_agg = Σ_f g_f · P_up_f · z_f            // 게이팅 집계
    h_final = h_dora + α · Constrain(h_agg)    // 제약 복원

    // 4. Per-Facet 손실
    L = L_wCE(w_f) + Σ_{f∈active} (λ₁·L_hier_f + λ₂·L_dis_f)
      + L_facet_orth + L_tool_family

    // 5. KV 압축 (추론 시)
    For each block j:
      importance_j = max_{f∈active}(Compress_f(block_j) × g_f)
```

#### 5.1.3 Facet 모듈의 생명주기

Facet-Centric Architecture에서 각 facet 모듈은 독립적인 생명주기를 가진다.

```
Facet 모듈 생명주기:

  (1) 탄생: AFOD가 새 facet을 발견
    → 7가지 기능 초기화 (어댑터, 손실, 가중치, 투영, 압축, 인코딩, 라우팅)
    → 기존 facet에 영향 없음

  (2) 학습: Per-Facet 손실로 독립 학습
    → 다른 facet과 L_facet_orth로만 상호작용

  (3) 갱신: facet 내 클래스 변경 (새 도구 추가 등)
    → 해당 facet의 Encode_f와 Loss_f만 재학습
    → 다른 facet 동결

  (4) 병합: 두 facet의 NMI가 증가하여 0.5 초과 시
    → 두 facet의 어댑터/투영을 merge
    → F → F-1

  (5) 분할: 한 facet 내 클래스가 과다하게 증가 시
    → AFOD 재실행으로 해당 facet을 2개로 분할
    → F → F+1

  (6) 은퇴: facet의 usage_frequency가 임계값 미만으로 하락 시
    → 해당 facet 모듈 비활성화 (삭제 아님, 재활성화 가능)
    → 추론 시 K_max에서 제외

이 생명주기에 의하여 시스템이 도메인 변화에 점진적으로 적응하며,
전체 재학습 없이 facet 단위의 증감이 가능하다.
```

이하에서 각 구성요소를 상세히 설명한다.

### 5.2 AFOD: Automatic Facet-Orthogonal Ontology Discovery

#### 5.2.1 개요 및 동기

AFOD는 본 발명의 기반 구성요소로서, 다른 모든 구성요소(FC-LoRA, MF-OSL, MF-OPB, LKCA 등)가 참조하는 다면 직교 온톨로지를 비정규화 현장 데이터로부터 반자동 구성한다.

```
AFOD의 입출력:

입력:
  (1) 페이지 경로 데이터: (페이지명, 페이지 경로, 페이지ID) 튜플의 집합
      예: ("금융회원 홈", "메인(나)>금융회원 홈(일반홈)", "NWMMH00009_002M")
  (2) 도구 카탈로그: (도구명, 파라미터 스키마, 설명, 출력 스키마) 집합
  (3) 사용자 행동 로그: 세션별 페이지 방문 시퀀스
  (4) 도구 사용 이력: 팀별·개인별 도구 호출 로그

출력:
  (1) F개의 직교 facet 정의: {F_1, F_2, ..., F_F}
      각 facet은 이름, 클래스 집합, 클래스 계층 구조를 포함
  (2) 엔티티별 facet 벡터: 각 엔티티의 facet별 클래스 할당
  (3) facet별 의미 분기 매트릭스: 어떤 facet에서 동음이의어인지의 정보
  (4) 도구 패밀리 분류: facet 벡터 기반 도구 그룹핑
  (5) facet별 직교 클래스 임베딩: MF-OPB 초기화에 사용
```

#### 5.2.2 Stage 1: 반구조화 메타데이터 정규화 (Semi-Structured Metadata Normalization)

비정규화된 반구조화 메타데이터를 정규화된 계층 트리로 변환한다. 본 단계의 입력은 도메인에 따라 상이하며, 페이지 경로(금융 CDP), 진단 코드 계층(의료 EMR), 설비 분류 코드(제조), 배송 경로 트리(물류), 행정 분류 코드(공공) 등 해당 도메인의 계층적 메타데이터가 입력된다. 이하에서는 금융 CDP의 페이지 경로를 예시로 설명하나, 동일 알고리즘이 모든 도메인의 반구조화 계층 메타데이터에 적용된다.

```
Stage 1 처리 절차:

── Step 1a: 다중 구분자 자동 감지 ──

입력 경로에서 구분자 패턴을 자동 감지한다.
감지 알고리즘은 다음 우선순위를 따른다.

  우선순위 1: " > " (공백+꺽쇠+공백) — 가장 명시적 구분자
  우선순위 2: ">" (공백 없는 꺽쇠)
  우선순위 3: "-" (하이픈) — 단, 복합어 내부 하이픈과 구분 필요
  우선순위 4: 구분자 미감지 — LLM 기반 분절로 폴백

각 경로에 대해 감지된 구분자로 1차 분할 수행.

예:
  "메인(나) > 로그인전 > 로그인 이력 있는 고객"
  → 구분자: " > "
  → 분할: ["메인(나)", "로그인전", "로그인 이력 있는 고객"]

  "즉시/예약이체-입금계좌 입력"
  → 구분자: "-"
  → 분할: ["즉시/예약이체", "입금계좌 입력"]

  "공통/기타로그인우리won인증서 로그인PIN"
  → 구분자: 미감지
  → LLM 기반 분절 (Step 1a-fallback)

── Step 1a-fallback: LLM 기반 경로 분절 ──

구분자가 감지되지 않는 경로에 대해, 경량 LLM(또는 학습된 분류기)을
이용하여 의미 단위 분절을 수행한다.

입력: "공통/기타로그인우리won인증서 로그인PIN"
프롬프트: "다음 페이지 경로를 계층적 의미 단위로 분절하시오: {input}"
출력: ["공통/기타", "로그인", "우리won인증서", "로그인", "PIN"]

분절 결과의 품질 검증:
  - 분절된 각 세그먼트가 다른 경로의 세그먼트와 매칭되는지 확인
  - "로그인"이 다른 경로에서도 독립 세그먼트로 출현하면 분절 정확도 높음
  - 미매칭 세그먼트가 50% 초과 시 수작업 검토 대상으로 플래그

── Step 1b: 괄호 메타데이터 추출 ──

경로 내 괄호 표기를 메타데이터로 분리한다.

패턴:
  "(나)", "(TAB)", "(일반홈)", "(쉬운홈)", "(게이트)" 등

처리:
  "메인(나)>금융회원 홈(일반홈)"
  → path: ["메인", "금융회원 홈"]
  → meta: {context: "나", variant: "일반홈"}

  "전체계좌조회-(TAB)계좌"

#### 5.2.3 Stage 2: 다관점 클러스터링 (Multi-Perspective Clustering)

동일 엔티티 집합에 대해, 서로 다른 정보원(information source)을 기반으로 복수의 독립적 분류를 자동 생성한다.

```
Stage 2 처리 절차:

── Clustering A: 경로 구조 기반 (개발자 관점 후보) ──

정규화된 경로의 상위 N 레벨(N=1,2,3)로 클러스터링.

N=1: {"메인", "전체계좌조회", "즉시/예약이체", "다건이체", "자동이체",
       "인증/보안", "공통/기타", "알림함", "이벤트", "WON PLAY",
       "통합검색", "통합상담", ...}

N=2: 상위 레벨 + 하위 레벨 조합
  "메인" → {"금융회원 홈", "비로그인 홈", "쉬운 홈", "혜택", "상품", "자산"}
  "전체계좌조회" → {"거래내역조회", "계좌관리", "(TAB)계좌"}
  "공통/기타" → {"로그인", "전체메뉴", "에러페이지", "비대면실명확인"}

결과: C_A = 경로 구조 기반 클래스 집합

── Clustering B: 행동 시퀀스 기반 (분석가 관점 후보) ──

사용자 세션에서 페이지 전이 확률 행렬 P(i→j)를 구성하고,
동일 세션 내 빈출 동시 출현(co-occurrence) 기반으로 클러스터링.

전이 확률 행렬:
  P(로그인 → 금융회원 홈) = 0.72  → 높은 전이
  P(금융회원 홈 → 전체계좌조회) = 0.45  → 중간 전이
  P(전체계좌조회 → 거래내역조회) = 0.68  → 높은 전이
  P(이체정보입력 → 이체정보확인) = 0.91  → 매우 높은 전이 (순차 퍼널)

Markov Chain 기반 커뮤니티 감지:
  커뮤니티 1 (인증 퍼널):
    {로그인방법 선택, 우리won인증서, PIN, 생체, 패턴, 금융인증서, 공동인증서}
  커뮤니티 2 (조회 퍼널):
    {금융회원 홈, 전체계좌조회, 거래내역조회, 계좌관리, 운용현황}
  커뮤니티 3 (이체 퍼널):
    {입금계좌 입력, 이체정보입력, 이체정보확인, 이체완료, 보안매체 인증}
  커뮤니티 4 (탐색 퍼널):
    {상품몰, 입출금/예금/적금, 안내(상품상세), 통합검색}
  커뮤니티 5 (엔터테인먼트/이벤트):
    {WON PLAY, 이벤트, 버즈빌 브릿지}
  커뮤니티 6 (관리/설정):
    {알림함, 푸시 알림 수신 설정, 홈 계좌 설정, 인증/보안}

결과: C_B = 행동 시퀀스 기반 클래스 집합

── Clustering C: 페이지ID 접두사 기반 (시스템 관점 후보) ──

Step 1c에서 추출한 페이지 ID 접두사를 기반으로 분류.

결과: C_C = {MainHome(NWMMH), Inquiry(NWINQ), Transfer(NWTSW),
             Navigation(NWNAV), Services(NWFAV), Security(NWCEC),
             AccountMgmt(NWDID), Notification(NWFNS), Pension(NWIRP),
             Search(NWGDC), Payment(NWSTL), GroupBanking(NWUBS)}

── Clustering D: 기능 키워드 기반 (기능 관점 후보) ──

페이지명 및 경로 내 동사/기능 키워드를 추출하여 분류.

키워드 추출:
  조회 관련: {"조회", "내역", "현황", "확인"}
  실행 관련: {"이체", "입력", "완료", "가입", "해지"}
  인증 관련: {"로그인", "인증", "본인확인", "비밀번호", "PIN", "생체"}
  설정 관련: {"설정", "관리", "변경"}
  탐색 관련: {"홈", "메인", "검색", "메뉴", "상품몰"}
  이벤트 관련: {"이벤트", "PLAY", "혜택"}

결과: C_D = {Query, Execute, Auth, Configure, Explore, Event}

── Clustering E: 도구 연관 기반 (분석 도구 관점 후보) ──

각 페이지와 연관된 분석 도구의 사용 빈도로 분류.

예:
  "거래내역조회" → 연관 도구: {거래내역_조회, 입출금_분석, 잔액추세_분석}
  "이체완료" → 연관 도구: {이체성공률_분석, 채널전환율_분석}
  "상품상세" → 연관 도구: {상품가입률_분석, 상품비교_분석}

결과: C_E = 도구 연관 기반 클래스 집합

── Clustering F: 도구 파라미터 유사도 기반 (도구 중복 해소) ──

도구 카탈로그에서 도구 간 유사도를 계산하여 "도구 패밀리"를 구성.

유사도 = α · name_sim + β · param_sim + γ · output_sim
  name_sim: 도구명의 편집 거리(edit distance) 기반 유사도
  param_sim: 파라미터 스키마의 Jaccard 유사도
  output_sim: 출력 스키마의 Jaccard 유사도
  α=0.3, β=0.4, γ=0.3

유사도 > 0.7인 도구 쌍을 connected component로 묶어 패밀리 구성.

예:
  패밀리 1: {"전환율 분석_마케팅", "전환율 분석_분석", "전환율 분석_경영진"}
  패밀리 2: {"채널별 유입 분석", "유입 채널 분석", "채널 퍼포먼스"}
  패밀리 3: {"코호트 분석", "코호트 리텐션"}

각 패밀리 내 도구의 차별점(differentiator)을 자동 추출:
  패밀리 1 내 differentiator:
    "마케팅": 파라미터에 "채널", "캠페인" 포함
    "분석": 파라미터에 "퍼널단계", "세그먼트" 포함
    "경영진": 파라미터에 "사업부" 포함, 출력이 요약 형식

결과: C_F = 도구 패밀리 집합 + 패밀리 내 differentiator
```

**Clustering G: 도구 체인 경로 기반 (계획 관점 후보)**

도구 간 입출력 호환 관계를 기반으로 유효한 도구 체인을 열거하고, 체인 패턴별로 클러스터링한다.

```
── Clustering G: 도구 체인 경로 열거 및 클러스터링 ──

Step G-1: 도구 호환 그래프 구성
  각 도구 쌍 (t_i, t_j)에 대해, t_i의 출력 스키마와 t_j의 입력 스키마를
  비교하여 호환 여부를 판정.
  호환 조건: t_i.output_schema ∩ t_j.input_schema ≠ ∅
  → 방향 그래프 G_tool = (V_tools, E_compatible) 구성

Step G-2: 유효 체인 열거
  사용자 질의 유형별로, G_tool에서 깊이 D 이하(D=4 기본)의 경로를 열거.
  각 경로 = 도구 체인 = (t_1 → t_2 → ... → t_k), k ≤ D

  예: 질의 유형 "상품별 전환율 분석"
    경로 A: product_lookup → page_mapper → channel_path_analysis (3단계)
    경로 B: product_page_search → channel_path_analysis (2단계)
    경로 C: product_channel_analysis (1단계)

Step G-3: 체인 패턴 클러스터링
  유사한 체인 구조를 가진 경로들을 그룹핑:
  - 동일 목적(입력 유형 + 출력 유형)을 가진 체인을 같은 클러스터에 배치
  - 클러스터 내 체인들은 "동일 목적의 대안 경로"

  결과: C_G = {체인 패턴 그룹}
    그룹 1: 상품→페이지→경로 분석 (3단계 변종들)
    그룹 2: 상품→경로 분석 (2단계 변종들)
    그룹 3: 상품경로 분석 (1단계 복합 도구들)

  → 이 클러스터링이 Stage 3에서 다른 클러스터링과 NMI 비교되어
    독립적 facet인지 판정됨
```

#### 5.2.4 Stage 3: Facet 직교성 검증 및 선정

Stage 2에서 생성된 7개 클러스터링(C_A ~ C_G) 중, 상호 직교하는 facet 조합을 자동 선정한다.

```
Stage 3 처리 절차:

── Step 3a: 클러스터링 결과의 벡터 인코딩 ──

각 엔티티 e에 대해, 클러스터링 c에서의 클래스를 인코딩:
  V_c(e) = one-hot(class_c(e))  ∈ R^{|C_c|}

── Step 3b: 클러스터링 쌍별 정규화 상호정보량(NMI) 계산 ──

모든 클러스터링 쌍 (c_i, c_j)에 대해:
  NMI(c_i, c_j) = MI(c_i, c_j) / sqrt(H(c_i) · H(c_j))

여기서:
  MI: 상호정보량 (Mutual Information)
  H: 엔트로피

NMI 해석:
  NMI = 0: 완전 독립 (완전 직교)
  NMI < 0.3: 직교로 판정
  NMI ∈ [0.3, 0.5]: 약한 상관 (소프트 직교 정규화 대상)
  NMI > 0.5: 강한 상관 (병합 대상)

CDP 은행 도메인 NMI 행렬 (설계 분석 기반 추정, 실측 보충 예정):
             C_A(경로) C_B(행동) C_C(ID) C_D(기능) C_E(도구) C_F(패밀리) C_G(체인)
  C_A(경로)     -      0.15     0.62    0.18     0.22     0.20      0.25
  C_B(행동)    0.15      -      0.11    0.28     0.35     0.31      0.33
  C_C(ID)     0.62    0.11       -      0.14     0.19     0.16      0.21
  C_D(기능)    0.18    0.28     0.14      -      0.42     0.38      0.40
  C_E(도구)    0.22    0.35     0.19    0.42       -      0.55      0.48
  C_F(패밀리)  0.20    0.31     0.16    0.38     0.55       -       0.52
  C_G(체인)    0.25    0.33     0.21    0.40     0.48     0.52        -

  C_G(도구 체인) 특성:
    C_E, C_F와 높은 상관 (NMI 0.48, 0.52) → C_E+C_F+C_G를 병합하여
    하나의 Tool Ecosystem facet으로 통합

── Step 3c: 최대 직교 facet 집합 선정 ──

NMI < 0.3인 쌍들의 최대 독립 집합(Maximum Independent Set)을 탐색.

알고리즘:
  1. NMI > 0.5인 쌍을 병합: C_E와 C_F를 병합 → C_EF(도구+패밀리)
  2. NMI > 0.5인 쌍을 병합: C_A와 C_C를 병합 → C_AC(경로+ID)
     (NMI=0.62이므로 경로 구조와 ID 접두사는 강한 상관)
  3. 병합 후 NMI 재계산
  4. NMI < 0.3인 조합 탐색

최종 선정 facet (CDP 은행 도메인):

  F1: Structure Lens (C_AC 병합)
    → 개발자 관점의 메뉴 트리 + 시스템 ID 접두사 통합
    → 클래스: {MainHome, Inquiry, Transfer, Navigation, Security,
               AccountMgmt, Notification, Pension, Search, Payment,
               GroupBanking, Services}

  F2: Behavioral Journey (C_B)
    → 사용자 행동 시퀀스 기반 퍼널 커뮤니티
    → 클래스: {AuthFunnel, QueryFunnel, TransferFunnel,
               ExploreFunnel, EntertainFunnel, ManageFunnel}

  F3: Functional Intent (C_D)
    → 기능 키워드 기반 의도 분류
    → 클래스: {Query, Execute, Auth, Configure, Explore, Event}

  F4: Tool Ecosystem (C_EF 병합)
    → 도구 연관 + 도구 패밀리 통합
    → 클래스: 도구 패밀리 그룹 (자동 결정, 예: 15~30개 패밀리)

  NMI 검증 (선정된 4 facet 간):
    NMI(F1,F2) = 0.13 < 0.3 ✓
    NMI(F1,F3) = 0.16 < 0.3 ✓
    NMI(F1,F4) = 0.21 < 0.3 ✓
    NMI(F2,F3) = 0.28 < 0.3 ✓
    NMI(F2,F4) = 0.33 → 약한 상관 → L_facet_orth로 소프트 직교 강제
    NMI(F3,F4) = 0.40 → 약한 상관 → L_facet_orth로 소프트 직교 강제

참고: facet 수 F는 데이터에 의해 자동 결정되며,
      도메인에 따라 F=2~수백 범위에서 변동한다.
      상기 CDP 은행 도메인에서는 F=4가 선정되었으나,
      다른 도메인(예: 의료, 제조)에서는 다른 F와 facet 정의가 도출된다.
```

#### 5.2.5 Stage 4: 계층 구조 정제 (Hierarchy Refinement)

각 facet 내에서 클래스 계층 구조를 정제하고, facet별 의미 분기 매트릭스를 자동 생성한다.

```
Stage 4 처리 절차:

── Step 4a: facet 내 계층 생성 ──

각 facet에 대해, 해당 facet의 클러스터링 기반으로 계층 구조를 구축.

F1(Structure Lens) 계층 예:
  Root
  ├── MainHome
  │   ├── 금융회원 홈 {일반홈, 쉬운홈}
  │   ├── 비로그인 홈
  │   ├── 혜택 홈
  │   ├── 상품 홈
  │   └── 자산 홈
  ├── Inquiry
  │   ├── 전체계좌조회
  │   ├── 거래내역조회
  │   │   ├── 입출금
  │   │   ├── 예적금
  │   │   └── 퇴직연금
  │   └── 운용현황
  ├── Transfer
  │   ├── 즉시/예약이체

  Root

── Step 4b: 공통 접두사 병합 ──

동일 facet 내에서 공통 경로 접두사를 가진 노드를 자동 병합.

예: F1의 "거래내역조회" 하위
  "거래내역조회-입출금-우리은행"     (NWINQ00005_001M)
  "거래내역조회-예적금_적금-우리은행" (NWINQ00005_004M)
  "거래내역조회-예적금_청약-우리은행" (NWINQ00005_005M)
  "거래내역조회-입출금-오픈뱅킹"     (NWINQ00005_002M)
  "거래내역조회-퇴직연금-우리은행"   (NWINQ00005_031M)

  → 공통 부모: "거래내역조회"
  → Level 2 분기: {"입출금", "예적금_적금", "예적금_청약", "퇴직연금"}
  → Level 3 분기: {"우리은행", "오픈뱅킹"}

── Step 4c: facet별 의미 분기 매트릭스 자동 생성 ──

동일 페이지명/용어가 다른 facet에서 다른 클래스에 할당되는 경우를
자동으로 동음이의어로 식별한다.

핵심 원리:
  기존 방식: 단일 온톨로지에서 동음이의어 = 같은 표면형, 다른 클래스
  본 발명: 다면 온톨로지에서 동음이의어 = "어떤 facet에서 동음이의어인가"

예시:
  "안내" (NWMMH00051_001M):
    F1(Structure): Services → 단일 클래스 (동음이의어 아님)
    F2(Journey): ExploreFunnel (상품탐색 시) vs QueryFunnel (이용안내 시)
      → F2에서 동음이의어!
    F3(Intent): Query (정보조회) → 단일 클래스 (동음이의어 아님)

  → 의미 분기 매트릭스 항목:
    {
      term: "안내",
      ambiguous_in: [F2],  // F2(Journey)에서만 동음이의어
      classes_F2: {
        ExploreFunnel: {differentiator: ["상품", "가입", "금리", "예적금"]},
        QueryFunnel: {differentiator: ["이용방법", "안내", "도움말", "FAQ"]}
      },
      unambiguous_in: [F1, F3]  // F1, F3에서는 명확
    }

  "전환":
    F1(Structure): 단일 클래스
    F2(Journey): TransferFunnel (이체 관련) vs QueryFunnel (분석 관련)
      → F2에서 동음이의어
    F3(Intent): Execute (이체 실행) vs Query (전환율 조회)
      → F3에서 동음이의어

  → {
      term: "전환",
      ambiguous_in: [F2, F3],
      classes_F2: {
        TransferFunnel: {differentiator: ["이체", "입금", "계좌"]},
        QueryFunnel: {differentiator: ["분석", "전환율", "채널", "CVR"]}
      },
      classes_F3: {
        Execute: {differentiator: ["이체", "실행", "완료", "입금"]},
        Query: {differentiator: ["분석", "조회", "통계", "추세"]}
      }
    }

핵심 차별점:
  기존: "전환"은 전역적으로 동음이의어 → 전역 공간에서 분리
  본 발명: "전환"은 F2와 F3에서만 동음이의어 → 해당 facet 부분공간에서만 분리
  → 불필요한 facet(F1)에서의 분리를 강제하지 않아 학습 효율 향상
```

#### 5.2.6 Stage 5: 도구 Facet 매핑 (Tool Facet Mapping)

중복 도구를 facet 벡터로 표현하여 구별하고, 팀별 추천 가중치를 생성한다.

```
Stage 5 처리 절차:

── Step 5a: 도구별 facet 벡터 생성 ──

각 도구 t에 대해, 모든 facet에서의 클래스를 할당하여 facet 벡터를 구성.

  tool_facet_vector(t) = [F1_class(t), F2_class(t), F3_class(t), F4_family(t)]

예:
  "전환율 분석_마케팅":
    F1(Structure): Transfer (이체 관련 페이지 연관)
    F2(Journey): TransferFunnel → QueryFunnel (전환율 분석은 조회)
    F3(Intent): Query
    F4(Tool Ecosystem): 전환율분석_패밀리
    → vector = [Transfer, QueryFunnel, Query, CVR_Family]

  "전환율 분석_경로":
    F1(Structure): Navigation (경로 분석은 네비게이션 관련)
    F2(Journey): ExploreFunnel (사용자 탐색 경로 분석)
    F3(Intent): Query
    F4(Tool Ecosystem): 전환율분석_패밀리
    → vector = [Navigation, ExploreFunnel, Query, CVR_Family]

  두 도구는 F4(패밀리)에서 동일하지만 F1, F2에서 다름
  → facet 벡터로 완전히 구별 가능

── Step 5b: 도구 패밀리 대표 벡터 생성 ──

각 도구 패밀리의 대표 facet 벡터를 생성하여,
프롬프트에 개별 도구 대신 패밀리 대표만 제시 가능.

패밀리 대표 벡터:
  "전환율분석_패밀리":
    공통 facet: F3=Query, F4=CVR_Family
    가변 facet: F1={Transfer, Navigation, ...}, F2={QueryFunnel, ExploreFunnel, ...}

  → 프롬프트에는 "전환율분석_패밀리(F3:Query)" 1개만 기술
  → 실제 도구 선택은 FC-LoRA가 facet 벡터로 결정

프롬프트 토큰 절감:
  개별 도구 × 3개 변종: 3 × 200 tokens = 600 tokens
  패밀리 대표 1개: 200 tokens
  → 66% 절감 (패밀리당)
  → 전체: 82,000 → 약 15,000 tokens (도구 패밀리화 효과)

── Step 5c: 팀별 사용 이력 기반 추천 가중치 ──

각 팀/개인의 도구 사용 이력에서 도구 패밀리 내 선호를 추출.

예:
  팀 A (마케팅 전략팀):
    "전환율 분석_마케팅" 사용 42회
    "전환율 분석_경로" 사용 8회
    "전환율 분석_경영진" 사용 2회
    → preference(팀 A, CVR_Family) = {마케팅: 0.81, 경로: 0.15, 경영진: 0.04}

  팀 B (CRM 운영팀):
    "전환율 분석_경로" 사용 35회
    "전환율 분석_마케팅" 사용 12회
    → preference(팀 B, CVR_Family) = {경로: 0.74, 마케팅: 0.26}

이 추천 가중치는 §5.8의 3-Level Decoupled Training의 Level 3(개인화)에서
Preference LoRA 학습 데이터로 사용된다.
```

#### 5.2.7 Stage 6: 대규모 Facet 관리 (Hierarchical Facet Management)

Facet 수가 수십~수백에 달하는 대규모 도메인(의료, 범정부 행정 등)에서는, 모든 facet을 동등한 수준에서 처리하면 계산 비용이 폭증한다. Stage 6은 대규모 facet을 계층적으로 관리하는 메커니즘을 제공한다.

```
Stage 6 처리 절차:

── Step 6a: Facet 계층 구성 (Facet Hierarchy) ──

Stage 3에서 선정된 F개 facet 중, facet 간 NMI가 0에 가까운 것들을
의미적 유사성 기준으로 상위 그룹(super-facet)으로 묶는다.

알고리즘:
  1. F개 facet 각각의 클래스 분포를 벡터로 표현
  2. facet 간 의미적 유사도 계산 (클래스명 임베딩의 코사인 유사도)
  3. 계층적 응집 클러스터링(hierarchical agglomerative clustering)으로
     super-facet 트리 구성

예시 (의료 도메인, F=25):
  Super-Facet A: 임상 관점 그룹
    ├── F1: 진단 분류 (ICD-10)
    ├── F2: 시술 분류 (수술/시술/처치)
    ├── F3: 약물 분류 (ATC)
    ├── F4: 검사 분류 (Lab/영상/기능)
    └── F5: 증상 분류 (주증상/부증상)

  Super-Facet B: 행정 관점 그룹
    ├── F6: 보험 분류 (급여/비급여/선택)
    ├── F7: 부서 분류 (진료과/병동/외래)
    ├── F8: 인력 분류 (전공의/전문의/간호사)
    └── F9: 시설 분류 (본원/분원/협력병원)

  Super-Facet C: 연구 관점 그룹
    ├── F10: 질환 분류 (희귀질환/만성/급성)
    ├── F11: 임상시험 분류 (Phase I/II/III/IV)
    └── F12: 문헌 분류 (근거수준 1a~5)

  ... (F13~F25: 공급망, 환자 경험, 법규 준수 등)

  → 3개 super-facet × 각 4~5개 하위 facet = 12+ facet
  → 나머지 13개 facet도 super-facet으로 그룹핑

Facet 계층의 depth:
  소규모 (F≤10): depth=1 (flat, 계층 불필요)
  중규모 (10<F≤50): depth=2 (super-facet → facet)
  대규모 (50<F≤200): depth=3 (mega-facet → super-facet → facet)
  극대규모 (F>200): depth=4 이상 (필요 시 자동 확장)

── Step 6b: Facet 중요도 스코어링 (Facet Importance Scoring) ──

모든 facet이 모든 질의에 동등하게 중요하지 않으므로,
질의별로 활성화할 facet 부분집합을 결정하기 위한 사전 스코어링.

  importance(f, query_type) = α · coverage(f) + β · discrimination(f)
                             + γ · usage_frequency(f)

  coverage(f): facet f가 전체 엔티티 중 몇 %를 분류하는지
  discrimination(f): facet f의 클래스가 얼마나 균등하게 분포하는지 (엔트로피)
  usage_frequency(f): 과거 질의에서 facet f가 활성화된 빈도

  → 질의 시 상위 K개 facet만 활성화 (K = min(F, K_max))
  → K_max: 계산 예산에 따라 결정 (기본 K_max = 16)

── Step 6c: 적응적 차원 할당 (Adaptive Dimension Allocation) ──

F가 수백일 때 dim_per_class=10을 유지하면 d_ont이 수천으로 폭증.
이를 방지하기 위한 적응적 차원 할당:

  소규모 (F≤10):
    d_f = dim_per_class × |C_f|
    dim_per_class = 10
    d_ont = Σ_f d_f (예: 440)

  중규모 (10<F≤50):
    d_f = max(dim_per_class × log2(|C_f| + 1), min_dim)
    dim_per_class = 8
    d_ont 상한: 1024
    → 초과 시 중요도 낮은 facet의 차원을 축소

  대규모 (50<F≤200):
    d_f = max(shared_dim + private_dim × I(importance(f) > τ), min_dim)
    shared_dim = 4 (모든 facet 공통 최소 차원)
    private_dim = 8 (중요 facet 추가 차원)
    d_ont 상한: 2048
    → 중요도 상위 30% facet에만 private_dim 할당

  극대규모 (F>200):
    2단계 인코딩:
    1. Super-facet 수준: d_super = 8 per super-facet
    2. Facet 수준: d_f = 4 (공통) + 4 (활성화 시)
    d_ont 상한: 4096
    → 질의 시 활성 facet만 full 차원 사용

핵심 원리:
  F가 증가하더라도 d_ont는 로그적으로만 증가하도록 제한.
  d_ont ≤ O(K_max × dim_per_class × log F) 보장.
```

### 5.3 FC-LoRA: Facet-Conditioned LoRA

#### 5.3.1 종래 OC-LoRA의 한계와 FC-LoRA의 차별점

종래 OC-LoRA는 "도메인"이라는 단일 축으로 어댑터를 분리하였다. 도메인은 수동으로 정의되며(marketing, analytics, product, technical, general의 5개 고정), 현장 데이터의 다중 관점을 반영하지 못하였다.

FC-LoRA는 AFOD가 자동 발견한 F개 facet을 기반으로, 다면적 조건부 어댑터 활성화를 수행한다.

```
종래 OC-LoRA (단일 축 분리):
  d = Φ(x)  → d ∈ {marketing, analytics, product, technical, general}
  h = m_d · (Q(W₀) + w_d · s_d · B_d · A_d) / ‖...‖_c · x
  → 5개 어댑터, 5가지 문맥 표현

FC-LoRA (다면 축 분리):
  g = Φ_multi(x)  → g = {g_1, g_2, ..., g_F}
    g_f ∈ R^{|C_f|}: facet f에서의 클래스별 활성화 가중치
  h = m · (Q(W₀) + Σ_{f=1}^{F} Σ_{c∈C_f} g_f[c] · s_{f,c} · B_{f,c} · A_{f,c})
      / ‖...‖_c · x
  → F × |C_f| 조합, F=4, |C_f|≈6 시 4×6 = 24개 어댑터
  → facet 조합으로 6^4 = 1,296가지 문맥 표현 가능

실용적 구현 — 희소 Facet 활성화 (Sparse Facet Activation):

  F가 수십~수백일 때 모든 facet의 어댑터를 동시 활성화하면 비용 폭증.
  질의별로 상위 K개 facet만 활성화하는 희소 활성화를 적용.

  h = m · (Q(W₀) + Σ_{f∈TopK(g,K)} g_f · s_f · B_f · A_f) / ‖...‖_c · x

  K = min(F, K_max), K_max: 계산 예산 (기본 16)

  Facet 계층 활용 (F>50):
    1단계: super-facet 중 상위 S개 선택 (S≤8)
    2단계: 선택 super-facet 내 상위 K/S개 facet 선택
    → O(F) 감지를 O(S + K)로 축소

  스케일별 구성:
    소규모 (F≤10): K=F, 전체 활성화. 메모리 예: 83.9M (0.26%)
    중규모 (F≤50): K=16, rank=32. 저장 1.05GB, 추론 활성 336M
    대규모 (F≤200): K=16, rank=16. 저장 2.1GB, 추론 활성 168M
    극대규모 (F>200): 공유 기저 어댑터 + facet별 ΔB_f(rank=4)
      B_f = B_shared + ΔB_f
      F=500: 저장 82M/layer, 추론 활성 33.6M/layer
```

#### 5.3.2 다면 Facet 감지기 Φ_multi(x)

```
Φ_multi(x) 결정 로직:

각 facet f에 대해 독립적으로 클래스 활성화 가중치를 산출한다.

For each facet f ∈ {F1, F2, ..., F_F}:

  1순위: 명시적 facet 태그 감지
    입력에 <ONT_REF> 또는 [F_f:class] 태그가 있으면 해당 클래스 확정
    (MF-AA가 사전 태깅한 경우)

  2순위: facet별 키워드 TF-IDF 매칭
    각 facet의 클래스별 대표 키워드 사전과 입력의 TF-IDF 유사도 계산

    F1(Structure) 키워드:
      Inquiry: {"조회", "내역", "현황", "잔액", "수익률"}
      Transfer: {"이체", "입금", "송금", "다건", "자동이체"}
      Security: {"로그인", "인증", "비밀번호", "PIN", "생체"}
      ...

    F3(Intent) 키워드:
      Query: {"조회", "확인", "분석", "보여줘", "알려줘"}
      Execute: {"이체", "가입", "해지", "변경", "설정"}
      Auth: {"로그인", "인증", "본인확인"}
      ...

  3순위: 페이지ID 접두사 매칭 (F1 전용)
    입력에 페이지 ID가 포함된 경우, 접두사로 F1 클래스 결정

  4순위: "general" 폴백
    각 facet의 기본 클래스(가장 빈도 높은 클래스) 할당

출력: g = {g_F1, g_F2, g_F3, g_F4}
  각 g_f는 해당 facet의 클래스별 가중치 벡터 (softmax 정규화)

예: "이번 달 전환율이 높은 채널의 가입 고객 세션을 분석해줘"
  g_F1 = {Transfer: 0.3, Inquiry: 0.4, MainHome: 0.1, ...}
  g_F2 = {QueryFunnel: 0.6, TransferFunnel: 0.3, ...}
  g_F3 = {Query: 0.7, Execute: 0.2, ...}
  g_F4 = {CVR_Family: 0.5, Session_Family: 0.3, ...}
```

#### 5.3.3 MoLoRA/MoE 대비 차별점

```
비교:
  MoLoRA/MoE:
    Router(x) = softmax(W_r · x)  ← 학습 파라미터 W_r
    → 단일 축 라우팅 (어떤 expert를 선택할 것인가)
    → 라우팅 불안정, expert collapse

  FC-LoRA:
    Φ_multi(x) = {Φ_f(x) for f in facets}  ← 규칙 기반, 학습 파라미터 없음
    → 다면 축 동시 라우팅 (각 facet에서 어떤 클래스인가)
    → 결정론적, 해석 가능, 안정적
    → facet별 독립 감지이므로 f1의 감지가 f2에 영향 없음

  LoRAMoE (Dou et al., 2024):
    학습 가능 라우터 + LoRA expert
    → 단일 축 라우팅의 한계 동일

  FC-LoRA 고유:
    (1) facet 축이 데이터에서 자동 발견 (AFOD)
    (2) 복수 facet의 조합으로 기하급수적 문맥 표현력
    (3) 규칙 기반 감지이므로 학습 불안정 없음
    (4) facet별 독립 감지이므로 cross-facet 간섭 없음
```

### 5.4 MF-OSL: Multi-Facet Ontology-Structured Loss

#### 5.4.1 총 손실 함수

```
총 손실 함수:
  L = L_wCE + λ₁·L_hier_multi + λ₂·L_dis_multi + λ₃·L_rel
    + λ₄·L_facet_orth + λ₅·L_tool_family

기본값:
  λ₁ = 0.3, λ₂ = 0.5, λ₃ = 0.2, λ₄ = 0.01, λ₅ = 0.1
```

#### 5.4.2 L_hier_multi: 다면 계층 보존 손실

```
기존: L_hierarchy = Σ_{(p,c)∈H} max(0, μ_k - cos(h_p, h_c))
  → 전역 hidden state h에서 부모-자식 유사도 강제

수정: L_hier_multi = Σ_f Σ_{(p,c)∈H_f} max(0, μ_k - cos(z_f(p), z_f(c)))

여기서:
  H_f: facet f 내의 부모-자식 쌍 (AFOD Stage 4에서 생성)
  z_f(p) = P_down_f · h_p: 부모의 facet f 투영 (MF-OPB의 투영 활용)
  z_f(c) = P_down_f · h_c: 자식의 facet f 투영

  μ_k = μ₀ · exp(-γ · k)
  μ₀ = 0.8, γ = 0.5

핵심 변경:
  → 전역 공간이 아닌 facet별 부분공간에서 계층 보존
  → F1의 계층(메뉴 트리)과 F2의 계층(행동 퍼널)이 독립적으로 보존
  → 한 facet의 계층 학습이 다른 facet에 간섭하지 않음

예시:
  F1(Structure)에서:
    cos(z_F1(Inquiry), z_F1(거래내역조회)) > 0.8 (k=1)
    cos(z_F1(Inquiry), z_F1(입출금)) > 0.49 (k=2)

  F2(Journey)에서:
    cos(z_F2(TransferFunnel), z_F2(이체정보입력)) > 0.8 (k=1)
    cos(z_F2(TransferFunnel), z_F2(이체완료)) > 0.49 (k=2)

  → F1과 F2의 계층이 서로 독립적으로 보존됨
```

#### 5.4.3 L_dis_multi: 다면 동음이의어 분리 대조 손실

```
기존: L_disambiguation = Σ_{(a,b)∈D} max(0, δ - ‖h_a - h_b‖₂)
  → 전역 공간에서 모든 동음이의어 쌍을 분리

수정: L_dis_multi = Σ_f Σ_{(a,b)∈D_f} max(0, δ_f - ‖z_f(a) - z_f(b)‖₂)

여기서:
  D_f: facet f에서의 동음이의어 쌍 (AFOD Stage 4c에서 자동 생성)
  z_f: facet f 부분공간에서의 표현

  δ_f = 1.5 (모든 facet에서 동일, 또는 facet별 조정 가능)

핵심 변경:
  → "어떤 facet에서 동음이의어인지"를 반영한 선택적 분리
  → facet에서 동음이의어가 아닌 쌍은 분리하지 않음 (불필요한 분리 방지)

예시:
  "전환"이 F2와 F3에서만 동음이의어인 경우:
    L_dis_F2: ‖z_F2(이체관련_전환) - z_F2(분석관련_전환)‖₂ > 1.5
    L_dis_F3: ‖z_F3(Execute_전환) - z_F3(Query_전환)‖₂ > 1.5
    L_dis_F1: 적용 안 함 (F1에서는 동음이의어 아님)
    L_dis_F4: 적용 안 함 (F4에서도 동음이의어 아님)

  → 기존 방식: 전역 공간에서 분리 → 4개 facet 모두에 영향
  → 본 발명: 관련 facet에서만 분리 → 학습 효율 + 정밀도 향상
```

#### 5.4.4 L_facet_orth: Facet 간 직교 보존 손실

```
L_facet_orth = Σ_{f≠g} ‖P_down_f · P_down_g^T‖_F²

여기서:
  P_down_f: facet f의 투영 행렬 (MF-OPB)
  ‖·‖_F: 프로베니우스 노름

목적:
  AFOD Stage 3에서 NMI < 0.3으로 검증된 직교성을
  학습 과정에서도 유지하도록 강제.

  특히 NMI ∈ [0.3, 0.5]인 "약한 상관" facet 쌍에 대해
  소프트 직교를 강제하여 학습 중 직교성이 열화되는 것을 방지.
```

#### 5.4.5 L_tool_family: 도구 패밀리 정렬 손실

```
L_tool_family = L_intra + L_inter

L_intra (패밀리 내 유사):
  = Σ_{family} Σ_{(i,j)∈same_family} max(0, τ_sim - cos(h_i, h_j))
  τ_sim = 0.7

L_inter (패밀리 간 분리):
  = Σ_{(i,j)∈diff_family} max(0, cos(h_i, h_j) - τ_diff)
  τ_diff = 0.3

여기서:
  h_i: 도구 i의 hidden state representation
  same_family: AFOD Stage 2f에서 결정된 동일 패밀리 내 도구 쌍
  diff_family: 다른 패밀리의 도구 쌍

목적:
  동일 패밀리 내 도구 ("전환율 분석_마케팅"과 "전환율 분석_경로")의
  representation이 유사하되 (cos > 0.7),
  다른 패밀리의 도구 ("전환율 분석"과 "코호트 분석")와는
  충분히 분리 (cos < 0.3).

  → 모델이 도구 패밀리 개념을 학습하여,
    프롬프트 없이도 유사 도구를 그룹으로 인식
```

### 5.5 MF-TW: Multi-Facet Token Weighting

```
기존: 토큰 유형별 고정 가중치
  w = 3.0 (ONT), 5.0 (DIS), 0.1 (distractor 내 ONT), ...

수정: Facet 관련성에 따른 동적 가중치

  L_wCE = -Σ_i w_i · log P(y_i | x)

  w_i = w_base(type_i) × facet_boost(token_i, query)

  w_base(type): 기존 토큰 유형별 기본 가중치
    일반 텍스트: 1.0
    온톨로지 태그: 3.0
    disambiguation 태그: 5.0
    SQL 키워드: 2.0
    도구명: 3.5
    distractor 내 일반: 0.3
    distractor 내 ONT: 0.1

  facet_boost(token_i, query):
    = Σ_f relevance_f(token_i) × importance_f(query) / F

    relevance_f(token_i): token_i가 facet f에서 얼마나 관련성 높은지
      → AFOD의 facet별 키워드 사전과의 매칭 점수

    importance_f(query): 현재 질의에서 facet f가 얼마나 중요한지
      → FC-LoRA의 facet 감지기 Φ_multi(x)의 활성화 강도

예시:
  질의: "이번 달 전환율이 높은 채널의 가입 고객 세션을 분석해줘"

  FC-LoRA 감지:
    F1 importance: {Inquiry: 0.4, Transfer: 0.3, ...} → max=0.4
    F2 importance: {QueryFunnel: 0.6, TransferFunnel: 0.3, ...} → max=0.6
    F3 importance: {Query: 0.7, Execute: 0.2, ...} → max=0.7
    F4 importance: {CVR_Family: 0.5, Session_Family: 0.3, ...} → max=0.5

  "전환율" 토큰:
    F1 relevance(Transfer) = 0.3
    F2 relevance(QueryFunnel) = 0.8
    F3 relevance(Query) = 0.9
    F4 relevance(CVR_Family) = 0.95
    facet_boost = (0.3×0.4 + 0.8×0.6 + 0.9×0.7 + 0.95×0.5) / 4 = 0.55
    w = 3.0 × 0.55 = 1.65

  distractor 내 "전환" (페이지 전환 의미):
    F3 relevance(Execute) = 0.6 (이체 관련)
    F3 importance(Query=0.7과 불일치) → 불일치 패널티
    facet_boost = 낮음
    w = 0.1 × 0.15 = 0.015 (매우 낮음)
```

### 5.6 MF-OPB: Multi-Facet Ontology Projection Bottleneck

#### 5.6.1 AFOD 연동 구조

```
기존 MF-OPB: 4개 고정 facet, d_ont=256 고정 분할
  Domain[0:80), Action[80:144), Entity[144:208), Temporal[208:256)

수정 MF-OPB: AFOD 발견 F개 facet, d_ont 동적 결정

  F개 facet, 스케일에 따른 적응적 차원 할당
  (AFOD Stage 6c의 정책에 따름):

  소규모 (F≤10):
    d_f = max(dim_per_class × |C_f|, min_dim)
    dim_per_class = 10, min_dim = 32
    d_ont = Σ_f d_f
    예 (CDP 은행, F=4):
      F1(Structure, |C|=12): d_F1 = 120
      F2(Journey, |C|=6):    d_F2 = 60
      F3(Intent, |C|=6):     d_F3 = 60
      F4(Tool, |C|≈20):      d_F4 = 200
      d_ont = 440

  중규모 (10<F≤50):
    d_f = max(dim_per_class × log2(|C_f| + 1), min_dim)
    dim_per_class = 8, min_dim = 16
    d_ont 상한 = 1024 (초과 시 중요도 낮은 facet 차원 축소)
    예 (의료, F=25):
      고중요도 15개 facet: 평균 d_f=48 → 720
      저중요도 10개 facet: 평균 d_f=24 → 240
      d_ont = 960

  대규모 (50<F≤200):
    d_f = shared_dim + private_dim × I(importance(f) > τ)
    shared_dim = 4, private_dim = 8
    d_ont 상한 = 2048
    예 (스마트팩토리, F=80):
      상위 30% (24개) facet: d_f = 4+8 = 12 → 288
      하위 70% (56개) facet: d_f = 4 → 224
      d_ont = 512

  극대규모 (F>200):
    2단계 인코딩: super-facet(d=8) + 활성 facet(d=4+4)
    d_ont 상한 = 4096
    예 (범정부 행정, F=300):
      30개 super-facet × 8 = 240
      활성 facet 16개 × 8 = 128
      비활성 facet 284개 × 4 = 1136
      d_ont = 1504

  핵심: d_ont ≤ O(K_max × dim × log F), F 증가 시에도 로그적 증가

── Step 6d: Facet 병합 알고리즘 ──

두 facet f_i, f_j의 NMI가 시간 경과에 따라 제2 임계값을 초과하게 된 경우:

  1. 어댑터 병합:
     B_merged = (n_i · B_i + n_j · B_j) / (n_i + n_j)
     A_merged = (n_i · A_i + n_j · A_j) / (n_i + n_j)
     (n_i, n_j: 각 facet의 학습 샘플 수)

  2. 투영 행렬 병합:
     P_down_merged: 두 facet의 P_down을 concatenate 후 SVD로 d_merged 차원 축소
     d_merged = max(d_i, d_j) (큰 쪽 차원 유지)

  3. 클래스 계층 병합:
     두 계층의 루트를 새 공통 루트의 자식으로 연결
     중복 클래스는 합집합으로 통합

  4. 분기 매트릭스 갱신:
     병합된 facet에서의 분기를 재계산

── Step 6e: Facet 분할 알고리즘 ──

한 facet f의 내부 클래스 수가 임계값(예: |C_f| > 50)을 초과하거나,
내부 NMI 분석에서 하위 그룹 간 독립성이 감지된 경우:

  1. facet f의 클래스 집합에 대해 2-way 클러스터링 수행
  2. 두 클러스터 간 NMI 계산 → NMI < 제1 임계값이면 분할 확정
  3. 어댑터 분할:
     B_f1 = B_f (복사 후 fine-tune)
     B_f2 = B_f (복사 후 fine-tune)
  4. 투영 행렬 분할:
     P_down_f의 행을 두 클러스터에 할당하여 P_down_f1, P_down_f2 구성
  5. F → F+1, facet 계층 업데이트
```

MF-OPB 5-Step (기존 구조 유지, facet 정의만 AFOD 연동):

  Step 1: Facet별 독립 투영
    z_f = P_down_f · h_dora  (d_model → d_f)

  Step 2: Facet별 비선형 정제
    z_f_refined = GELU(LayerNorm_f(z_f))

  Step 3: 입력 의존적 Facet 집계
    g_f = σ(w_f^T · h_dora + b_f)
    h_agg = Σ_f g_f · P_up_f · z_f_refined

  Step 4: 제약 복원
    노름 정규화: β = 0.3
    방향성 클리핑: facet별 target embedding 기반

  Step 5: 잔차 연결
    h_final = h_dora + α · h_norm

P_down_f 초기화가 AFOD 기반:
  기존: 기저 모델 hidden state → PCA
  수정: AFOD Stage 5의 facet별 클래스 임베딩으로 초기화
    → 현장 데이터의 실제 분포를 반영한 초기화
    → 학습 수렴 속도 향상

계층적 직교 임베딩 (§5.2.5의 계층 구조 활용):
  각 facet 내:
    형제 클래스(sibling) 직교: Gram-Schmidt
    부모-자식 포함 관계: β=0.7 부분공간 포함
  facet 간:
    차원 분할에 의한 구조적 직교 (자동 보장)
```

### 5.7 MF-AA: Multi-Facet Auto-Annotator

```
기존 Auto-Annotator: 단일 온톨로지 태그 [domain.subdomain:term]
수정 MF-AA: 다면 태그 형식

처리 파이프라인:

  Step 1: NER (기존과 동일)
    도메인 용어 추출

  Step 2: Facet-Aware Linking
    각 용어에 대해, 각 facet에서의 후보 클래스를 검색

    "전환율":
      F1 후보: {Transfer(0.4), Inquiry(0.6)}
      F2 후보: {QueryFunnel(0.7), TransferFunnel(0.3)}
      F3 후보: {Query(0.8), Execute(0.2)}
      F4 후보: {CVR_Family(0.9)}

  Step 3: Facet-Selective Disambiguation
    AFOD의 facet별 의미 분기 매트릭스를 참조하여,
    동음이의어인 facet에서만 disambiguation 수행.

    "전환율":
      F1에서 동음이의어? → 매트릭스 확인 → 아님 → 스킵
      F2에서 동음이의어? → 매트릭스 확인 → 예 → disambiguation 수행
      F3에서 동음이의어? → 매트릭스 확인 → 예 → disambiguation 수행
      F4에서 동음이의어? → 매트릭스 확인 → 아님 → 스킵

    F2 disambiguation:
      context_keywords: {"이번달", "채널", "가입", "세션", "분석"}
      QueryFunnel differentiator match: {"분석", "채널"} = 2
      TransferFunnel differentiator match: {} = 0
      → QueryFunnel 확정

  Step 4: Multi-Facet Tag Insertion

    OPE-X 분리 방식 (권장):
      메인 입력: "<ONT_REF_0>이 높은 <ONT_REF_1>의..."
      온톨로지 입력: {
        ref_id: 0,
        term: "전환율",
        facets: {
          F1: "Inquiry",
          F2: "QueryFunnel",
          F3: "Query",

        },
        disambiguation: {
          F2: {resolved: "QueryFunnel",
               rejected: ["TransferFunnel"]},
          F3: {resolved: "Query",
               rejected: ["Execute"]}
        }
      }

    인라인 방식 (대안):
      "[F1:Inquiry|F2:QueryFunnel|F3:Query|F4:CVR_Family:전환율]이 높은..."
```

### 5.8 LKCA: Learned KV Compression Adapter (Facet-Aware 확장)

#### 5.8.1 기본 구조 (기존 유지)

LKCA의 3-Stage 구조(Block-wise Compression, Query-Aware Selection, Sliding Window)는 기존과 동일하되, Ontology Anchor 처리를 facet 중요도 기반 적응적 압축으로 대체한다.

```
기존 LKCA (이진 판단):
  anchor_mask[j] = 1 if any token in block_j ∈ {[ONT_START], ...}
  → 온톨로지 블록: 압축 면제 (전부 원본 유지)
  → 비온톨로지 블록: 압축 (전부 압축)

수정 LKCA (연속 중요도):
  importance(block_j) = max_f(
    facet_density_f(block_j) × query_focus_f
  )

  facet_density_f(block_j):
    블록 j 내에서 facet f 관련 토큰의 비율

  query_focus_f:
    현재 질의에서 facet f의 활성화 강도
    (FC-LoRA의 Φ_multi(x) 출력 재활용)

  압축률 결정:
    importance > 0.8: 원본 유지 (압축 면제)
    importance ∈ [0.3, 0.8]: 경량 압축 (블록 크기 8로 축소)
    importance < 0.3: 완전 압축 (블록 크기 32로 압축)

예시:
  질의: "이번 달 전환율이 높은 채널 분석" (F3:Query 지배적)

  블록 42 (전환율 관련 온톨로지 토큰 포함):
    facet_density_F3(block_42) = 0.6 (Query 관련 토큰 60%)
    query_focus_F3 = 0.7
    importance = 0.6 × 0.7 = 0.42 → 경량 압축

  블록 100 (인증 관련 토큰):
    facet_density_F1(block_100) = 0.8 (Security 관련 토큰 80%)
    query_focus_F1 = 0.1 (현재 질의와 무관)
    importance = 0.8 × 0.1 = 0.08 → 완전 압축

  → 질의와 관련 없는 facet의 블록은 적극 압축
  → 질의 관련 facet의 블록은 보존
  → 기존 이진 판단보다 적응적이고 효율적
```

### 5.8a FOKVQ: Facet-Orthogonal KV Quantization — Facet 직교 분해 기반 질의 의존적 KV 양자화

#### 5.8a.1 동기: 랜덤 직교 vs 의미론적 직교

TurboQuant(§3.8a)은 랜덤 직교 회전으로 KV 벡터의 좌표 독립성을 유도한 후 균일 양자화를 적용한다. 본 발명의 FOKVQ(Facet-Orthogonal KV Quantization)는 이와 동일한 직교 분해 원리를 사용하되, **랜덤 회전 대신 facet 기반 의미론적 직교 분해**를 적용하고, **균일 양자화 대신 질의 의존적 적응 양자화**를 수행한다.

```
원리 비교:

  TurboQuant:
    K ∈ R^d → R·K (랜덤 직교 회전) → 좌표별 3bit 균일 양자화
    R: 랜덤 직교 행렬 (data-oblivious)
    → 모든 차원 동등, 모든 질의 동등

  FOKVQ (본 발명):
    K ∈ R^d → {P_down_f · K}_f (facet 직교 투영) → facet별 적응 양자화
    P_down_f: AFOD 발견 facet의 투영 행렬 (domain-aware)
    → 의미적으로 중요한 facet에 더 많은 비트 할당
    → 질의마다 중요 facet이 달라지므로 비트 할당도 동적 변화

  공통 원리: 직교 변환 → 독립 좌표 → 좌표별 최적 양자화
  차별점: 랜덤 vs 의미론적, 균일 vs 적응적, 정적 vs 질의 의존적
```

🔵 **Lie 군 수학적 기반.** 본 발명의 FOKVQ와 TurboQuant는 Lie 군 이론의 지수 사상(exponential map) e^{iHt}의 서로 다른 특수 사례로 통일된다. TurboQuant는 H=랜덤 반대칭 행렬, t=1(정적)인 경우이고, 본 발명의 FOKVQ는 H=AFOD facet 투영 연산자의 직합, t=g_f(q)(질의 의존적)인 경우이다. 즉 TurboQuant의 랜덤 회전과 FOKVQ의 의미론적 회전은 동일 수학적 프레임워크(직교군 O(d) 위의 지수 사상)의 상이한 매개변수화이며, FOKVQ는 도메인 온톨로지로부터 H를 결정하고 질의에 따라 t를 적응시킴으로써 양자화 품질을 극대화한다.

#### 5.8a.2 FOKVQ 알고리즘

```
Algorithm: Facet-Orthogonal KV Quantization

입력:
  K ∈ R^{L × d_model}  (L: 시퀀스 길이, d_model: 5120)
  V ∈ R^{L × d_model}
  {P_down_f ∈ R^{d_f × d_model}}_f  (F개 facet 투영 행렬, MF-OPB에서 공유)
  g = {g_f}_f  (현재 질의의 facet 활성화 강도, FC-LoRA에서 공유)
  B_total: 총 비트 예산 (예: 평균 4bit/차원)

🔵 ── Step 0: 헤드별 비등방성 판정 (Head-Level Anisotropy Gate) ──
🔵
🔵   각 어텐션 헤드 h에 대해, 사전 캘리브레이션 데이터로부터
🔵   유효 랭크 r_eff(h) = exp(H(p))를 측정한다.
🔵   (p_i = λ_i / Σλ, H = -Σ p_i log p_i, λ는 K^T K의 고유값)
🔵
🔵   r_eff(h) < τ (기본값 τ = d_head/3):
🔵     → FOKVQ 적용 (Step 1~6 진행)
🔵   r_eff(h) ≥ τ:
🔵     → 해당 헤드는 TurboQuant 방식의 균일 양자화 적용 (비등방성 불충분)
🔵
🔵   근거: 실험에서 r_eff > 14 헤드에 FOKVQ 적용 시 -346% 악화 관측 (§7.4)
🟢
🟢   주의: GQA+RoPE 모델(Qwen2.5, Llama-3 등)에서는 Uniform 양자화가
🟢   모든 비트에서 치명적으로 실패하므로(PPL 26~164배 증가, §7.4),
🟢   r_eff ≥ τ인 헤드에도 FOKVQ 적용을 권장한다.
🟢   Adaptive threshold τ는 RoPE 모델에서 하향 조정이 필요하다.

── Step 1: Facet 직교 분해 ──

  각 토큰 위치 t에 대해:
    For each facet f:
      K_f[t] = P_down_f · K[t]  ∈ R^{d_f}    // facet f 부분공간 투영
      V_f[t] = P_down_f · V[t]  ∈ R^{d_f}

  잔차 (facet으로 설명되지 않는 성분):
    K_res[t] = K[t] - Σ_f P_up_f · K_f[t]    // facet 투영의 잔차
    V_res[t] = V[t] - Σ_f P_up_f · V_f[t]

── Step 2: 질의 의존적 비트 할당 (Query-Dependent Bit Allocation) ──

  facet별 비트 수를 질의의 facet 활성화 강도에 비례하여 할당:

    b_f = round(B_total × d_f/d_model × (g_f / g_mean))

    여기서:
      B_total: 총 비트 예산 (예: 4 bits/dim)
      d_f/d_model: facet f의 차원 비율
      g_f: 현재 질의에서 facet f의 활성화 강도
      g_mean: 모든 활성 facet의 평균 활성화 강도

    비트 할당 범위: b_f ∈ [2, 8]
    비트 합 제약: Σ_f (b_f × d_f) ≤ B_total × d_model
🔵
🔵   감도 계수(gamma) 권장값: 실험 결과에 의하면(§7.4),
🔵     B_total ≤ 3bit: gamma = 0.3 (보수적 할당이 최적)
🔵     B_total = 4bit: gamma = 0.3~0.5
🔵     → gamma가 클수록 공격적 할당. 과도한 gamma(>0.7)는
🔵       저분산 facet의 극저비트 할당으로 오히려 품질 저하.

  예: "적금 전환율이 높은 채널 분석" 질의 (B_total=4bit)
    F1(Structure):  g=0.3, d=1280 → b=2bit  (1280×2 = 2,560bit)
    F2(Journey):    g=0.5, d=1280 → b=4bit  (1280×4 = 5,120bit)
    F3(Intent):     g=0.9, d=1280 → b=7bit  (1280×7 = 8,960bit)
    F4(Tool=CVR):   g=0.8, d=1280 → b=6bit  (1280×6 = 7,680bit)
    잔차:                          → 1bit QJL
    총: 24,320bit + 잔차 = ~5bit/dim 평균

  예: "로그인 인증 오류" 질의 (B_total=4bit)
    F1(Structure=Security): g=0.9, d=1280 → b=7bit
    F2(Journey=AuthFunnel): g=0.7, d=1280 → b=5bit
    F3(Intent=Auth):        g=0.8, d=1280 → b=6bit
    F4(Tool):               g=0.1, d=1280 → b=2bit  (과감 압축)
    → 완전히 다른 차원에 비트 집중

🔵 ── Step 2a: 8비트 역전 방지 (High-Bit Reversal Prevention) ──
🔵
🔵   B_total ≥ 8bit인 경우, facet별 적응적 할당을 비적용하고
🔵   전체 차원에 균일 양자화를 적용한다.
🔵
🔵   근거: 실험에서 B_total=8bit 시 FOKVQ의 KL divergence가
🔵   균일 양자화 대비 5~8배 악화됨을 관측하였다 (§7.4).
🔵   원인은 facet 투영 변환(P_down_f · K)의 부동소수점 반올림 오차가,
🔵   고비트에서의 양자화 이득을 초과하기 때문이다.
🔵   따라서 FOKVQ는 저비트(2~4bit) 양자화에 특화된 기법이며,
🔵   고비트에서는 종래의 균일 양자화가 더 효율적이다.

── Step 3: Facet별 양자화 ──

  For each facet f:
    K_f_q = ScalarQuantize(K_f, bits=b_f)
    V_f_q = ScalarQuantize(V_f, bits=b_f)

  양자화 방법:
    b_f ≥ 4: 균일 양자화 (absmax 또는 zeropoint)
    b_f < 4: TurboQuant의 Lloyd-Max 최적 양자화 적용 (Beta 분포 기반)
    → facet 투영 후의 좌표 분포는 이미 정규화되어 있으므로
      TurboQuant의 랜덤 회전 없이도 최적 양자화 적용 가능

── Step 4: 잔차 1-bit QJL 보정 ──

  K_res에 1-bit QJL 변환 적용 (TurboQuant과 동일 기법):
    K_res_q = sign(QJL_matrix · K_res)  // 1bit per dim

  이 단계는 facet 투영으로 설명되지 않는 잔차 성분의
  내적 추정 편향을 제거한다.

── Step 5: 압축된 KV 저장 ──

  저장 형식:
    For each token t:
      {K_f_q[t], b_f}_f  (facet별 양자화 값 + 비트 수)
      K_res_q[t]          (잔차 1bit)

── Step 6: 역양자화 및 어텐션 계산 ──

  어텐션 계산 시:
    K_approx[t] = Σ_f P_up_f · Dequantize(K_f_q[t], b_f) + QJL_restore(K_res_q[t])

  또는 facet 부분공간에서 직접 어텐션 계산 (효율적):
    Attn_f = softmax(Q_f · K_f_q^T / √d_f) · V_f_q
    Attn = Σ_f g_f · P_up_f · Attn_f  (facet별 어텐션 가중 합산)

  → 기존 어텐션 코드 변경 불필요 (K, V 입력만 교체)
```

#### 5.8a.3 LKCA(토큰 수 축소)와의 결합

```
FOKVQ는 LKCA(§5.8, 토큰 수 축소)와 직교적으로 결합 가능:

  Step A: LKCA로 토큰 수 축소
    32,768 토큰 → 9,728 토큰 (3.4배)

  Step B: FOKVQ로 잔존 토큰의 KV 양자화
    9,728 토큰 × d_model × 16bit → 9,728 × d_model × 4bit(평균) (4배)

  총 압축률: 3.4 × 4 = 13.6배

  메모리 절감:
    원본: 32,768 × 5120 × 2(K,V) × 2byte = 671MB/layer
    LKCA+FOKVQ: 9,728 × 5120 × 2 × 0.5byte = 49.9MB/layer
    → 13.4배 압축

  동시 사용자 수 (H200×4, 564GB):
    원본:         13명
    LKCA만:       44명
    TurboQuant만: 69명 (균일 3bit)
    FOKVQ만:      69명 (적응적 4bit, 정확도 더 높음)
    LKCA+FOKVQ:   ~180명

TurboQuant과의 결합도 가능:
  LKCA(토큰 축소) + TurboQuant(균일 양자화): ~230명, 도메인 무관
  LKCA(토큰 축소) + FOKVQ(적응 양자화): ~180명, 도메인 인식
  → FOKVQ는 동시 사용자 수는 약간 적으나, 도구 선택 정확도가 더 높음
  → 엔터프라이즈 환경에서는 정확도가 동시 사용자 수보다 중요
```

#### 5.8a.4 TurboQuant 대비 차별점 요약

```
┌──────────────────┬──────────────────────────┬──────────────────────────┐
│       속성       │       TurboQuant         │     FOKVQ (본 발명)      │
├──────────────────┼──────────────────────────┼──────────────────────────┤
│ 직교 변환        │ 랜덤 직교 행렬 R         │ Facet 투영 행렬 P_down_f │
│ 변환의 의미      │ 통계적 (해석 불가)       │ 의미론적 (facet별 해석)  │
│ 비트 할당        │ 균일 (모든 차원 3bit)    │ 적응적 (facet별 2~8bit)  │
│ 질의 의존성      │ 없음 (정적)              │ 있음 (g_f에 따라 동적)   │
│ 학습 필요        │ 불필요                   │ P_down_f 사전 학습 필요  │
│ 도메인 인식      │ 없음 (범용)              │ 있음 (facet 구조 반영)   │
│ 잔차 보정        │ 1-bit QJL               │ 1-bit QJL (동일)         │
│ 기존 코드 변경   │ 불필요                   │ 불필요 (K,V 입력만 교체) │
│ 적용 대상        │ 모든 LLM                 │ facet 학습된 모델        │
└──────────────────┴──────────────────────────┴──────────────────────────┘

핵심 차별:
  TurboQuant = "모든 차원을 동등하게 압축" (평등한 양자화)
  FOKVQ = "중요한 facet에 더 많은 비트를" (적재적소 양자화)

  → 같은 평균 비트에서, FOKVQ가 task 정확도에서 우월할 수 있음
  → 특히 도구 선택 정확도에서 결정적 차이:
    TurboQuant: 도구 관련 차원도 3bit → 미세한 도구 차이 소실
    FOKVQ: 도구 facet에 8bit 할당 → 미세한 도구 차이 보존
```

### 5.9 OPE-X: Ontology Prefix Encoder eXtended (Facet-Aware 확장)

```
기존 OPE-X 노드 임베딩:
  x_i = E_class[class_id] + E_domain[domain_id] + E_type[type_id]

수정 OPE-X 노드 임베딩 (AFOD 연동):
  x_i = Σ_{f=1}^{F} E_f[class_f(i)]

  E_f ∈ R^{|C_f| × d_ont}: facet f의 클래스 임베딩 테이블

  예: "전환율" 노드
    x = E_F1[Inquiry] + E_F2[QueryFunnel] + E_F3[Query] + E_F4[CVR_Family]

Graph Attention의 구조 바이어스도 facet별 확장:
  A_struct[i,j] = Σ_f bias_f[rel_type_f(i,j)]

  facet별 관계 유형이 다를 수 있음:
    F1에서 i→j: is-a (Inquiry → 거래내역조회)
    F2에서 i→j: follows (이체정보입력 → 이체정보확인)
    → 각 facet의 관계 유형에 맞는 bias 적용
```

### 5.11 통합 학습 알고리즘: Facet-Centric Training

```
Algorithm: Facet-Centric Training

핵심 전환: 종래 "3축 × N도메인"이 아닌 "F개 facet 모듈의 독립 학습 + 교차 정규화"

Input:
  M: 사전학습 모델 (4-bit NF4 양자화)
  AFOD_output: F개 facet 정의 + facet별 계층/동음이의어/도구패밀리
  D: RAFT 형식 학습 데이터

Initialize:
  F개 facet 모듈 인스턴스화:
    For each facet f = 1..F:
      Adapter_f:    {B_f, A_f, m_f, s_f}  (rank = r(F))  // r(F): F에 따른 적응적 rank
      Loss_f:       {hier_pairs_f, dis_pairs_f}           // AFOD 출력에서 추출
      Weight_f:     {keyword_dict_f}                       // facet f의 키워드 사전
      Projection_f: {P_down_f, P_up_f, LN_f, g_f_params}  // AFOD 임베딩 기반 PCA 초기화
      Compress_f:   {density_model_f}                      // facet f 토큰 밀도 모델
      Encode_f:     {E_f[class_id]}                        // 클래스 임베딩 테이블

  적응적 rank 결정:
    r(F) = max(4, min(32, 128 / F))
    → F=4: rank=32, F=16: rank=8, F=50: rank=4, F>128: rank=4(공유기저+ΔB)

For each epoch:
  For each batch (x, y, oracle, distractors) in D:

    ── Phase A: Facet 활성화 (희소) ──
    all_gates = Φ_multi(x)                  // 모든 facet의 활성화 강도
    active_facets = TopK(all_gates, K)      // 상위 K개 facet 선택
    // K = min(F, K_max), K_max = 16 (기본)

    ── Phase B: Per-Facet 순전파 ──
    For each f ∈ active_facets (병렬 실행 가능):

      // B-1: Facet 어댑터 적용
      delta_h_f = g_f · s_f · B_f · A_f · x       // facet f의 적응 출력

      // B-2: Facet 투영
      z_f = P_down_f · (h_dora + delta_h_f)        // facet f 부분공간으로 투영
      z_f = GELU(LN_f(z_f))                        // facet 내 정제

      // B-3: Facet 토큰 가중치
      w_f_tokens = Weight_f(tokens, g_f)            // facet f 관련 토큰 가중치

      // B-4: Facet 손실 쌍 추출
      hier_pairs_f = extract_hierarchy(x, Loss_f.hier_pairs)
      dis_pairs_f = extract_disambiguation(x, Loss_f.dis_pairs)

    ── Phase C: Cross-Facet 집계 ──
    h_agg = Σ_{f∈active} g_f · P_up_f · z_f        // 게이팅 집계
    h_norm = Constrain(h_agg, h_dora, β=0.3)        // 노름+방향 제약
    h_final = h_dora + α · h_norm                    // 잔차 합산

    ── Phase D: Per-Facet 손실 + Cross-Facet 손실 ──

    // Per-Facet 손실 (활성 facet에서만 계산)
    L_per_facet = Σ_{f∈active} (
      λ_h · L_hier_f(z_f, hier_pairs_f)             // facet f 부분공간에서 계층 보존
    + λ_d · L_dis_f(z_f, dis_pairs_f)               // facet f에서만 동음이의어 분리
    )

    // Cross-Facet 손실 (전체)
    L_cross = λ_o · L_facet_orth({P_down_f})         // facet 간 직교 보존
            + λ_t · L_tool_family(hidden, tool_families) // 도구 패밀리 정렬

    // 토큰 가중 CE (모든 활성 facet의 가중치 통합)
    w_combined = merge_facet_weights({w_f_tokens : f ∈ active})
    L_wCE = weighted_cross_entropy(logits, y, w_combined)

    // 통합
    L = L_wCE + L_per_facet + L_cross
    backward(L)

    ── Phase E: 비활성 Facet 처리 ──
    // 비활성 facet의 어댑터는 gradient를 받지 않음 (자연 동결)
    // → 비활성 facet의 지식이 망각되지 않음
    // → 다음 배치에서 해당 facet이 활성화되면 학습 재개

스케일별 동작:
  F=4 (CDP):     K=4, rank=32, 모든 facet 항상 활성 → 종래와 동등
  F=25 (의료):   K=16, rank=8, 배치당 16개 facet 활성
  F=80 (제조):   K=16, rank=4, 2단계 희소화, super-facet 경유
  F=200 (대규모): K=16, rank=4, 공유기저+ΔB_f
  F=500 (극대규모): K=16, rank=4, 3단계 희소화, mega→super→facet
```

### 6.6 정성적 효과

**첫째, 현장 데이터 직접 활용.** 종래 기술이 전제하는 "정규화된 온톨로지"를 수작업으로 구축할 필요 없이, AFOD가 비정규화 현장 데이터를 직접 입력받아 다면 직교 온톨로지를 반자동 구성한다.

**둘째, 도메인 일반화 및 대규모 facet 지원.** AFOD의 facet 발견은 데이터 의존적이므로, 금융(CDP), 의료(EMR/보험), 제조(스마트팩토리), 물류(배송/재고), 공공(행정 데이터), 이커머스 등 반구조화 메타데이터가 존재하는 모든 도메인에 동일 파이프라인으로 적용 가능하다. 각 도메인에서 발견되는 facet의 수는 F=4(소규모 CDP)에서 F=수백(범정부 행정)까지 변동하며, 계층적 facet 관리(Stage 6), 희소 활성화(FC-LoRA), 적응적 차원 할당(MF-OPB)에 의하여 대규모 facet에서도 계산 비용이 로그적으로만 증가한다.

**셋째, 이해관계자별 해석 가능성.** MF-OPB의 facet gate 값을 관찰하면, "이 질의는 F1(Structure) 관점에서 Inquiry, F2(Journey) 관점에서 QueryFunnel, F3(Intent) 관점에서 Query"와 같이 모델의 다면적 인식을 facet 수준에서 투명하게 해석할 수 있다. 이는 개발자, 마케터, 분석가 각각이 자신의 관점에서 모델의 판단을 이해할 수 있도록 한다.

**넷째, 도구 중복 해소.** 이름과 기능이 중복되는 수천 개의 도구를 facet 벡터로 구별하고, 팀별·개인별 사용 이력에 기반한 추천을 모델 가중치 수준에서 수행함으로써, 프롬프트에 모든 도구를 나열하는 비효율을 제거한다.

**다섯째, 운영 안정성.** GraphRAG 방식의 외부 그래프 DB 의존성을 완전히 제거하고, 온톨로지가 모델 가중치에 내재화되어 단일 장애점이 없는 서비스를 제공한다.

🟤 ### 6.7 Channel A (Flat Dump) 측정의 정성적 종합 — Channel C 필요성의 진단적 근거 (v5 전면 재작성)

§6.1의 실측치는 전부 *Channel A (flat dump) row*에 한정된 진단 결과다. 본 절은 이 측정이 본 발명의 청구항과 갖는 관계를 4가지 차원에서 기술하며, Channel C (weight internalize)의 필요성을 논거로 제시한다.

**첫째, Channel A 단일 도구에서 facet IR 신호 존재 확인.** Qwen에서 facet_full이 nl_full 대비 +9.4%p (0.820 vs 0.749). Channel A 안에서도 H_str (facet 구조 정보)가 도구 선택에 기여함을 시사한다. 단, 이 효과는 Llama에서 역전 (facet_full < nl_with_desc −3.7%p)되며, 이는 모델 학습 데이터의 포맷 분포 차이(§3.2.4: Qwen=Hermes-style typed JSON Schema, Llama=다중 포맷 혼합)에 기인한다. **Channel C (weight internalize) 이후에는 이 모델군 비대칭이 normalize됨이 본 발명의 기대 효과**이며, 이것이 §5.1의 facet-conditional fine-tuning의 동기가 된다. facet IR 신호가 Channel A에서 존재한다는 것은, Channel C에서 그 신호를 *안정적으로 내재화*할 가능성의 근거다.

**둘째, Channel A는 multi-step에서 실패함 — §3.2.1 비판의 직접 실증.** τ²-bench retail (N=114) multi-step에서 Qwen의 facet_full F1이 nl_full보다 −6.3%p 낮다. 단순 prompt 포맷 변경은 trajectory 길이가 늘수록 효과가 약화된다. 이는 §4.1 "가능 경로 85,000+" 문제를 Channel A 방식으로 해결할 수 없음의 직접 증거다. §3.2.1에서 본 발명이 비판한 "전량 덤프 방식의 한계"가 실측으로 확인됨. 따라서 **Channel A 실패는 Channel C (weight internalize)가 본질적 해결책임을 지지하는 negative 근거**이며, 본 발명의 청구항 2의 필요성을 실증한다.

**셋째, 정적 L1 steering (E7)도 실패 — per-facet per-token dynamic gating이 필수.** rank-2 KV 정적 개입은 single-token top-1 98.4% 회복에도 multi-tool F1=0. §5.1.1의 MF-OPB(F개 facet 축 per-token gating) 없이는 multi-step tool calling을 구현할 수 없음을 보인다. Channel C의 대안으로 고려되는 Channel C' (steering) 역시 L1 정적 방식은 불충분하며, per-token 재계산(L2) + facet product routing이 필요하다. 이는 §5.1.1의 아키텍처 선택 (고정 평균 bias가 아닌 input-conditional gate)의 정당성을 negative result로 강력 뒷받침한다.

**넷째, H_id 분리 가능성 — 토큰 압축 경로 확인.** Qwen에서 list_only→list_anon +231%, facet_full→facet_anon −2.2%. H_id (도구 이름 token)를 placeholder로 대체해도 H_str (facet IR)이 도구 선택 정보를 거의 보존한다. 이는 §6.5의 프롬프트 82K→12K 압축 목표의 실현 경로다 — Channel C에서 H_id 운반 비용을 가중치로 흡수하고, 프롬프트에는 H_str/H_sem의 compressed IR만 제공하는 방식이 가능함을 시사한다.

**종합**: §6.1 Channel A 결과는 본 발명의 *필요성*을 진단적으로 지지한다. Channel A 한계 입증 → Channel C 필요성. H_id 분리 가능성 → 압축 경로 존재. L1 정적 steering 실패 → per-token per-facet gating 필수. **본 발명의 실제 효과 — 도구 선택 정확도 향상(§4.2 과제 2) 및 계획 수립 개선(§4.2 과제 2) — 의 직접 측정은 §6.8의 Channel C 검증 단계에서 이루어진다.**

🟤 ### 6.8 발명 검증 기준 (Go/No-Go) — Channel C 측정 로드맵 (v5 신규)

본 발명의 핵심 청구항 (독립항 2 및 종속항 2-1~2-12)은 Channel C (facet-conditional weight internalization)의 실증적 효과에 기반한다. §6.1의 Channel A 측정은 진단적 근거에 그치며, 본 절은 독립항 2를 최종 승인하기 위해 필요한 검증 목표·기준·일정을 명시한다.

#### 🟤 6.8.1 핵심 검증 목표 (v5 신규)

본 발명이 주장하는 두 가지 핵심 기능적 효과를 직접 측정한다:

1. **도구 선택 정확도 향상**: facet-conditional fine-tuning(§5.1.1 MF-OPB) 적용 후 τ²-bench pass^1이 vanilla RFT baseline보다 유의미하게 높아야 한다.
2. **계획 수립 개선**: multi-step trajectory에서 DB end-state hash 정합률(τ²-bench native pass^k)이 향상되어야 한다. §4.1의 "가능 경로 85,000+" 조합 폭발 문제를 Channel C가 실질적으로 완화함을 실증.

위 두 목표 중 하나라도 미달하면 §6.8.3의 No-Go 조건이 발동된다.

#### 🟤 6.8.2 청구항별 검증 매핑 (v5 신규)

| 청구항 | 측정 채널 | 검증 방법 | 현재 상태 |
|--------|-----------|-----------|-----------|
| 독립항 1 (AFOD) | Channel A (diagnostic) | facet_full vs nl_full F1 (MetaTool ST4) | ✅ 측정 완료 (§6.1 참조) |
| 독립항 2 (facet-conditional fine-tuning) | Channel C × H_str+H_sem | τ²-bench pass^1 facet-RFT vs vanilla RFT | ⏳ **미측정 — Primary Go/No-Go** |
| 종속항 2-1~2-4 (MF-OPB gating) | Channel C | ablation: per-facet gating vs uniform fine-tuning | ⏳ 미측정 |
| 종속항 2-5~2-8 (H_id 압축 경로) | Channel C × H_id | list_anon 조건 extended to Channel C | ⏳ 미측정 |
| 종속항 2-9~2-12 (steering vector C') | Channel C' × L2 | MAT-Steer 비교 (§L2 prior 참조) | ⏳ 미측정 |

독립항 2의 Channel C 검증이 전체 청구항 트리의 Gate이다. 독립항 2 No-Go 시 종속항 2-1~2-12 전체가 실증 근거를 상실한다.

#### 🟤 6.8.3 명시적 Go/No-Go 판정 기준 (v5 신규)

**Go 조건** (전부 충족 필요):
- τ²-bench retail·telecom·airline 중 ≥2개 도메인에서
- facet-aware RFT pass^1 > vanilla RFT baseline **+5%p 이상**
- 각 도메인 N ≥ 50 tasks
- 95% 신뢰구간 비중첩 (bootstrap CI, n=1000)

**No-Go 조건** (아래 중 하나라도 해당 시):
- 위 Go 조건 미충족
- ≥2 도메인에서 facet-aware RFT가 vanilla RFT 대비 열위(−2%p 이하)
- §6.1 D0 재측정 후 가정 (가)~(마) 보정 결과가 Channel A 효과를 전면 소거

**No-Go 결과**: 독립항 2 및 종속항 2-1~2-12의 실증 근거 약화 → 청구항 범위 재검토 또는 발명 방향 전면 피벗. 독립항 1 (AFOD 분류체계)은 Channel A 측정치에 근거하므로 별도 판정.

> **사용자 명시 기준** (2026-05-18): "facet 온톨로지로 계획, 도구 선택에 개선이 안되면 포기해야 한다." — 위 Go/No-Go 기준은 이 지침의 정량적 구현이다.

🔵 ### 7.4 실시예 4: FOKVQ 실험적 검증 — KV 캐시 비등방성과 Facet-Aware 양자화 효과
🔵
🔵 GPT-2 Medium(24층, 16헤드, d_head=64) 모델에서 3개 코퍼스(기술문서, 코드, 대화체)를 사용하여 FOKVQ의 원리를 검증하였다.
🔵
🔵 **KV 캐시 비등방성 측정.**
🔵
🔵 | 코퍼스 | 평균 r_eff | 최소 r_eff | 최대 r_eff | STRONG 판정 |
🔵 |--------|-----------|-----------|-----------|------------|
🔵 | Technical | 8.98 | 4.09 | 13.79 | 24/24 (100%) |
🔵 | Code | 7.17 | 3.69 | 10.70 | 24/24 (100%) |
🔵 | Conversational | 9.24 | 4.02 | 14.03 | 24/24 (100%) |
🔵
🔵 d_head=64에서 유효 랭크 r_eff ≈ 7은 64차원 중 약 7차원만이 실질적 정보를 담고 있음을 의미한다. 상위 4개 PCA 축이 전체 분산의 69~94%를 설명하며, 조건수(condition number)는 610~59,899에 달한다. 이 비등방성은 코퍼스에 무관하게 모든 레이어에서 관찰되므로, 모델 가중치가 만들어낸 구조적 속성이다.
🔵
🔵 **Facet-Aware 양자화 vs 기준선 비교 (Technical 코퍼스).**
🔵
🔵 | 비트 | Uniform KL | Facet-Aware KL | Isotropize KL | Hadamard KL | FA 감소율 |
🔵 |------|-----------|---------------|--------------|-------------|----------|
🔵 | 2bit | 1.116 | 0.347 | 1.437 | 1.079 | 68.9% |
🔵 | 3bit | 0.279 | 0.097 | 0.317 | 0.312 | 65.0% |
🔵 | 4bit | 0.058 | 0.018 | 0.067 | 0.043 | 68.4% |
🔵 | 8bit | 0.000170 | 0.000973 | 0.000292 | 0.000150 | -472% (역전) |
🔵
🔵 2~4비트에서 Facet-Aware(PCA 기반 비균일 비트 할당)는 Uniform 대비 65~69% KL 감소, TurboQuant식 Isotropize 대비에서도 일관되게 우수하다. 3개 코퍼스 모두에서 동일 패턴이 재현된다.
🔵
🔵 **8비트 역전 현상.** B_total=8bit에서는 Facet-Aware의 KL이 Uniform 대비 5~8배 악화된다. 이는 facet 투영(P_down_f · K)의 부동소수점 반올림 오차가 고비트에서의 양자화 이득을 초과하기 때문이다. 따라서 §5.8a.2의 Step 2a(8비트 역전 방지)가 필수적이다.
🔵
🔵 **헤드별 이질성.** 384개 헤드(24층×16헤드)에 대해, 비등방성 지표 r_eff와 Facet-Aware 이득 간 Spearman ρ = -0.6811 (p = 1.13×10⁻⁵³)으로 극도로 유의한 음의 상관이 관찰되었다. 특히:
🔵 - Layer 12, Head 15 (r_eff=3.49): +82% 개선
🔵 - Layer 12, Head 1 (r_eff=15.39): -346% 악화
🔵
🔵 이 결과는 §5.8a.2의 Step 0(헤드별 비등방성 판정)의 근거이며, r_eff < d_head/3인 헤드에만 FOKVQ를 적용하는 적응적 전략의 필요성을 실증한다.
🔵
🔵 **Oracle 비트 할당과의 비교.** 4개 그룹(상위/중상/중하/하위 PCA 축)의 비트를 최적화하면 (5,3,3,2) 배분이 최적이며, Uniform 대비 73~93% 개선이 가능하다. 현재의 gamma 기반 heuristic은 Oracle 이득의 36~100%를 달성한다.
🔵
🔵 **참고**: 상기 실험은 AFOD 의미론적 facet이 아닌 PCA 통계적 facet에 기반한 검증이다. AFOD facet이 PCA보다 우수한지에 대한 실험은 후속 과제이다. 핵심 원리 — "비등방성을 파괴(등방화)하는 것보다 활용(비균일 할당)하는 것이 저비트에서 우수하다" — 는 PCA 수준에서 이미 검증되었으며, 의미론적 facet(AFOD)은 이를 더 개선할 잠재력을 가진다.
🟢
🟢 **Phase 4-1 End-to-End PPL 측정 결과 (2026-03-31 완료).**
🟢
🟢 상기 KL divergence 기반 검증에 더하여, 실제 Perplexity(PPL)를 측정하였다. GPT-2 Medium에 더하여 Qwen2.5-7B(GQA, 4 KV heads, d_head=128)을 포함하여 GQA+RoPE 모델에서의 FOKVQ 유효성을 검증한다.
🟢
🟢 평가 방법: full-forward KV cache → 위치별 KV slice + K 양자화 → single-token forward → NLL 측정. FP16 포함 모든 방법이 동일 평가 경로를 사용.
🟢
🟢 **GPT-2 Medium PPL 결과:**
🟢
🟢 | Method | 2bit | 3bit | 4bit |
🟢 |--------|------|------|------|
🟢 | FP16 | — | 17.59 | — |
🟢 | Uniform | 31.10 (+77%) | 17.71 (+0.7%) | 17.64 (+0.3%) |
🟢 | FOKVQ | 18.24 (+3.7%) | 17.54 (-0.2%) | 17.65 (+0.4%) |
🟢
🟢 **Qwen2.5-7B PPL 결과:**
🟢
🟢 | Method | 2bit | 3bit | 4bit |
🟢 |--------|------|------|------|
🟢 | FP16 | — | 8.21 | — |
🟢 | Uniform | 678 (+8162%) | 211 (+2465%) | 1344 (+16269%) |
🟢 | FOKVQ | 8.78 (+6.9%) | 8.44 (+2.7%) | 8.23 (+0.3%) |
🟢
🟢 FOKVQ 3bit는 FP16 대비 GPT-2에서 -0.2%, Qwen에서 +2.7%로, 5.3배 메모리 압축(16bit→3bit) 대비 PPL 열화가 3% 이내이다.
🟢
🟢 **GQA+RoPE에서 Uniform의 치명적 실패.** Qwen2.5-7B에서 Uniform 양자화는 모든 비트에서 PPL이 26~164배 증가한다. RoPE가 K 벡터의 차원 쌍에 위치 의존적 회전을 적용하여 차원 간 강한 상관관계를 만들며, per-token uniform 양자화가 이를 파괴하기 때문이다. 본 발명의 PCA 기반 FOKVQ는 이 상관 구조를 보존하여 FP16 수준 PPL을 유지한다.
🟢
🟢 이 결과는 §5.8a에서 기술한 FOKVQ의 실용적 우위를 end-to-end 지표로 확인하며, 특히 GQA+RoPE 아키텍처를 채용하는 최신 LLM(Qwen, Llama, Mistral 등)에서 PCA 기반 비균일 양자화가 필수적임을 실증한다.

**입력**: MetaTool Subtask 4 (multi-tool selection, 본 평가에서는 사용자 질의당 평균 1.6~2.1 도구 호출). N=64 무작위 sample (seed=0). Qwen2.5-7B-Instruct (bfloat16, eager attention, 28 layers, 28 Q heads, 4 KV heads), Llama-3.1-8B-Instruct (Nous repo, bfloat16, eager attention, 32 layers, 32 Q heads, 8 KV heads). max_new_tokens=192. 평가 metric: F1 (multi-tool selection over predicted set ∩ ground-truth set).

- nl_full: 도구 이름만 나열 (현 표준)
- nl_with_desc: 이름 + 짧은 자연어 설명
- facet_full: `name | action | domain : desc` (다면 직교 IR)
- facet_compact: `name|action_abbrev|domain` (저정보 압축)
- list_only: `[name1, name2, ...]` (이름만 atomic)
- noprompt: query only (zero-shot sanity)

|---|---|---|---|---|
| nl_full | 0.749 | 0.874 | 146 | 154 |
| nl_with_desc | 0.747 | **0.898** | 271 | 279 |
| **facet_full** | **0.820** | 0.861 | 312 | 317 |
| facet_compact | 0.523 | 0.553 | 137 | 143 |
| list_only | 0.214 | 0.638 | 95 | 101 |
| noprompt | 0.000 | 0.000 | 55 | 37 |

**해석**: Qwen은 facet IR을 prompt format으로 받았을 때 +9.4 %p (0.749 → 0.820), Llama는 facet_full보다 nl_with_desc가 +3.7 %p 우위 (0.861 vs 0.898). 즉 prompt-only manipulation은 *모델군 비대칭*을 보인다. 본 발명의 facet-conditional fine-tuning (§5.1)은 *모델군 비대칭을 normalize*하여 어느 모델군에서도 facet IR 처리 능력을 가중치 수준에서 보장하는 메커니즘이며, 후속 측정(§6.1 v5)에서 검증한다.

🟣 ### 7.6 실시예 6: 이름 anonymization에 의한 분포 회복 (v4 신규, E10b)

**목적**: 본 발명의 핵심 가정 — "도구 이름 token이 KV cache의 dominant cost source이며, facet vector로 대체 가능" — 의 사전 검증. 만약 이름 token을 제거하고 placeholder + facet IR만 제공해도 도구 선택이 가능하다면, 본 발명의 facet vector 내재화가 이름 token 의존성을 *영구적으로 대체* 가능함이 입증된다.

**입력**: MetaTool ST4 N=64 (실시예 5와 동일). 5종 condition: nl_full, facet_full, list_only, **list_anon**, **facet_anon**.
- **list_anon**: 도구 이름 → T1..Tn placeholder, ID-to-name mapping이 system prompt 하단에 명시. 예: `Tools (by ID): [T1, T2, ..., Tn]. ID-to-name mapping: T1=NewsTool, T2=WeatherTool, .... Emit <tool_call>{"name":"X","arguments":{}}</tool_call> blocks using the real tool names from the mapping.`
- **facet_anon**: facet_full 형식에서 이름도 placeholder로, 매핑을 ID 옆에 명시. 예: `- T1 | read | news : ... ID-to-name mapping: T1=NewsTool, ...`

**결과 (Qwen2.5-7B)**:

| 조건 | F1 | 프롬프트 토큰 | 비고 |
|---|---|---|---|
| nl_full | 0.749 | 146 | baseline |
| list_only | 0.214 | 95 | 이름만 단독 → 분포 외 |
| **list_anon** (placeholder + mapping) | **0.708** | 173 | **F1 +0.494, +231%** |
| facet_full | 0.820 | 312 | facet IR |
| **facet_anon** (placeholder + facet IR) | **0.802** | 386 | **facet_full 대비 −0.018, −2.2%** |

**결과 (Llama-3.1-8B)**:

| 조건 | F1 | 프롬프트 토큰 |
|---|---|---|
| nl_full | 0.874 | 154 |
| list_only | 0.638 | 101 |
| list_anon | 0.518 | 177 |
| facet_full | 0.861 | 317 |
| facet_anon | 0.747 | 390 |

**해석**:
1. **list_only → list_anon F1 +231% (Qwen)**: 이름 token을 placeholder로 분리하고 mapping을 하단에 제공하면, 모델은 system prompt의 mapping 라인을 *재참조*하면서 분포 내로 회복한다. 이는 학습 시 *완전한 schema 컨텍스트와 함께 본 이름*만 단독으로 제공하면 OOD가 되는 분포 특성을 직접 측정한 것이다.
2. **facet_full → facet_anon F1 −2.2% (Qwen)**: facet IR이 있는 상황에서 이름 token을 placeholder로 바꿔도 F1 손실은 최소 (0.820 → 0.802). 즉 **facet IR이 이름 token의 도구 선택 정보 대부분을 운반**한다.
3. **Llama는 list_anon에서 분포 회복이 미흡 (0.638 → 0.518)**: 모델군 비대칭. Llama는 NL 친화 학습 데이터의 영향으로 *원래 이름의 자연어 의미*에 더 의존.

**산업적 함의**: 본 발명의 facet vector 내재화 후에는, *이름 token을 prompt에 포함하지 않고 facet vector만으로* 도구 선택이 가능함이 시사된다. 이는 v3 §6.1의 프롬프트 토큰 82K → 12K 절감 (85% 감소) 목표치의 직접 실현 메커니즘이다. 본 결과를 청구항으로 보강하기 위해 §8에 종속항 2-11 (placeholder + mapping 형식의 facet vector serialization) 신규 추가하였다.

**출처**: `reports/facet_ontology_2026_04/{qwen,llama}_e10b_n64.json`

🟣 ### 7.7 실시예 7: 정적 rank-2 KV 개입의 multi-tool 한계 (v4 신규, E7)

**목적**: 본 발명의 facet-centric 접근이 *단순 1차 모멘트 KV 보정*으로 대체될 수 없음을 negative result로 입증.

**실험 설계**:
- 베이스: Qwen2.5-7B-Instruct, Llama-3.1-8B-Instruct
- 비교 조건 4종:
  - **full** (baseline): 전량 schema 덤프 prompt
  - **noprompt**: 비공급 zero (sanity)
  - **static**: prompt 제거 + 평균 attention output 방향으로 rank-2 KV 보정 (정리 1: 1차 모멘트 보정). KV side의 모든 token에 대해 동일한 rank-2 bias를 더해 평균 attention 분포를 회복.
  - **hybrid**: rank-2 KV 보정 + Q-projection bias (정리 2: 분포 모드 회복). KV side bias에 더해 Q-side에서 클래스 conditional rank-2 bias를 추가하여 attention 분포의 *모드*를 회복.
- 평가: MetaTool ST4 multi-tool selection, F1

**Single-tool sanity (별도 측정, summary 외, 정리 2 hybrid 조건)**:
- next-token top-1 일치율: **98.4%** (Qwen)
- KL divergence: **25.05 → 3.01** (Qwen, baseline KL → hybrid KL)
- 즉 single-tool first-token level에서는 분포 모드 회복이 성공적이다.

**Multi-tool F1 (본 실시예 핵심)**:

| Condition | Qwen F1 | Llama F1 |
|---|---|---|
| full (baseline) | 0.749 | 0.874 |
| noprompt | 0.000 | 0.000 |
| static (rank-2 KV) | **0.000** | **0.000** |
| hybrid (rank-2 KV + Q-bias) | **0.000** | **0.000** |

**해석**:
1. Single-tool 분포 모드는 정적 rank-2 개입으로 회복 가능 (top-1 98.4%).
2. 그러나 multi-tool selection F1은 0 — **autoregressive trajectory에서 누적되는 schema 제약을 정적 1차 모멘트가 보존하지 못함**.
3. 이는 정보이론적으로 본 발명이 §3.4에서 비판한 "단일 (B, A) 어댑터" 한계의 *KV-side 변형* 한계와 같은 본질이다. 한 평균 방향 vector는 *조건부 분포의 mode* 를 보존하지 못하며, multi-tool처럼 여러 *condition*이 동시에 활성화되어야 하는 trajectory에서는 본질적으로 부족하다.
4. **F개 facet 축 각각의 input-conditional gating + 직교 부분공간 투영 (MF-OPB, §5.1.1)** 가 multi-tool에서 본질적으로 필요함을 negative result로 강력 시사한다.

**산업적 함의**: 본 발명의 핵심 청구항 2 (Facet별 선택적 분기 해소 미세조정)는 *대안 기술 X가 안 되는 곳에서* 작동한다는 직접 증거를 확보. 단순한 prompt 압축이나 정적 KV 보정으로 대체 가능하지 않음.

## 8. 청구 범위

> **청구 전략 (심사관 비판 반영 수정):**
> 1. **모든 독립항은 자립형** — 다른 청구항을 인용하지 않음.
> 2. **AFOD의 핵심 진보성은 "facet-동음이의어 공동 발견"** — 개별 기법(NMI, multi-view clustering)은 공지이나, facet 직교성 검증과 facet별 의미 분기 매트릭스를 단일 파이프라인에서 공동 산출하는 것이 비자명한 기술적 기여.
> 3. **독립항 수 축소 (6→3)** — 분할 출원 고려하여 핵심 3개만 독립항. 나머지는 종속항으로 전환.
> 4. **선행기술 회피**: 독립항 1에서 특정 클러스터링 기법(Markov Chain 등)을 한정하지 않아, 기법 변경에 의한 회피를 방지.

### 독립항 1: Facet-분기 공동 발견 방법

엔터프라이즈 환경의 반구조화(semi-structured) 도메인 데이터로부터, 상호 직교하는 복수의 의미론적 관점(facet)과 각 facet에 특유한 컨텍스트 의존적 의미 분기 정보를 공동 발견(co-discover)하는 방법에 있어서,

(a) 도메인 엔티티(용어, 도구, 계획 경로를 포함)의 집합에 대해, 서로 상이한 정보원을 각각 기반으로 하는 복수(N≥2)의 독립적 클러스터링을 수행하여, 상기 동일 엔티티 집합에 대한 복수의 상이한 분류 결과를 생성하는 다관점 클러스터링 단계;

(b) 상기 복수의 클러스터링 결과 간의 쌍별 통계적 독립성 척도를 계산하고, 독립성이 소정 기준 이상인 클러스터링 조합을 직교 facet 후보로 판정하며, 독립성이 소정 기준 미만인 클러스터링 쌍을 병합하여, F개(F≥2)의 직교 facet을 선정하되 F의 값이 데이터 의존적으로 결정되는 직교 facet 선정 단계;

(c) 선정된 각 facet 내에서 클래스 계층 구조를 정제하면서, **동시에**, 동일 엔티티(용어, 도구, 또는 계획 경로)가 상기 복수의 facet 중 어떤 facet에서 서로 다른 클래스에 할당되는지를 식별하여, 각 분기에 대해 "분기가 발생하는 facet의 집합", "해당 facet에서의 분기 클래스 쌍", 및 "각 분기를 구별하는 문맥 조건(differentiator)"을 포함하는 **facet별 의미 분기 매트릭스**를 생성하는 계층 정제 및 facet별 분기 공동 발견 단계

를 포함하되,

상기 의미 분기는 용어 수준의 다의성(동음이의어), 동일 기능을 수행하는 복수 도구 간의 선택 분기(도구 경로 분기), 및 동일 목적을 달성하는 복수의 도구 체인 간의 선택 분기(계획 경로 분기)를 포함하는 상위 개념이며,

상기 facet별 의미 분기 매트릭스는, 분기가 존재하지 않는 facet에 대해서는 해당 엔티티를 비분기로 표기하여, 후속 대규모 언어 모델의 미세조정에서 해당 facet의 부분공간에서만 선택적으로 분기 해소 학습이 수행되고 비분기 facet에서는 학습이 억제되도록 하는 정보를 제공하는 것

을 특징으로 하는 facet-분기 공동 발견 방법.

#### 종속항 1-1

독립항 1에 있어서, 상기 다관점 클러스터링 단계의 입력 데이터가 비정규화된 페이지 경로 데이터를 포함하는 경우, 상기 다관점 클러스터링 단계에 선행하여, 복수의 상이한 구분자 패턴이 혼재하는 상기 페이지 경로 데이터에 대해 구분자 패턴을 감지하고, 감지되지 않는 경로에 대해서는 언어 모델 기반 의미 분절을 수행하여 정규화하는 경로 정규화 단계를 더 포함하는 것을 특징으로 하는 방법.

#### 종속항 1-2

독립항 1에 있어서, 상기 복수의 독립적 클러스터링은 경로 구조 기반 클러스터링, 사용자 행동 시퀀스 기반 클러스터링, 시스템 식별자 패턴 기반 클러스터링, 기능 키워드 기반 클러스터링, 및 도구 파라미터 유사도 기반 클러스터링 중 3개 이상을 포함하는 것을 특징으로 하는 방법.

#### 종속항 1-3

독립항 1에 있어서, 상기 직교 facet 선정 단계에서 NMI가 제1 임계값 이상 제2 임계값 이하인 클러스터링 쌍에 대하여, 해당 쌍을 별개의 facet으로 유지하되, 후속 미세조정에서 해당 facet 쌍의 투영 행렬 간에 직교 정규화 손실을 적용하도록 소프트 직교 표시를 부여하는 것을 특징으로 하는 방법.

#### 종속항 1-4

독립항 1에 있어서, 도구 카탈로그에 대해 도구명 유사도와 파라미터 스키마 유사도의 가중 결합으로 도구 간 유사도를 산출하고, 유사도가 소정 임계값 이상인 도구를 도구 패밀리로 그룹핑하며, 각 도구를 상기 복수 facet에서의 클래스 할당 벡터(facet 벡터)로 표현하는 도구 facet 매핑 단계를 더 포함하는 것을 특징으로 하는 방법.

#### 종속항 1-5

독립항 1에 있어서, 선정된 facet의 수(F)가 소정 임계값(예: 10)을 초과하는 경우, 상기 복수의 facet을 의미적 유사성에 기반한 계층적 응집 클러스터링으로 상위 그룹(super-facet)으로 묶어 facet 계층 구조를 구성하되, 상기 facet 계층의 깊이는 F의 크기에 따라 적응적으로 결정되고, 후속 미세조정에서 질의별로 상기 facet 계층을 통한 2단계 이상의 희소 선택(상위 그룹 선택 후 하위 facet 선택)이 수행되도록 하는 계층적 facet 관리 단계를 더 포함하는 것을 특징으로 하는 방법.

#### 종속항 1-6

독립항 1에 있어서, 선정된 facet의 수(F)가 소정 임계값을 초과하는 경우, 각 facet에 할당하는 온톨로지 부분공간의 차원(d_f)을, facet의 중요도 스코어에 따라 차등 할당하되, 전체 온톨로지 차원(d_ont)이 F에 대하여 로그적으로만 증가하도록 d_ont ≤ O(K_max × dim × log F)의 상한을 적용하는 적응적 차원 할당을 수행하는 것을 특징으로 하는 방법.

### 독립항 2: Facet별 선택적 분기 해소를 수반하는 대규모 언어 모델 미세조정 방법

대규모 언어 모델의 미세조정에 있어서, 복수의 상호 직교하는 의미론적 관점(facet)에 기반하여, 도메인 온톨로지 구조 및 컨텍스트 의존적 도구 선택에 필요한 의미 분기 정보를 모델 가중치에 내재화하는 방법으로서,

(a) 상기 복수의 facet 각각에 대응하는 독립적인 저랭크 어댑터를 보유하고, 입력 텍스트로부터 각 facet에서의 클래스를 감지하여 해당 facet의 어댑터를 조건부로 활성화하되, facet의 수가 소정 임계값을 초과하는 경우 상위 K개 facet만을 희소적으로 활성화하는 facet 조건부 저랭크 적응 단계;

(b) 상기 저랭크 적응의 출력을 각 facet에 대응하는 직교 부분공간으로 독립 투영한 후, 입력 의존적 게이팅으로 facet별 기여도를 조절하여 집계하고, 노름 및 방향 제약 하에 잔차 연결로 합산하는 다면 직교 투영 병목 단계;

(c) 각 facet 내의 부모-자식 쌍의 은닉 상태 표현을 해당 facet의 부분공간에서 비교하여, 계층 거리에 따른 감쇠 마진 이상의 유사도를 강제하는 다면 계층 보존 손실을 적용하는 단계;

(d) 사전에 구성된 facet별 의미 분기 매트릭스 — 각 엔티티에 대해 의미 분기가 발생하는 facet의 집합과, 해당 facet에서의 분기 클래스 쌍과, 각 분기를 구별하는 문맥 조건을 포함하는 정보 — 에 기반하여, 분기가 존재하는 것으로 지정된 facet의 부분공간에서만 해당 분기 쌍의 표현이 분리 마진 이상으로 분리되도록 강제하고, 분기가 존재하지 않는 facet에서는 상기 분리를 강제하지 않는 **facet 선택적 분기 해소 대조 손실**을 적용하는 단계

를 포함하되,

상기 (d) 단계의 facet 선택적 분기 해소에 의하여, 분기가 아닌 facet에서의 불필요한 표현 왜곡이 방지되고, 분기가 발생하는 facet에서만 집중적으로 해소 학습이 수행되며,

상기 의미 분기는 용어 수준의 다의성(동음이의어) 및 동일 기능을 수행하는 복수 도구 간의 컨텍스트 의존적 선택(도구 경로 분기)을 포함하는 것

을 특징으로 하는 대규모 언어 모델 미세조정 방법.

#### 종속항 2-1

독립항 2에 있어서, 상기 facet 조건부 저랭크 적응의 감지기는 학습 가능 파라미터 없이 규칙 기반으로 동작하되, 각 facet에 대하여 독립적으로 클래스 활성화 가중치를 산출하여 facet 간 감지 독립성을 보장하는 것을 특징으로 하는 방법.

### 독립항 3: Facet 직교 분해 기반 질의 의존적 KV 캐시 양자화 방법

대규모 언어 모델의 어텐션 레이어에서의 키(Key)와 값(Value) 캐시를, 복수의 상호 직교하는 의미론적 관점(facet)에 기반하여 양자화하는 방법으로서,

(a) 상기 K, V 벡터를 복수(F≥2)의 facet에 각각 대응하는 직교 투영 행렬에 의하여 facet별 부분공간으로 분해하고, 상기 직교 투영으로 설명되지 않는 잔차 성분을 분리하는 facet 직교 분해 단계;

(b) 현재 질의에서의 각 facet의 활성화 강도에 기반하여, 활성화 강도가 높은 facet의 부분공간에는 상대적으로 높은 비트 수를, 활성화 강도가 낮은 facet의 부분공간에는 상대적으로 낮은 비트 수를 할당하되, 전체 평균 비트 수가 소정의 예산 이내가 되도록 하는 질의 의존적 비트 할당 단계;

(c) 각 facet의 부분공간에서 상기 할당된 비트 수로 스칼라 양자화를 수행하는 facet별 양자화 단계;

(d) 상기 잔차 성분에 대하여 1비트 양자화된 Johnson-Lindenstrauss 변환을 적용하여 내적 추정의 편향을 제거하는 잔차 보정 단계

를 포함하되,

상기 직교 투영 행렬은 도메인 온톨로지의 의미론적 관점(facet)으로부터 도출되어, 각 부분공간에 해석 가능한 의미(기능 관점, 구조 관점, 도구 관점 등)가 부여되며,

상기 질의 의존적 비트 할당에 의하여 동일 KV 캐시라도 질의에 따라 서로 다른 facet에 비트가 집중되어, 균일 양자화 대비 도메인 특화 작업(도구 선택, 의미 분기 해소 등)에서의 정확도가 향상되는 것

을 특징으로 하는 facet 직교 분해 기반 질의 의존적 KV 캐시 양자화 방법.

#### 종속항 3-1

독립항 3에 있어서, 상기 facet별 양자화에서 할당 비트 수가 4 이상인 facet에는 균일 양자화(absmax 또는 zeropoint)를 적용하고, 할당 비트 수가 4 미만인 facet에는 해당 부분공간 좌표의 분포에 최적화된 Lloyd-Max 양자화를 적용하는 것을 특징으로 하는 방법.

#### 종속항 3-2

독립항 3에 있어서, 상기 facet 직교 분해 단계의 직교 투영 행렬은 독립항 2의 다면 직교 투영 병목의 투영 행렬과 동일한 것을 사용하여, 미세조정 시의 facet 부분공간과 추론 시의 양자화 부분공간이 일치하는 것을 특징으로 하는 방법.

#### 종속항 3-3

독립항 3에 있어서, 상기 방법은 독립항 2의 종속항 2-9에 기재된 토큰 수 축소와 결합하여, 토큰 수 축소 후 잔존 토큰에 대하여 상기 facet 직교 분해 기반 양자화를 적용함으로써, 토큰 수 축소와 비트 수 축소의 곱셈적 압축 효과를 달성하는 것을 특징으로 하는 방법.

#### 종속항 3-4

독립항 3에 있어서, 상기 방법은 기존 어텐션 연산의 커널 코드를 변경하지 않고, K, V 텐서의 입력 경로에서 facet 분해·양자화·역양자화를 수행하여, vLLM, TensorRT-LLM 등 기존 추론 엔진과 호환되는 것을 특징으로 하는 방법.
