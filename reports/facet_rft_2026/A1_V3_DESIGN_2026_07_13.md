# A1-v3 설계서 — 미구현 레버 전체 설계 (2026-07-13)

> ★A1-v2(3레버·~0.64) → A1-v3(전체 레버·ceiling ~0.72). 미구현 L2/L3/L4/L7/L9 설계 + 조합 아키텍처 + examined-safe↔GET-forcing 충돌 해소.
> 상위: `A1_IMPROVEMENT_DESIGN`(v2)·`REMEDIATION_DESIGN`·`GENERALIZED_SCAFFOLD_ARCHITECTURE`(LOCK GET→FIND→INFER→ASK).
> 불변: [[05]] 도메인일반·A2만 · [[10]] 선택기=결정론·NL→formalize=LLM · Δspurious≤0 · gold-independence.

## 0. 목표·스코프
- A1-v2 = examined-safe + reads-only + filter(order). ceiling의 일부만 실현(~0.64).
- **A1-v3 = A1-v2 + {L2 GET-forcing, L3 origin-prov, L4 fexec-variants, L7 precondition, L9 set-op}** = LOCK 아키텍처 완성.
- 격차 = 미구현 레버(learn/scale 아님). 진짜 learn/scale 잔여 = ~3-5 태스크(§6).

## 1. 통합 아키텍처 = GET→FIND→INFER→ASK 완성 (LOCK §4d)
per-operand 해소 루프. 각 레버 = 이 루프의 한 단계·operand만 다름:
```
operand(order|item|new_item|address|payment) 값 해소:
  GET   : A2 getter → 후보 생산 (order=user orders / new_item=product variants)   ← L2·L4-GET
  FIND  : formalize(criterion)+결정론 필터 → 1?치환 : ≥2?ASK : 0?재형식화          ← L1(order)·L4(variant)·L9(set-op)
  PROV  : 값이 grounded(출력∪발화) ∧ *에이전트-발명 아님*(first-mention)            ← L3
  GATE  : operator 전제(status·정책) 충족                                          ← L7 + 기존(auth/confirm)
  COVER : 요청이 span하는 record 전수 처리                                          ← eplan + L9
```
**⇒ A1-v3 = 이 루프를 order·item·new_item·address 전 operand에 완비.** 엔진=고정 인터프리터·A2=operand별 {getter,filter,gate,producer} 스키마.

### 1a. ★examined-safe ↔ GET-forcing 충돌 해소 (핵심 설계결정)
두 레버가 "examined 대상에 write" 상황에 정반대 처방 → **서로 다른 루프라 분리**:
- **examined-safe** = COVERAGE 루프(eplan): "요청이 여러 주문 span하나?" 대상 검토됐으면 span-deny 생략(t58 qty-conflation).
- **GET-forcing** = SELECTION 루프(disamb): "쓰려는 주문이 후보 중 *맞나*?" 후보 미조회면 조회 강제(t83).
- **통합 판별 규칙 (결정론)**: order operand에 **formalize 가능한 selection 기준**(op≠none = "더 비싼"·"내용X 든")이 있으면 → **SELECTION**(GET-forcing+filter·examined 무관·후보 비교 필수). 없으면 → **대상 examined면 충분**(examined-safe)·coverage=eplan.
  - t58 "이 2품목 바꿔"(order 기준 없음) → examined-safe. ✓
  - t83 "더 비싼 태블릿"(argmax price 기준 有) → GET-forcing+filter. ✓
- ⇒ **examined-safe를 "order-operand formalize op==none일 때만" 조건화**. 이 한 줄이 충돌 제거.

> **★리뷰 반박 (미해소·[[08]]·구현 前 필수 확인)**: 판별 규칙이 SELECTION과 COVERAGE를 **상호배타**로 처리하나(op≠none이면 examined-safe *전면 OFF*), 두 축은 **직교**다 — *선택된 한 주문 안에서* 다품목 examined-safe가 동시에 필요할 수 있다. 반례 후보: **"가장 비싼 주문의 파란 2품목 교환"** = order-operand op=argmax(total·retail 주문에 total 有 → most_recent와 달리 formalize *가능*) ∧ 그 주문 내 2품목 = examined-safe 필요. 규칙대로면 op≠none → examined-safe OFF → span-deny 재활성 → t58형 재파손. **검증 n=2(t58·t83)는 두 축이 *우연히 공기하지 않은* 케이스**(이 세션 반복 색출한 소표본 과대일반화·[[08]]). **구현 前 게이트: 114-set서 (order op≠none ∧ 다품목-examined) 태스크 전수 확인** — 존재하면 판별을 "operand별 독립"(선택은 order-식별에만·coverage는 items-span에만·한 태스크서 공존 허용)으로 재설계. 부재 실증되면 현 규칙 채택+범위-caveat 명기.

## 2. 레버별 설계

### L2 — GET-forcing (selection discovery)
- **문제**: filter가 후보 record <2면 폴백(t83·92·112 "틀린 주문만 조회"→filter 무효).
- **방법**: disamb이 order operand ≥2 후보 감지 ∧ formalize op≠none(selection 기준 有) ∧ 후보 중 **detail 미조회분 존재** → 열거-ASK 대신 **미조회 후보 order의 detail_reader 호출 강제**(read-deny·eplan-L2 동형·selection 목적) → 조회 후 filter 재시도.
- **트리거·상한**: order 후보≥2 ∧ op≠none ∧ unfetched 후보 有. sim당 GET-force cap(T2_GETFORCE_CAP·eplan_deny_cap 동형·루프 방지).
- **구현**: t2_gate_patch disamb 경로 — fexec_filter_decide가 "records<2 but ≥2 grounded 후보 존재" 반환 시 신규 status="need_get" → 배선이 미조회 후보에 detail-read deny 피드백. 신규 후크 0(기존 regen deny 재사용).
- **[[05]]**: 후보=user order list(grounded)·getter=A2 detail_reader·엔진 루프·리터럴 0.
- **대상**: 83·92·112(+69 부분). filter를 "다수조회"에서 "전 후보"로 확장.

### L3 — origin-provenance (first-mention 세탁 차단)
- **문제**: 주소 날조가 user-confirm laundering→prov(값∈ctx) 통과(t96 "123 Broadway" 발명→사용자 복창→통과).
- **방법**: 각 식별값의 **최초 등장 turn·role** 추적(index). write 시 값이 **assistant-first**(이전 tool출력·user발화에 부재) ∧ producer getter 존재 → prov-deny(getter 지목). **user-first(t43 "1234 S Michigan"=사용자 명시)=허용**(날조 아님).
- **구현**: `_ctx_from_messages` 확장 → `_origin_index[value]=(turn,role)`. prov 검사(`_first_fab_call`)에 origin 축 추가: 값∈ctx이나 origin=assistant ∧ getter존재면 fab 취급. toggle T2_PROV_ORIGIN=1.
- **turn-order 확증(2026-07-13)**: t96 first=ASSISTANT(msg18)·t43 first=USER(msg19) → 규칙이 둘을 정확 분리. **★리뷰 caveat**: n=2 확증 = 규칙 성립의 존재증명일 뿐 일반성 아님([[08]]). probe서 **origin false-positive 전수 필요** — 특히 (a) 에이전트가 getter 출력을 재진술한 값(§7이 "tool-first라 안전"이라나 *getter 호출이 write보다 늦은* 경우 write 시점엔 tool-first가 아직 아님 → 오탐 가능) (b) user가 assistant 추측을 확인한 정당 케이스(assistant-first지만 사용자 승인 = 날조 아님). Δspurious로 (b) 오차단 계측 필수.
- **[[05]]**: 보편 규칙(에이전트 값 발명 금지)·도메인 리터럴 0.
- **대상**: 96(+주소 날조류 일반).

### L4 — fexec-variants (변형 극값/속성 선택)
- **문제**: new_item_id 오선택 — "가장 줌 큰"(52)·"가장 큰 사이즈"(77)·"7in/128/black"(110).
- **방법**: fexec 엔진을 **product-variant record**에 적용. new_item_id operand 애매 시 get_product_details의 `variants`(item_id-keyed dict) 각각을 후보 record로 추출 → formalize("cheapest green"→filter(options.color=green)+argmin(price)·"max zoom"→argmax(options.zoom)) → variant item_id 선택.
- **variant 구조**: `variants[iid]={item_id, options:{color,zoom,size,...}, price, available}`. `_field_values` 점경로 `options.color`·`price` 각 variant 내 지원(기구현·재검 필요=variant는 dict-keyed라 후보추출만 신규).
- **구현**: `_candidate_record_dicts` variant 변형(`_variant_records`: get_product_details 출력의 variants→[(iid,record)]) + `available=true` 사전필터. fexec_filter_decide 재사용(op=argmax/argmin/filter). A2에 `variant_operand: new_item_ids`·`variant_producer: get_product_details`.
- **[[05]]**: variants=도구출력(grounded)·fexec 재사용·A2 스키마. 명시속성/극값만(의미매칭="버드워칭용 좋은"=learn 잔여·§6).
- **대상**: 52·77·110(+변형 명시분).

### L7 — precondition gate (도구-전제·정책)
- **문제**: 도구 오선택(t21 pending에 exchange→불가)·정책(t38 split-payment 불가).
- **방법**: A2 gate_spec에 preconditions 추가(**기존 kind·온톨로지 내**·엔진 무수정): exchange_delivered/return_delivered → `status==delivered` 요구(pending이면 deny+"modify 사용" 유도) · modify_payment split → 2 결제수단 금지(gift_card+1 예외).
- **구현**: `a2/retail.gate.json` gates[]에 precondition 항 추가(resolver_path=[order_id,get_order_details,status]). GateInterpreter 기존 preconditions 처리 재사용. **정책→gate_spec 도출**(LOCK make-or-break TODO의 첫 실사례).
- **[[05]]**: 정책=A2 데이터·고정 compliance-reader. 엔진 리터럴 0.
- **대상**: 21(exchange→modify)·38(split 거부→cancel).

### L9 — set-op coverage (집합-여)
- **문제**: "X 빼고 전부"(t108 "태블릿 빼고 전부 반품") item 집합-여.
- **방법**: formalize에 **complement op 추가**("all except X"→set-여). 대상 order.items − {지목 item} 결정론 계산→item_ids 채움. get_order_details items가 재료.
- **구현**: parse_formalize OPS에 "complement" 추가·execute_formalized서 order.items 전체−constraint-매칭 = 잔여 item_ids. (또는 coverage 헬퍼 별도.)
- **[[05]]**: items=order record(grounded)·NL→formalize=LLM·집합연산=엔진.
- **대상**: 108(+"except"류). 단 행동-선택(return vs cancel)분은 L7/learn.

## 3. 조합·예산·충돌
- **operand 라우팅**(엔진 결정론): order→L1+L2, new_item→L4, address→L3, payment→L3+L7, items→L9. 각 operand 독립·순서=GET→FIND→PROV→GATE→COVER.
- **예산**: GET-forcing/eplan-deny/prov-regen 각 sim-cap(루프 방지·기존 semantics 승계). 총 per-sim regen 상한 유지.
- **충돌 매트릭스**: examined-safe(coverage)×GET-forcing(selection) = §1a 규칙으로 분리. L3(prov)×L1/L4(filter) = prov 先(grounded 확인)→filter(선택). L7(gate)×전부 = gate 最後(replay-safe strip).
- **prov mode**: rescue 유지(무죄)·L3 origin은 mode 무관 추가 축.

## 5. 구현 순서·검증 (무료 先·[[09]])
1. **L4 fexec-variants** [최고 ROI·기존 fexec 재사용]: `_variant_records` + A2 variant_operand → 로컬 unit(변형 record서 argmax/filter) → probe(52·77·110).
2. **L2 GET-forcing** [order-selection 완성]: fexec need_get status + read-deny 배선 → 로컬 ledger unit → probe(83·92·112).
3. **L3 origin-prov** [주소]: origin index + prov 축 → turn-order unit(96 reject·43 allow) → probe.
4. **L7 precondition** [정책]: A2 gate_spec 추가 → 오프라인 gate unit(pending exchange deny) → probe(21·38).
5. **L9 set-op** [집합]: complement op → 로컬 unit → probe(108).
- 각 단계 격리 probe(회귀 표적 + trivial 무회귀 + Δspurious) → 통과분만 A1-v3 스택 편입. **전부 무료검증 先·유료 probe 승인**.

## ★8. A1-v3 ENHANCED — 0.92 목표 (frontier 바닥 전부 닫기·2026-07-13)

> **보강 원리: formalize-LLM 의존을 *결정론 추출*로 대체** → realization을 solvability(97%)에 밀착. 극값어·record-grounded 속성은 LLM 안 거침(0.79 병목 제거).

### 8a. 두 축 (혼동 방지·정본)
- **solvability ≈ 97-100%** (irreducible 0-3%: t106 표현애매·user-sim 이탈). frontier 바닥도 결정론이라 극복가능.
- **realization** = 32B+scaffold 실현치. scaffold=결정론 기계 100%정확·**모델이 운전(formalize/tool/loop)** = 병목. formalize 0.79(C44).
- **0.92 목표 = realization을 solvability에 밀착** — 보강은 "운전 정확도"를 scaffold-side 결정론화로 올림(learn 없이도).

### 8b. L4++ fexec-variants 강화 (극값·속성 결정론화 = 최대 ROI)
frontier 바닥 8중 5(t20·0·15·79·82)가 여기. formalize 우회:
- **L4a 극값어 결정론 사전** (도메인일반 닫힌영어): {most expensive·priciest·highest→argmax · cheapest·least expensive·lowest→argmin · largest·biggest→argmax · smallest→argmin} → LLM formalize 없이 op 확정. field = variant record의 **숫자 option 필드**(price·zoom·size·capacity) 중 극값어-정합(price가 기본·"zoom"명시 시 zoom). t20 "most expensive"→argmax(price) 4품목 각 결정론(frontier가 근사로 틀린 것을 정확히).
- **L4b record-grounded 속성 매칭** (LLM 지식 불필요): filter 제약값(green·clicky·8·1-liter·RGB)은 **요청 토큰 ∩ variant option 값** 결정론 교집합. record가 `options.color:green` 담으므로 "green=색"을 모델이 알 필요 0 — 요청에 등장 ∧ 어느 variant option-값에 등장 = 제약. t0(clicky·RGB·fullsize)·t15(8)·t79(1-liter) 결정론.
- **L4c available 사전필터 + fallback 조건**: `available=true`만 후보. t0형 "없으면 no-backlight" = 1차 filter 공집합→제약 완화 재filter(요청 명시 fallback 순).
- **동률·0통과→enumerate-ASK**(안전). 잔여 LLM formalize = 극값도 속성도 아닌 복합기준만(대폭 축소).

> **★리뷰 [R5·중대·L4b 충돌] 짧은/숫자 제약값 = 표면-교집합 오탐 폭발.** "요청 토큰 ∩ option 값"은 `green`엔 안전하나 **t15 "8"이 정확히 위험**: "8"은 options.size:8 · options.count · price에 포함된 8 · item_id의 8 전부와 충돌. 이 세션 CENSUS §1이 이미 확정한 교훈 = **숫자 토큰은 field-타입 exact-match 필수·substring/set-교집합 금지**. L4b는 그 트랩을 재도입 — **필드-타입 제약 교집합**(요청 "8"이 *어느 옵션-키의 값 타입*과 정합하는지·색상어는 color-키만·수치는 명시-단위[size/capacity] 키만)으로 강화. FP 가드가 §8g의 명시된 유일 리스크인데 **가장 약한 지점이 숫자**임을 못박고 probe에서 숫자-제약 태스크(t15) FP 전수.

### 8c. L2++ GET-forcing 완전화 (order선택 t72·109·82)
- selection 기준(op≠none) 有 ∧ 후보 order 미조회분 존재 → **전 후보 detail 조회 강제**(write 보류)·완료 후 L1 filter. frontier가 틀린 주문(t72 #W5782623·t109 #W1092119) 선택을 후보 비교로 교정.
- 후보 order도 L4b 속성 매칭 적용(주문 내용으로 선택·"backpack 든 주문").

### 8d. Coverage 완전화 (t41·eplan+)
- 요청이 span하는 record 전수 처리 확인. t41=2주문 주소변경 중 1 누락 → eplan coverage-walk(현 off)를 **읽기-완료형으로** 켬(write 강제 아님·미처리 span 리마인더). L9 set-op와 결합("전부"·"각각").

### 8e. Formalize 경화 (realization 보강·learn 전 scaffold-side)
- **self-verify**: 형식화 op의 field가 record에 존재 ∧ 값 타입 정합 아니면 재형식화(malformed 차단).
- **re-formalize 루프 상한↑**(현 1→2-3)·최종 실패→enumerate-ASK.
- **(선택) ensemble formalize N-vote**: 극값/속성 결정론화로 대부분 우회되나, 복합기준 잔여엔 N=3 consensus로 0.79→↑.
- ⇒ formalize 잔여 의존 최소화 = realization이 solvability에 근접.

> **★리뷰 (0.92 보강·4건·구현 前 게이트)**
> **[R1·중대] L4a는 op는 닫으나 *field*는 안 닫는다 = 결정론 미완.** 극값어 사전 {expensive→argmax}은 **연산자**만 닫힌-영어로 확정한다. 그러나 극값의 *대상 필드*는 열려 있다 — "**largest** backpack"=argmax(capacity? dimensions?)·"**biggest** TV"=argmax(screen? price?)·"**expensive**"조차 price vs 상위-tier 애매. §8b의 "극값어-정합 숫자필드(price 기본·zoom 명시시)"는 field 선택을 **다시 LLM/휴리스틱에 위임** = formalize 병목이 op에서 field로 *이동*했을 뿐 제거 아님. **폐쇄 조건: 8 태스크 각 극값어→유일 숫자필드 매핑을 전수 표로 증명**(다중 숫자필드 존재 시 field-선택이 formalize로 잔존함을 인정). op-결정론화의 실질 이득분과 field-잔여를 **분리 계상**.
> **[R2·중대·gold-fitting] 사전이 eval서 역산되면 도메인-타깃(=[[11]] 위반).** "닫힌 영어 사전"은 **영어 의미서 사전등록**될 때만 도메인-일반 — 8 바닥 태스크의 gold를 보고 극값어·field를 채우면 retail-eval 과적합(τ²/banking 미전이). **게이트: 사전을 eval-blind로 고정(영어 극값어 일반 목록)→그 뒤 8-태스크 커버리지 측정**. 커버리지가 사전-후 낮으면 그게 정직한 realization.
> **[R3·중대·정직] 0.92는 A1-v2가 방금 실증한 gap-누수를 무시한다.** A1-v2 = 자기 설계 ceiling ~0.72 대비 **0.62~0.64 실현**(≈8~10pp 누수·원인=eplan 과발화·prov 최소낙폭·present 회귀). 0.92 투영은 **"이번엔 누수 없다"의 무근거 가정** — 누수-비재발 *기전*을 명시하지 못하면 0.92는 [D] 목표지 [M] 경로 아님. §8f "frontier 초과"·"완전결정론"은 **realization 미측정 상태의 declarative** → **[진행]/[D] 등급 강등 필수**([[40]]). 8f 표 헤더에 "예측·probe 前" 명기.
> **[R4·중간] "frontier 4모델 바닥"의 floor 강도.** n=4가 어느 4인가(retail 챔피언 qwen3.5-397b 0.855 [[47]] 포함?)·4-모델 실패가 **universal-fail인가 mid-tier 표본**인가. 챔피언도 8/8 실패 확증 없으면 "frontier 초과"는 과대(챔피언이 일부 통과 시 "초과"가 아니라 "일부 frontier 수준"). banking universal-fail이 17-18모델×trial이었던 기준([[47]]) 대비 4-모델은 약함 — floor 집합을 챔피언-fail로 재확증.

### 8g. 0.92 realization 경로 (정직)
- A1 0.62 → +L4++(변형 argmax/filter·~+6-8) +L2++(order·~+5-7) +coverage(~+3-4) +L3(prov·~+1-2) +L7(precond·~+1-2) → **~0.85-0.90**(formalize 0.79 잔여 갭).
