# 요구-원장(demand_ledger)과 오늘 실측의 합류 — 설계는 옳은 형태였고, 값은 등재가 아니라 그 다음에 있다

> 2026-08-20 밤 · 사용자 지시 *"1,2,3 순으로 하라"* 의 3
> 선행 정본 `DECLARATION_FIRST_REDESIGN_2026_07_29.md` §1d(rev3·**구현 대기**) · 오늘 실측 = **C555**
> ⛔이 문서는 **설계 합류·판정 정리**다. 라이브에 한 줄도 넣지 않았고, [[62]] 순서를 밟기 전에는 넣지 않는다.

## 0. 한 줄

§1d 의 `demand_ledger` 는 **`emit: 유저 턴마다 append-only`** 라고 이미 못 박아 두었다 — 오늘 격리가
**정확히 그 형태만 요구를 회수한다**는 것을 실측했다(전 문맥 1회는 055 에서 요구 0개). 즉 설계는 옳은
자리를 짚었고 오늘 처음 **경험적 근거**가 붙었다. 그러나 같은 실측이 두 번째 사실도 말한다:
**등재를 고쳐도 성적은 안 산다** — 회수된 요구가 다음 단계(술어 표현·전달)에서 죽는다.

## 1. 지금 있는 것과 없는 것 (전부 직접 확인)

| 조각 | 상태 | 근거 |
|---|---|---|
| 요구 **등재**(인용 근거 + 원문 실재 검산) | **라이브에 있다** | `t2_search.sub_requirements()` · 검산 `quote_in()` |
| 원장 자체(턴 간 누적·`demand_id`·status) | **없다** | repo 전수 grep: `demand_ledger` 히트 전부 **마크다운**, 코드 0 |
| R7 DONE-게이트 | **라이브에 없다** | `t2_declfirst.verify()` 는 5규칙만 |
| R7 의 유일한 구현 | **프로브 전용·상수** | `x3_decl_comp.py` 의 `OPEN_DEMANDS = {"d1"}` = 모듈 상수 |
| `resolves`(원장 링크 필드) | 스키마에 **있으나 소비자 0** | `a2/base/shared.json` 에 선언·엔진 독자 없음 |

⚠**R-번호 충돌**: 설계서 §1d 의 R4·R2·R13 과 라이브 `t2_declfirst` 의 같은 번호는 **다른 술어**다.
어느 쪽 R-id 든 **출처를 병기하지 않으면 오독**이다.

⚠기존 *"R7 4/4 검출"*(X3)을 **요구-원장 검증의 근거로 인용하면 사실이 아니다** — 상수 하나를 보고
DONE 발화만 잰 것이고, 등재(`quote ∈ utterance`)·소거(R11)·번복(R12)은 잰 적이 없다.

## 2. C555 가 설계에 보태는 것 — **등재 시점**이 결과를 가른다

```
task_055 · 같은 모델 · 같은 프롬프트 · 같은 표
  전 문맥 한 덩어리(A_full)     → 요구 **0개**   (셋 다 `question` 으로 선언)
  손님 턴 하나씩(B_turn)        → 요구 **3개**   (인용 근거가 전부 **뒤쪽 턴의 평서문 재진술**)
```
전 문맥 판은 첫 언급(의문문)에 정박해 **뒤에 나온 재진술을 안 쓴다**. §1d 가 `emit` 을 *"유저 턴마다
append-only"* 로 못 박은 것은 이 실패를 구조적으로 피하는 형태다 — 오늘 그 형태가 **유일하게 작동하는
형태**임이 실측됐다.

★단, 부정통제가 범위를 좁힌다: 뜻과 무관하게 **글자 수로 N등분**한 팔도 회수한다 ⇒ 이득의 정체는
*턴 경계*가 아니라 **한 번에 보는 양**이다. 대신 아무 데나 자르면 **오추출**을 산다(063 t0 전멸·055 잔고를
ATM 한도로 오귀속). ⇒ 원장이 **턴 경계**를 쓰는 것은 부정통제를 통과한 선택이다.

## 3. 그러나 등재를 고쳐도 성적은 안 산다 (오늘의 두 번째 사실)

```
055  요구 3개 회수 → 다운스트림 **생존 0**(gold 탈락)   ← "no FX fee" 를 `absent` 로 썼는데 gold 는 값 0%
     이접(OR) 어휘를 스키마로 주면?  → 모델이 **한 번도 안 쓴다**(x438·8 사례 전수 확인 중·현재 0)
024  요구 0개 → 2개(정당한 `business` 포함) → 13 → 9 로 좁힘 (gold 유지)
```
⇒ 원장이 요구를 **정확히 담아도**, 그 요구를 표에 거는 **술어 표현**과 **적격 집합의 전달**이 막혀 있으면
성적은 그대로다. 값이 있는 자리는 등재가 아니라 **그 다음 두 자리**다.

## 4. R7(DONE 게이트)에 붙는 경고 — 이 축의 실측 이력은 나쁘다

R7 은 *"열린 요구가 남아 있으면 DONE 금지"* 다. 이것은 **게이트**이고, 이 프로젝트에서 게이트 축의 실측은
반복적으로 부작용을 냈다:

```
[[06]]  over-action = **게이트 금지 축**(선례)
C492    `T2_ACT_DEMAND`(행동 촉구) 라이브 A/B — 1차 종점 9/20↔12/20(차 3 < 잡음 바닥 ⇒ 인용 불가)
        · reward 8/20↔9/20(합 null) · **over-action 2 → 8**(차 6·인용 가능) ⇒ 로스터 판정 **HARMFUL**
C453    formalize 프롬프트에 케이스 한 줄(*"still asking questions … → none"*) = judge6 **−6**
```
⇒ R7 을 켜려면 **Δspurious(부작용) 계측이 종점과 동급**이어야 한다([[70]]·등대 §1.3). 설계서 자신도
1차 마일스톤을 **검출 전용**(`ENFORCE=0`)으로 잡아 두었다 — 그 순서를 지킨다.
