# 파생-사실 DAG — 계산을 **언제** 하는지를 코드가 아니라 선언이 정한다

## §0 왜 — 하루에 **세 번** 같은 실패를 했고, 셋 다 침묵이었다

전부 *"파생 사실을, 그 입력이 갖춰지지 않은 지점에서 계산했다"* 이다.

| 파생 사실 | 입력이 실제로 있던 곳 | 우리가 계산한 곳 | 증상 |
|---|---|---|---|
| 오늘 날짜(`now`) | 대화 **첫머리**(`The current time is …`) | 꼬리 8개 발췌 | 경과일 문장이 **빈 문자열로 렌더** |
| 유형별 상한(`limits`) | 대화 **중반 이후**(문서 회수 시점) | **원장 read 시점**(그 전) | 추출 0 → 빈손을 sim 내내 메모 |
| 관계기간 문턱(`thresholds`) | **계좌 선언** | 마지막 선언 하나로 덮음 | 추출 **0회**(로그 한 줄도 없음) |

셋 다 예외를 던지지 않았다. **레버가 켜져 있고, 배선이 살아 있고, 아무 말도 안 했다.**
그리고 셋 다 *"성공만 인쇄"* 하는 계기라 한동안 보이지 않았다(오늘 `seen=N` · `model gave N` ·
`accepted/rejected` 를 연달아 추가한 이유).

★**이것은 버그 셋이 아니라 결함 하나다.** 지금 구조에서는 *"이 계산을 어느 훅에 넣을까"* 를
사람이 매번 고르고, 그 선택이 **암묵적이고 검증되지 않는다.** 건바이건이 되는 이유가 그것이다.

## §1 선언 계약 — A2가 **의존성**을 말한다

```jsonc
"derived": [
  {"out": "tenure_days",  "inputs": ["read:accounts"],                 "op": "days_since_earliest"},
  {"out": "type_usage",   "inputs": ["read:referrals"],                "op": "tally"},
  {"out": "window_left",  "inputs": ["read:referrals", "today"],       "op": "window_remaining"},
  {"out": "doc_limits",   "inputs": ["corpus"],   "op": "formalize", "prompt": "limit_prompt"},
  {"out": "doc_minimums", "inputs": ["corpus"],   "op": "formalize", "prompt": "threshold_prompt"},
  {"out": "annual_left",  "inputs": ["type_usage", "doc_limits"],      "op": "subtract_by_group"},
  {"out": "tenure_ok",    "inputs": ["tenure_days", "doc_minimums"],   "op": "compare_ge"},
]
```

- `read:<name>` = 그 선언의 `trigger_tool` 가족이 **성공 실행**되면 만족(기존 `specs_for` 재사용)
- `corpus` = 이 대화에서 회수된 tool/user 텍스트 — **언제든 늘어날 수 있는 입력**
- `today` = 이미 있는 `now_prompt` 노드
- `op` = **닫힌 집합**(§2). 새 op는 설계 리뷰 트리거

문구(`text`)는 노드에 붙고, 지금처럼 A2가 소유한다. **엔진은 이름과 수만 채운다**([[05]] Q2).

## §2 엔진이 하는 일 — 스케줄링 + 닫힌 산수, 그뿐

```
매 발화 지점에서:
  1) 갱신된 입력이 있는가            (read 실행 / corpus 증가 / today 확정)
  2) 갱신으로 **계산 가능해진** 노드를 위상순으로 평가
  3) 값이 바뀐 노드의 문구만 표면화 (같은 값이면 침묵 — `admit()` 재사용)
  4) 계산 못 한 노드는 **이유와 함께** trace 에 남긴다
```

현재 엔진이 아는 op는 셋뿐이고 그게 전부다:

| op | 하는 일 |
|---|---|
| `tally` / `window_remaining` | 그룹 카운트 · 롤링 창 잔여 |
| `days_since_earliest` | 최초 일자 → 경과일 |
| `subtract_by_group` / `compare_ge` | 상한−누계 · 경과일≥문턱 |
| `formalize` | **LLM 노드** — 프롬프트를 던지고 `{키:{수, 인용}}`을 받아 **인용 실재만** 검증 |

⚠`formalize`가 유일하게 LLM을 부르는 op다. 나머지는 순수 산수다. 이 경계가 [[52]]
**엔진=이론 / LLM=해석**의 코드상 표현이고, [[59]](엔진이 도메인 텍스트를 읽지 않는다)의 집행점이다.

## §3 기존 기구와의 관계 — **새 병렬 기구를 만들지 않는다**

| 이미 있는 것 | 무엇을 하나 | 이 설계와의 관계 |
|---|---|---|
| `t2_precedence.graph_for` | **행동**의 DAG(무엇 다음에 무엇) | 그대로 둔다. 이 설계는 **사실**의 DAG로 직교 |
| `ledger_metrics` | 두 선언 안에 계산·문구·프롬프트가 뭉쳐 있음 | **흡수된다** — 노드로 분해하면 같은 것을 더 작게 말한다 |
| E-PLAN / TRACK-A per-step DAG | 실행 계획의 결정론 컨트롤러 | **같은 계보** — 합쳐야 하고, 따로 만들면 또 하나의 병렬 기구가 된다([[03]] 샛길 금지) |
| `t2_stack.speak()` | 발화의 단일 출구(창→층→자격→합병→버스) | 표면화 단계는 **그대로 speak()를 쓴다** — 이 설계는 *무엇을 말할지*까지만 정한다 |

⇒ 순증이 아니라 **재배치**다. `ledger_metrics`가 노드 목록으로 바뀌고, 계산 지점이 코드에서 선언으로 옮겨진다.

## §4 ★[[05]] 3질문 (필수 섹션·[[17]])

**Q1. scaffold 또는 A2의 도메인-특화를 순증시키나?**
A2는 **재배치**다 — `ledger_metrics`의 프롬프트·문구가 노드로 흩어질 뿐 총량은 늘지 않는다.
새로 드는 것은 `inputs`/`op` 선언(노드당 두 필드)이고 **상품 수에 비례하지 않는다**([[50]] ADB).
엔진 쪽은 오히려 **줄어든다** — 오늘 손으로 배치한 훅별 계산 코드가 스케줄러 하나로 대체된다.
⚠단 정직하게: **op 집합은 이 도메인의 정책을 보고 골랐다.** 어휘는 일반이지만 **규칙형은 일반이
아니다**. 다른 규칙형을 쓰는 도메인은 새 op를 필요로 하고, 그건 리뷰 트리거로 남긴다.

**Q2. 모델이 할 수 있는 유동적 판단을 결정론에 동결하나?**
아니다. 노드가 내는 것은 **사실**(잔여 수·도달 여부)이고 **추천이 아니다**. 어느 문서의 어느
문장이 상한인지는 `formalize` 노드가 **모델에게** 묻고, 엔진은 인용 실재만 확인한다.
선택은 그대로 모델 몫이며, 현행 문구가 이미 *"not a recommendation"* 을 명시한다.
⚠새로 동결되는 것이 하나 있다: **"언제 계산하는가"**. 그것은 지금 사람이 정하던 것이고,
선언으로 옮기는 것이 이 설계의 목적이다.

**Q3. scaffold가 모델 대신 도메인 행동을 수행하나?**
아니다. 노드는 **도구를 부르지 않는다.** `read:<name>`은 조건이지 명령이 아니고, 미충족이면
그 하류가 계산되지 않을 뿐이다. autofetch류 절차 offload와의 차이가 여기다.

## §5 계측 — 침묵이 보이게 하는 것이 이 설계의 절반이다

오늘의 교훈은 *"성공만 인쇄하면 못 찾았다와 안 돌았다가 같아 보인다"* 였다. 그래서 스케줄러는
**매 평가에서 노드별 상태를 남긴다**:

```
[T2_DAG] annual_left    = 미계산 (doc_limits 없음: corpus 에서 0종 추출)
[T2_DAG] tenure_ok      = 계산   (65 vs {HG 60, WB 90}) → 표면화 1건
[T2_DAG] window_left    = 불변   (2) → 침묵
```

판정 지표(다음 런의 1차):
- **미계산 노드 0** 이면 배치 결함이 없다 — 오늘 세 버그는 전부 여기서 잡혔을 것이다
- 표면화 건수 · 값 변화 건수 · `Δspurious`(제출 수 증가 여부)

## §6 위험 · 비-목표

- **위험 1 — 워크플로 엔진 재발명.** 계약을 `out`/`inputs`/`op`(+`prompt`) 넷으로 못 박는다.
  조건 분기·루프·우선순위는 **넣지 않는다**(그건 `route()`/`speak()` 소관).
- **위험 2 — LLM 노드의 재평가 폭주.** `corpus` 입력은 계속 늘어나므로 매 턴 재질의하면 비용이
  는다. 규칙: **입력 지문(회수 문서 수)이 바뀐 때만** 재평가하고, 성공한 값은 유지·**빈손은
  기억하지 않는다**(오늘 실측한 사고).
- **위험 3 — 표면화 증가가 과행동을 부른다.** 101은 이미 제출을 3~5건 초과한다. 노드가 늘면
  말이 늘고, 등대 GO 조건 `Δspurious ≤ 0`을 위협한다. ⇒ **표면화는 `speak()`를 지나야 하고**
  값 불변이면 침묵한다.
- **비-목표**: 무엇을 고를지 정하는 것 · 도구를 대신 부르는 것 · 규칙형 일반화.

## §7 단계 · 판정 게이트

| 단계 | 내용 | 비용 | 게이트 |
|---|---|---|---|
| 0 | `ledger_metrics` 현행 4계산을 **노드로 재서술**(거동 동일) | 무료 | 오프라인 산출이 현행과 **바이트 동일** |
| 1 | 스케줄러 + `[T2_DAG]` 계기 (표면화는 아직 현행 경로) | 무료 | 오늘 세 버그를 **재현 실패**시킬 수 있는가(회귀 테스트 3건) |
| 2 | 표면화를 `speak()`로 일원화 | 무료 | `admit()` 접힘 · 미계산 노드 0 |
| 3 | 라이브 4 sim | 유료 | 미계산 0 · Δspurious ≤ 0 · 발화 귀속 100% |

⚠**단계 0을 건너뛰지 않는다.** 거동을 바꾸기 전에 같은 값을 내는지부터 보여야 한다 —
오늘 배선 셋이 전부 *"바꾸고 나서 안 돌던 것"* 이었다.

## §8 미해결 (설계 리뷰에서 답해야 할 것)

1. `corpus` 노드의 **변화 감지 단위** — 회수 문서 수인가, 도구 메시지 수인가, 내용 해시인가.
   (내용 해시는 엔진이 텍스트를 만지는 냄새가 있다 — 개수/식별자 쪽이 [[59]]에 안전)
2. `read:<name>` 충족을 **실패한 호출**과 어떻게 가르나 — `failure_markers`가 이미 있지만
   그 판정을 노드 조건에 넣으면 A2 두 곳에 같은 지식이 생긴다.
3. E-PLAN / TRACK-A와의 **합병 지점** — 행동 DAG와 사실 DAG를 한 그래프로 볼 것인가,
   두 그래프로 두고 사실 노드가 행동 노드의 선행이 될 수 있게만 할 것인가.
4. op 집합을 늘려야 할 때의 **승인 절차** — §5.6 코드 규칙(새 코드는 설계 리뷰 트리거)과 정합시킬 것.
