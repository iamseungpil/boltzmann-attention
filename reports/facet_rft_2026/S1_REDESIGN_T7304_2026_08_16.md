# S1 재설계 — t7304: 결정-자리 배달 **객체** 교체 (2026-08-16)

> 선행 = t7303(원장 **C502**·인과 확립 실패: 전달 8/12·종점 순환·"선택 불변" 반증).
> 이 문서가 t7304 의 권위본이다. 판정 순서·중단 조건은 **발사 전 이 문서로 고정**된다.
> 상태: **초안 → 리뷰(설계 4안 + 심사 3인 워크플로 + 자체 감사) → 확정** 후 발사.

## §0 t7303 이 남긴 것 (설계 입력·전부 실측)

1. **결손은 능력이 아니다**: 유효 문서 본문을 주면 격리에서 **24/24**(x335b) · 부정통제 0/24.
   라이브 같은 자리 0. ⇒ 레버는 **전달뿐**([[62]]②).
2. **라이브 결정 자리에 실제로 배달되는 객체는 서브의 결정문 247자**이고, t7303 로그 직독으로
   **그 결정 자체가 오답**이다 — 055 양팔 모두 `DOCDECIDE → 'Blue Account'`(gold Purple) ·
   `→ 'Gold Account'`(gold Silver Plus). 문서 본문(50,421자)은 단일 슬롯 덮어쓰기로 **한 번도
   결정 자리에 도달한 적 없다**.
3. **t7303 의 유일한 유의 차이는 시점이 아니라 부피**(>5k 부착 0/12 → 8/12). 그리고 부피가
   실제 도달한 두 태스크(024·098)에서 같은 seed 짝의 최종 선택이 **오답→gold 로 갈렸다**
   (024#s1567 Gold→Bronze · 098#s1567 Dark Green→Blue·후자는 바이트 동일 검색 결과 위에서).
   n 이 작아 수치 인용은 금지 — **가설로만** 승계한다.
4. 종점 규율: 처치 팔에서만 찍히는 마커는 종점이 될 수 없다([[55]] 갱신).
5. 한도: `--max-model-len 44672`. 문서군 본문 37k~50k자 ≈ 9~12k tok. 후반 프롬프트는 38k tok
   까지 간다. t7303 treat 에서 CWE 5건(전부 055#s373753) — **가드 없이는 재발한다**.

## §0b ★리뷰 검증 (2026-08-16 밤·사용자 리뷰 ①~⑥ 을 t7303 원자료로 전수 확인)

**① CONFIRMED (8/8) — 기존 배달 자리는 결정 자리가 아니다.**

| 축 | 배달 turn | 손님이 요구를 진술한 msg | 간격 |
|---|---|---|---|
| checking | **2** (8/8) | **3** (8/8) | +1 |
| savings | **6** (7/8) · 16 (1/8) | 23·39·69·37 / 34·40·7·59 | **중앙 +29.5** |

⇒ 배달이 **8/8 전부 요구보다 먼저** 끝난다. 재료는 한 턴만 사니 결정 순간엔 없다.
⚠검증이 리뷰보다 더 나아간 지점: **checking 축도 요구보다 1 앞선다**(리뷰는 checking 을 정합으로
봤다). 즉 "savings 만 정보-빈약"이 아니라 **정도 차이**다 ⇒ 종점만 checking 으로 바꾸는 것으로는
부족하고 **배달 자리 자체를 옮겨야 한다**. → §2 재설계의 근거.

**③(b) PARTLY_CONFIRMED — 제수 3 은 과소추정.** t7303 커밋 생성호출 **472건**의 `usage.prompt_tokens`

오버헤드 O(system+도구 스키마+chat template) = p50 **10,157**·p90 11,069 tok 이 빠져 있었다 ⇒
`est=C/3` 이 실제 토큰보다 작다(**463/463**). 실사고는 0건이었으나 마진이 ≈0 이었다(pt=38,128 콜).
→ 가드를 `C/3.5 > CAP−11,000` 로 교체(발화점 C≈85.6k자).
⚠trace 에 `prompt_tokens` 가 **없어서** 결과 json 의 `messages[].usage` 로 쟀다(계기 대체).

**④ CONFIRMED — 024 = 정답 앵커 제거 대비군.** ctl 024 `DOCDECIDE` = gold **4/4**(최종 write gold 2/4),
055 `DOCDECIDE` = gold **0/12줄**(`Blue Account`·`Gold Account`뿐·`Purple`/`Silver Plus` 등장 0).
⇒ 서브 결정문은 024 에서 **정답**, 055 에서 **오답**. 해석 규칙 사전등록: **055↑ ∧ 024↓ 면
"문서 < 정답 결정문"** 이므로 즉흥 하이브리드 금지·별도 설계로 넘긴다.

**⑤ CONFIRMED (수치) — 단 사인이 둘로 갈린다.** `T2_DECIDE_BEFORE_WRITE` 발화 **0/0**(양팔) ·
`WRITE_ARG_ENUM` 동봉 **2/2**(양팔·전부 055). ⚠DBW 가 0 인 이유는 "모델이 안 걸려서"가 아니라
**write 집합이 이 태스크군의 write 를 안 담아서**(구조적 0) — [[55]] 오진 방지. 이것이 §2 가 고치는 것.

**⑥ CONFIRMED — ctl 3번째 검색 발화는 4/4 오군**(credit_cards 2·business_checking 1·general 1),
출처는 엔진이 아니라 **모델이 `DOCGROUP raw=` 에 스스로 넣은 이름**. treat 는 오군 발화 0/4(예약 1).
⇒ ⓔ 에 오군 부착↔write 교차표 상설.

## §1 가설 (반증 가능한 형태로)

> **H**: 라이브 선택 실패는 *격리를 통과시킨 객체(유효 문서 본문)가 **모델이 값을 확정하는
> 순간**에 문맥에 없기 때문*이다. 그 객체를 **선택을 담은 write 시도 지점**에 놓으면
> 최종 제출 클래스가 gold 로 이동한다.
>
> **반증 조건(정밀화·리뷰 ②)**: 문서가 그 자리에 실제 부착됐고(ⓐ 통과) **그 부착 생성에서
> 모델이 텍스트로 값을 말했는데도**(ⓒ 분류) 최종 제출이 안 움직이면 H 기각. 부착 생성이
> `tool_call`-only 였다면 그것은 *"문서를 읽고 말할 기회가 없던 자리"* 이지 H 기각이 아니다 —
> 결론은 **자리(비커밋 1회)의 실패**로 적고 사다리의 다음 칸을 지정한다.

## §2 처치 — 배달 **자리**를 결정 자리로 옮긴다 (`T2_DOCS_AT_WRITE=1`·기본 OFF)

t7303 은 *객체*(결정문 → 문서)를 바꿨고, 이번엔 §0b①이 보여준 대로 **자리**까지 옮긴다.

| | ctl | treat |
|---|---|---|
| 배달 자리 | 검색 서브 발화 지점(turn 2·6) | **선택을 담은 write 시도 지점**(1회) |
| 배달 객체 | 서브 결정문 243~263자 | **유효 문서 본문**(중앙 스위치가 `decide=False` 강제) |
| 예산 | 총 3 | **총 3 불변** — 이른 자리를 **비우고** 옮긴다(늘리지 않음) |
| 문서군 선택 | LLM | 동일 |
| 최종 선택 | 모델 | 동일(write 는 1턴 유예 후 **모델이 다시 낸다**) |

**write 집합의 출처 = A2 가 이미 선언한 선택-인코딩 write**(새 A2 키 0·엔진 리터럴 0):
`choice_grounding[].tool` ∪ `recommendation_verify.action_tool`.
오프라인 확인: 플래그 ON 이 더하는 것은 정확히 **2종**(계좌 개설·카드 신청)이고 인증·조회·
부정통제 태스크의 write 는 **안 걸린다** ⇒ 통제 보존.

**컨텍스트 가드(소비 지점 한 곳·실측 보정)**: `(_hist + len(_cp2)) / 3.5 > 44672 − 8192 − 1024 − 11000`
이면 부착을 건너뛰고 `[T2_DOC_DELIVERY] skipped` 기록. 축약·선별 0([[62]]③). 근거 = §0b③(b).
⚠**가드 skip 시에도 축은 이미 소비된다**(`_done.add` 가 재료 생성 시점에 실행) — 의도한 동작으로
사전 명시하고, skip 수를 ⓔ에 계상한다.

**대용량 anti-clobber**: 미소비 ≥10k 배달물은 덮어쓰지 않고 이어붙임(`[T2_CP2_APPEND]`).

**부수 변화(정직 명시)**: ⑴ 이 처치는 **객체+자리 복합**이다 — 자리만 바꾼 팔은 §0b①에 의해
이미 무의미(그 자리엔 문서가 안 온다)하고, 객체만 바꾼 팔은 t7303 tag i 로 확인 시작했다가
중단했다. 기전 귀속은 ⓒ 분류 + GO 시 wave-2 로 산다. ⑵ write 1턴 유예가 붙는다(기존 DBW 기구·
sim 당 1회). ⑶ 재제시 채널은 실측상 얇다(§0b⑤: ENUM 2/2·DBW 0/0).

## §4b ⚠발사 후 스모크 관측 (2026-08-16 20:06~20:31·**사전등록 문구를 바꾸지 않고 기록만 한다**)

배선은 작동하는데 **배달 채널이 내가 가정한 것과 다르다**. 로그 축자(treat·turn=8):

```
[T2_SEARCH_AGENT] group=checking_accounts … 문서-only 반환 50421자
[T2_DECISION_CARRY] 결정 값을 체인 밖 뷰 채널로 (target=call_discoverable_agent_tool · 50421자)
[T2_DECISION_CARRY] 이 턴 재생성 버퍼에 부착 (50421자)
```

- 문서 본문이 **모델이 write 도구를 겨냥한 턴**에 붙었다(요구 진술 msg 3 **이후**) ⇒ 설계 의도
  (요구 뒤·write 겨냥 시점)와 부합. 다만 그 일을 한 것은 내가 넣은 write-hold(DBW)가 아니라
  **기존 뷰 채널**(`_m3` 자리)이다.
- 25분 시점 계수: treat `문서-only 2` · 대용량 부착 1 · **guard skip 1**(둘째 배달은 한도로 건너뜀·
  기록됨) · ON_PROCEED **0**(비움 성공) · CWE 0. ctl ON_PROCEED 11 · 부착 247/243/4536자 · CWE 0.
- **판정에 미치는 영향**: ⓐ의 *1차* 기준(treat 대용량 부착 ≥1 ∧ ctl 0)은 그대로 유효. 반면
  보조 기준으로 적어 둔 `hold > 0` 은 **0 으로 끝날 수 있다** — 그것은 처치 실패가 아니라
  *다른 채널이 먼저 날랐다*는 뜻이다. ⇒ 판정 시 **어느 채널이 날랐는지 사실대로 적고**,
  보조 기준 미충족을 ⓐ 실패로 읽지 않는다. (사전등록 문구는 고치지 않는다 — 사후 유리한
  재해석 금지. 이 관측을 여기 남겨 판정 때 함께 읽는다.)
- ⚠파생 물음(다음 설계용): 뷰 채널이 write 겨냥 턴에 이미 배달하고 있었다면, t7303 ctl 에서도
  같은 채널로 **결정문 4,536자**가 갔다. 그렇다면 이번 대조의 실질은 *"같은 자리에서 객체만
  결정문→문서 본문"* 일 수 있다. ⓒ 기전 분류로 확인한다.
