# 값-grounding placeholder 학습 설계 — FIND/GET/COMPUTE/ASK 외 값 주입 금지 스킬 (2026-07-17)

> 사용자 제안: *"record grounding을 포함한 모든 값 인용은 FIND(사용자/정책)·GET(도구)·ASK(사용자)·COMPUTE 외에는
> 값을 못 집어넣게 **placeholder를 학습**할 수 있나?"* — **가능·이것이 [[16]] 유일 잔여 learn(INFER-calibration)의
> 일반화 완성형.** 파생: C92(연산 오분류 통일이론)·C104(learn-wing 처방)·이 세션 실패 5종(§19·§14.3).
> 규율: [[11]] 학습벤치서만·ABox-swap 전이 / [[12]] 다양성 / C38·C42 데이터 타당성 게이트 / [[42]] prompt 무효의 귀결.

## 1. 학습 목표 행동 = 값 슬롯의 타입 규율
모든 값 슬롯(도구 인자·사용자-대면 주장)에서 허용되는 emit은 5가지뿐:
`FIND`(문맥 그대로 복사) · `GET`(산출 도구 호출) · `COMPUTE`(계산 도구 호출) · `ASK`(질문) ·
★**placeholder**(위 넷 불가 시 — 예: `{"__source":"ASK"}` / `<UNKNOWN:field>`) — **날조 대신 낼 대체 행동을 설치**.
- 채널 논리: 금지("하지 마라")=억제 채널=무효(C30/C47/`2606.07555`) / placeholder=**target 채널 공급**
  (Relign "우유부단 행동 부재가 날조의 원인"의 값-수준 판).
- ★**scaffold 접점**: placeholder는 결정론으로 탐지 가능한 **타입** → 엔진이 잡아 ASK 턴/GET 라우팅.
  학습(모델)과 게이트(엔진)가 같은 인터페이스에서 만남 = 두 날개([[00]])의 정확한 분담.

## 7. ★★재프레임 (사용자 2026-07-17): placeholder → **인용-동반(citation-carrying) 도구 사용의 학습** = 논문 코어
> *"모든 날조를 rule로 막으면 scaffold 규칙이 너무 많아진다. 공통룰 — 모든 값이 인용을 밝히게 — 을 학습하는 게
> 효과적이다. tool use에서 입력·출력 출처를 명시하게 학습하는 방법 = 논문."*

### 7.1 규칙 증식의 실증 (motivation·우리 데이터)
이 세션만: TOOLGATE→PROV→FOLLOWUP→WRITE_PROV→record-grounding(예정)→match_verdict — **표면마다 게이트 1개**
+ 새 레버가 새 표면을 엶(§20 순환검증). 공통 원인 = **값이 출처 없이 나오는 인터페이스** → 검증기가 표면별
역추적 규칙을 가져야 함 = 발산. ⇒ 모델이 출처를 갖고 나오면 **검증기 1개로 붕괴**.

### 7.2 방법 (논문 방법부)
- **형식**: 모든 도구-인자 값 + 사용자-대면 주장에 인용 동반 —
  인자 `{"value": X, "src": "FIND:msg_i | GET:call_j | COMPUTE:call_k | ASK | PLACEHOLDER"}` ·
  완료/사실 주장 `evidence: "<이벤트 ref>"`(§18의 in-band 일반화·sub-call 불요=더 쌈).
- **단일 검증기(도메인-일반·결정론)**: FIND→verbatim∈해당 msg / GET·COMPUTE→값∈해당 호출 반환 /
  주장→인용 이벤트∈원장. **A2 per-tool 규칙 소멸 방향 = minimize-A2**. 거짓 인용도 대조서 결정론 검출.
  비검증 잔여 = ASK/placeholder 남용(과잉기권) → 선호쌍 1(`grounded>placeholder`)이 표적.
- **★주석 자동 생성**: gold 궤적의 값-출처는 이전 메시지/반환과의 대조로 **기계 계산 가능**
  (우리 오프라인 프로브 인프라 재사용) ⇒ SFT 인용-주석 데이터 = 무인 생성. + §2 음성/선호쌍/on-policy 그대로.
- **비용·비교성**: ①호출당 인용 토큰 오버헤드=측정 항목 ②인용은 검증기가 소비·환경엔 strip(clean args)
  → 벤치 인터페이스 불변(리더보드 comparability 유지).

### 7.2b ★★★깔때기 재프레임 (2026-07-18 사용자 통찰·실측 `FAB_PROBES_RESULTS §2b`)
> *"잡기 어려운 날조를 verify 하기 쉬운 도구명 날조로 옮겨서 쉽게 수정하게 하는 것도 논문의 주요 논점."*

- **표면엔 검증 가능성 사다리가 있다**: 도구명(✅완전·소속검사·오탐 0) > 값/record(⚠️부분·free-text 오탐=§12 사고) >
  완료 주장(❌타입상 거부 불가=C24).
- **실측된 깔때기**: `record 날조 46%` ─[A2 구성-지시]→ `도구명 날조 29%` ─[TOOLGATE 100%]→ 차단 ─→
  **ASK 24/24(전부 name/email/user ID를 물음·per-case 확인)** = **A2가 지시한 정답 경로**.
  ⇒ 레버의 "이동"은 **부작용이 아니라 기능**이다 — **위(decidable)로 옮겼기 때문**.
- **실측된 누수**: 라이브 sim1은 같은 사슬 끝에서 **아래로 샜다**(ASK 실패 → **가짜 케이스번호** = 검증 불가 표면).
- ⇒ **정식화**: *레버는 날조를 없애지 못하고 옮긴다. 위로 옮기면 이득·아래로 새면 손실.
  설계 목표는 이동을 막는 게 아니라 **아래로 샐 출구를 없애는 것**.*
- ⇒ **§7.2가 왜 옳은지의 진짜 이유**: 모든 인자 `src` + 모든 주장 `evidence` = **undecidable 표면의 소멸**.
  날조가 어디로 가든 **"출처 대조" 단일 결정론 표면**에서 잡히고 `ASK`/`PLACEHOLDER`가 **합법 출구**로 남는다.
  **코어는 "날조를 막는다"가 아니라 "깔때기의 누수를 없앤다".**
- **두 논증의 분업**: (a) **깔때기**(왜 게이트로 부족한가 = 누수) · (b) **발산**(왜 게이트를 더 못 붙이나 = 검증기 N개).
  둘 다 처방이 같다 = decidable 표면 하나로 통합. **(a)가 §7.1의 motivation을 대체하는 게 아니라 보강한다.**
- **선점 확인 대상(신규)**: "날조를 **의도적으로** decidable 표면으로 **유도**한다"는 설계 원리. DR2 24편엔 없음
  (전부 탐지·차단·기권). AgentLTL κground = decidable 검사이나 **유도 원리 아님**. → RELWORK 추가 조사.
