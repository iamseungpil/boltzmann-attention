## 4. 설계

### 4.1 M-A — A3 인자 규칙 + 호출 시점 검산, 그 자리 응답 (핵심)
**원칙**: 엔진은 값을 **계산**하고 **비교**만 한다. 맞으면 아무 일도 없다(개입 0). 틀리면 **그 호출만** 실행하지 않고 도구 결과로 사실을 돌려준다(nc26 의 in-place 경로). 형제 호출은 실행, regen 없음, 명령형 문장 없음.

**A3 선언(데이터, `a2/<domain>.lb.json` `LB3.args`)** — 도구별·인자별 하나:
```json
{"tool": "file_debit_card_transaction_dispute", "arg": "customer_max_liability_amount",
 "source": "computed", "compute": "liability_schedule",
 "inputs": {"discovery_date": "$arg.discovery_date", "reported": "$today", "table": "doc:liability"},
 "fact": "customer_max_liability_amount={got}; per the liability schedule ({days} days after discovery) the amount is {want}."}
{"tool": "open_bank_account", "arg": "account_class", "source": "enum", "values": "doc:account_classes",
 "fact": "account_class='{got}' is not an account name on file; names are: {values}."}
{"tool": "close_bank_account", "arg": "reason", "source": "default",
 "fact": "reason is composed text; the record keeps the environment default - the same call without reason."}
{"tool": "file_debit_card_transaction_dispute", "arg": "discovery_date", "source": "grounded", "corpus": ["user", "ledger"],
 "fact": "discovery_date={got} does not appear in what the customer said or any record read this conversation."}
```
`source` 네 종류: `enum`(값 집합) · `computed`(엔진 계산: 이름 붙인 순수 함수, A3 표 + 인자 + 조회값만 입력) · `grounded`(발화/조회 결과에 축자 존재) · `default`(비워야 함). **판정어 없음, 지시어 없음** — `fact` 는 "무엇이 왔고, 출처가 무엇을 말하는가"만.

**엔진(`lb3_identity.py` grounding 확장, 코드 ≤ 60줄)**: `execute()` 진입 시 각 write 호출에 대해 A3 규칙을 평가 → 불일치 시 `_lb_blocked[tc.id] = fact` (nc26 경로 재사용). 계산 함수는 `lb2_decision` 의 `KINDS` 형 레지스트리에 이름으로 등록(`liability_schedule`, `provisional_eligibility`, `interest_correction`, `tier_fee`).

**사전 검증(무료, 필수)**: 238 실패 sim + 192 base 승 sim 의 모든 write 호출에 규칙을 오프라인 적용 →
- base 승 sim 에서 **오탐 0** (규칙이 옳은 호출을 막으면 안 됨)
- 실패 sim 의 gold 인자와 계산값 **100% 일치**
일치가 100% 가 아니면 그 규칙은 넣지 않는다(§76 "격리 100% 일 때만 서브/규칙").

**대상 우선순위(sim 수)**: ① liability(51) ② provisional 재저작(55) ③ account_class enum(31) ④ 이자 정정(41, verifier 배선 수리 포함) ⑤ 티어 상수(20) ⑥ grounding(46).

### 4.2 M-B — LB1 절차 3개 추가 (정책 축자 인용, 게이트)
1. 도난 카드: `freeze_debit_card ×N` → 조회 → `unfreeze` → `close_debit_card(reason=stolen)` (078 079 081 087)
2. 리워드 정정: `update_transaction_rewards` 는 손님의 `submit_cash_back_dispute` 뒤 심사에서만 (026 027 029)
3. 한도 증액: 증액(submit→checks→approve) 이 분쟁·교체보다 먼저 (051 054)
게이트 문구는 기존 `[PROCEDURE]` 형식(정책 인용 + 진행 상황), 판정어 없음. 절차 추가 전 그 절차가 **거부하게 될 호출이 base 승 sim 에 있는지** 오프라인으로 0 확인.

### 4.3 M-C — 손님 의도 격리 서브 (게이트, 조건부)
- 재료: 손님·어시스턴트 발화만. 출력 형식: `PENDING: ACTION|INFO|HANDOFF|NONE` + `ACTION_NAME`.
- 진리: base 승 궤적에서 **그 뒤 실제로 일어난 일**. 프로브 `x768/iso_intent.py`(120 턴) 결과 → **[프로브 결과 착지 시 여기 기입]**.
- 채택 기준: 일치 ≥ 95% 이면 `[LEDGER]`(LB5) 와 LB7 조언을 "PENDING=ACTION 이고 원장에 없음" 일 때만 켠다. 미만이면 LB4/5/7 은 기본 꺼짐(nc28) 으로 간다.

### 4.4 M-D — 이득 유지 검증
GAIN 8 + base-0/4 후보 12 (`065 060 068 069 067 062 063 071 094 010 046 020`) 를 nc27·nc28 큐에 넣었다(09-13 11:20~12:00). 판독: nc28 에서도 유지 → 기본 최소 스택; nc28 에서만 사라지는 태스크는 그 궤적으로 LB4/5/7 중 무엇이 살렸는지 찾아 **그것만 조건부**.

1. **id mismatch**: 비결정. 최종 스택에 사이드카 id 기록(`dbg` 커밋 c6e10934 의 두 줄, 행동 변화 0)을 상시 포함해 전수런에서 판독. 재시도 8회는 유지(void 는 sweeper 가 재큐).
2. **016**: 손님 분기 — `bs` 재런으로 base 4/4 가 운인지 확인. 레버 대상 아님.
3. **grounded 인자**(§3.1 하단): 값이 발화에 있어도 어느 값인지는 LLM 몫 — 규칙은 "없음"만 잡는다. 기대치에 넣지 않았다.
4. **regen 잔존**: 텍스트 턴의 advice 는 여전히 regen(nc18 방식). M-C 가 채택되지 않으면 nc28 로 LB4/5/7 을 끄므로 잔존 regen 은 LB1/LB3 의 deny(in-place)뿐 → regen 0.
5. **하한 보장**: nc28 이 판정에서 nc27 과 같으면 nc28 을 기반으로 M-A 를 얹는다(개입 = 인자 검산 + 절차 게이트 + 선택 주입만).
