## 5. 새 스택 A/B 실험 설계

### 5-1 스모크 (엔진 1대 독점 시 40~50분)

목적이 둘이라 태스크도 둘로 나눈다.

**가드 10건** — base 4/4 & Max 4/4 에서 빠른 것 + 우리 우위 2건.
`002 004 015 006 050 076 005 035` + `007 090`
→ nt=2. **하나라도 떨어지면 버그다. 그 자리에서 세우고 궤적을 본다.**
（`f8b4f775` 커밋이 기록하듯 LB7 deliver 가 base 4/4 인 task_004 를 2/4 로 떨어뜨린 전례가 있다.）

**이득 8건** — flip 이면서 Max 에 여유가 있는 것, 빠른 순.
`033(2→3) 012(3→4) 021(3→4) 099(2→3) 003(2→3) 073(3→4) 070(2→4) 078(0→3)`
→ nt=4. base 기준값 = 이 8건에서 **15/32**. 합산으로만 판정한다(개별 등락은 노이즈).

**제외**: HARD 25개 · 055 · 059 · 094 · 058.

### 5-2 판정 규칙

1. 가드 10건 전승 + 크래시 0 + 레버 **실발화율 > 0**(단위테스트 통과 ≠ 라이브 발화).
2. 이득 8건 합산이 15/32 보다 오를 것.
3. 둘 다 통과해야 97 전수 A/B 로 넘어간다.

### 5-3 전수 A/B

97 태스크 nt=4 짝 A/B. 큐는 **대표 태스크 우선**으로 짠다 —

## 6. 운영 — 클라우드 엔진 (반드시 지킬 것)

`.153` 은 프로브 전용(8141). **장기런은 클라우드 A100 2대(터널 9141/9143)** 이다.

```
KV cache            634,267 토큰 (A100 80GB · Q3.8-27B-FP8)
sim 1개 최대 컨텍스트  131,072  (엔진 자체 보고 «Maximum concurrency … 4.84x»)
⇒ eviction 무발생 상한 = 엔진당 동시 4 sim.  5 이면 최악 655k 로 예산 초과.
```

- **동시성 숫자를 올려도 소용없다** — 한 태스크는 sim 이 4개뿐이라 `--max_concurrency` 5 이상은
  효과가 정확히 0이다. 엔진에 더 물리려면 **태스크를 겹쳐야** 한다.
- 실제 손실은 **낙오 꼬리**였다: 4 sim 중 셋이 끝나면 남은 하나가 혼자 돌아 44 tok/s 로 떨어진다
  (4개일 때 119 tok/s). 9141 은 시간의 59% 를 요청 1개로 보냈다.
- 그래서 채택한 형태 = **엔진당 conc 2 워커 2개**(= 항상 4 sim, 최악 524k = 예산의 83%).
  적용 후 9143 평균 생성이 95 → 145 tok/s, 선점 0건.
- 계기: `Waiting` 이 0 이면 엔진은 포화가 아니다. GPU util 100% 는 단일 디코드에서도 찍히므로
  포화의 증거가 **아니다**.
